# 对话内人话摘要（Chat Recap）

## 1. 背景与问题

当前 `Coder/20_Workflow_Lifecycle/delivery-summary.md` 仅规定了落到 `deliveries/YYYY-MM-DD-<slug>.md` 的**正式文件结构**（§4 最小结构，7 个小节）。规则体系**没有约束** AI 在对话框内给用户的收尾汇报风格。

实际使用中，AI 倾向于把正式文件的 7 小节结构原样复述到对话里，导致对话层输出过于"官方"、冗长、缺乏判断、不讲人话，降低了人机协作体验。

用户诉求：

- 对话里给一段自然、口语化、能快速判断是否真闭环的人话摘要。
- 归档文件（`deliveries/*.md`）仍按现有正式结构产出，不降级。

核心观点：**Delivery Summary 是同一事件的两种表达 — 对话层（口语）与文件层（正式）分层、同源、同触发。**

## 2. 目标

1. 在不破坏现有交付文档结构的前提下，为对话层输出新增一套风格约束。
2. 规则改动最小化，不引入新文件、不动目录结构、不动读取顺序。
3. 对话摘要要能独立说清"做了什么 / 有没有风险 / 下一步"，不依赖用户自己去 `deliveries/` 翻文件。
4. 同时给出正式文件的入口路径，便于归档检索与对外交接。

## 3. 非目标

- 不改动 Delivery Summary 的触发条件（§2 原样继承）。
- 不改动 `deliveries/` 文件的最小结构（§4 原样保留）。
- 不回溯迁移已生成的历史 Delivery Summary。
- 不覆盖 checkpoint / handoff / `.ai/` 运行态文件的既有职责。
- 不把"对话说人话"下沉到除 P5 完整闭环以外的其他阶段（P2 ACK、P3 ACK、阶段 checkpoint 等均不适用）。

## 4. 设计方案

### 4.1 落地形式

在 `Coder/20_Workflow_Lifecycle/delivery-summary.md` 内**新增一节 §8 对话内人话摘要**，排在现有 §7「与执行流程的关系」之后。不新建独立规则文件，不改变目录结构与读取顺序。

选择依据：对话摘要本质是 Delivery Summary 在对话层的表达形式，二者同源同触发，放在同一规则文件最便于读者建立"文件 vs 对话"的对照心智。未来若对话层约束膨胀到 3 条以上再考虑拆分。

### 4.2 §8 节内容

节内容骨架如下：

**触发**：与 §2 Delivery Summary 相同时机。若不满足 §2 触发条件（中途暂停、等待 ACK、只是 checkpoint），也不生成本节规定的对话摘要，继续走 checkpoint / handoff 口径。

**形式**：3–6 句中文散文。禁止输出任何编号小节标题（不得复述 §4 的 4.1 / 4.2 结构）。禁止铺排长 bullet 清单；若非用 bullet 不可，至多 2 条，且每条 ≤ 1 句。

**内容核心**（缺一不可）：

1. 做了什么：用户视角的最终结果，一句话说清。
2. 有没有风险 / 延后事项：有就说有；没有则显式声明"本轮无剩余风险"，不得用"一切顺利""已完成""已闭环"等模糊套话替代。
3. 建议下一步：例如"交付即止"、"需要你 ACK"、"建议后续迭代 X"。

**收尾**：最后单独一行引用正式版文件路径，固定格式：

```
正式版：deliveries/YYYY-MM-DD-<slug>.md
```

**与 §4 的关系**：§4 定义 `deliveries/` 文件的书面结构，§8 定义对话层表达。两者同源、同触发，但风格分层：文件正式、对话口语。不得用文件结构覆盖对话风格，也不得用对话口吻替代文件结构。

### 4.3 连锁修改

除 `delivery-summary.md` 外，还需：

- **`Coder/20_Workflow_Lifecycle/lifecycle.md` P5 Verify 段**：在现有"还应额外生成给人看的交付总结，结构参考 `delivery-summary.md`"一句后，补一句说明：P5 输出对话回应时，应同时遵守 `delivery-summary.md §8` 的对话层风格约束。
- **`Coder/README.md`**：不改动（无新增文件，目录与读取顺序不变）。
- **`templates/rule-card.md`**：不改动。该文件定位是启动即读的最高优先级硬约束，对话摘要属于 P5 收尾细节，塞入会稀释关键约束密度。
- **`Coder/CLAUDE.md`**：不改动。规则仓库自身协作约定层，与交付风格规则不在同一层。
- **历史 `deliveries/*.md`**：不回溯、不迁移。规则只对未来新交付生效。

## 5. 验收标准（草案，供 P2 细化）

1. `delivery-summary.md` 出现 §8，字段覆盖：触发、形式、内容核心、收尾、与 §4 关系。
2. §8 中"形式"明确写出"3–6 句"、"禁止编号小节标题"、"禁止铺排长 bullet"三条硬约束。
3. §8 中"内容核心"明确列出三项，且对"无风险"场景有反模糊口径。
4. §8 末尾包含 `正式版：deliveries/YYYY-MM-DD-<slug>.md` 的固定引用格式。
5. `lifecycle.md` P5 Verify 段出现对 `delivery-summary.md §8` 的显式引用。
6. `Coder/README.md`、`templates/rule-card.md`、`Coder/CLAUDE.md`、目录结构、读取顺序均未改动。
7. 规则新增后可以通过阅读 `delivery-summary.md` 单文件，一次性读懂文件层与对话层两种表达约束。

## 6. 风险与边界

- **规则密度风险**：`delivery-summary.md` 从 7 节扩到 8 节，文件变长但职责聚合。若未来对话层约束继续增加（≥ 3 条独立风格规则），应评估拆分到独立 `chat-recap.md`。
- **被误用风险**：AI 可能把"讲人话"误解为"可以省略风险声明"。通过"反模糊口径"（必须显式说"本轮无剩余风险"）兜底。
- **双写漂移风险**：对话摘要与 `deliveries/` 文件可能在细节上不一致。设计上二者同源，但实现时 AI 应以文件为结论真源，对话摘要只是其口语化投影。

## 7. 交付物

- 更新 `Coder/20_Workflow_Lifecycle/lifecycle.md`（P5 段补充引用）。
