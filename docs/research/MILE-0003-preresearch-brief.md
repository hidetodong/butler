## 1. MILE-0003 是什么（一句话）

现在每个项目的"整体说明"是一个薄薄的文件 `.ai/PROJECT.md`——里头就几个关键词加一句"细节自己看代码"。

MILE-0003 要把它**升级成一个说明文件夹**：随着每次干活越补越全，AI 读完就真知道"这个项目里有啥"，而不是只看到几个关键词。

它拆成三块：

- **主体**：知识文件夹本身（把 `PROJECT.md` 拆成 `.ai/project/` 文件夹、定维护规矩）。
- **子项一**：帮手名册（给 butler 派出去干活的几个"帮手 AI"立个名册 + 通用规矩）。
- **子项二**：说人话（让 butler 的输出别堆术语黑话，覆盖对话和落地文档）。

## 2. 要做什么（路线）

### 主体：说明文件夹（5 步）

1. **定文件夹长什么样**——把一个 `PROJECT.md` 文件拆成一个 `.ai/project/` 文件夹，里面按主题分文件（项目定位、架构地图、现在能做啥、约束、欠债……），配一个入口目录页。定清楚每份写多满、多详细。
2. **定维护规矩**——每次干完活收尾时，把"这次改了啥"更新进对应的主题文件（现在可做可不做，改成每次必做）。再加一条自检：定期核对"文件夹里写的"跟"真实代码"对不对得上，对不上就报出来。
3. **改冷启动**——让 AI 每次接手项目，第一件事先读这个文件夹。（"冷启动"就是 AI 没有任何上下文、从零开始接一个项目的时候。）
4. **部署新项目 + 老项目迁移**——新项目一部署就带上空模板；已经在用 `PROJECT.md` 的老项目，怎么平滑升级过来。
5. **拿 butler 自己练手**——用新结构把 butler 现在的状态重写一遍，验证这套真能用。（这叫"吃自己的狗粮"：先在自己身上用，用着没问题再推给别人。）

## 3. 帮手名册：定下来的关键决定

（详细版在 `MILE-0003-agent-doc-design.md`，这里是精简+自包含的决定清单。）

**背景**：butler 派出去干活的"帮手 AI"一直是散的——现在真正的帮手只有"复核"一个，可它的说明摊在 5 个文件里各写一遍。该立个名册。正好 MILE-0003 把帮手从 1 个变 3 个，是立名册最顺的时机。

### 三个帮手（这一轮都设计）

| 帮手 | 干嘛的 | 啥时候被叫起来 | 只准碰 |
|---|---|---|---|
| **复核** | 拿验收标准挨条核对写得对不对，挑出错就拦住收工 | 交付验证阶段 | 只看，不改代码 |
| **更新说明** | 把这次的改动写进项目说明文件夹（也就是第 2 节主体那个文件夹） | 每次收工、且这次动了结构 | 只改说明文件夹，别的不碰 |
| **查过时** | 对着真实代码查说明有没有过时，过时就报出来 | 冷启动 / 收工时抽查 | 只看，不改 |

### 关键决定（这几轮拍板的，最容易在移交时丢，务必记住）

1. **帮手 = 一份定义资料，用时读，不发到项目里。**
   一个帮手就是一份大白话说明（说清它是谁、给它什么、还你什么、能碰什么），放在 butler 规则里。butler 要用哪个，就当场读它的定义、临时起一个干净的子 AI 去干——**跟现在的"复核"（也就是 `/review` 命令）一模一样**。
   → **明确否掉**了早前"把帮手定义文件像发插件一样带进每个项目"的方案（那样要改部署、升级、迁移三处，用户判定"搞复杂了、不需要"）。

2. **"折叠帮手"这一轮就做，不算抢跑。**
   "更新说明"帮手（把这次改动收拢进说明文件，这个动作叫"折叠"）本来就是 MILE-0003 要设计的东西。父设计里"自动化留以后"那句得**改准**：留以后的是"完全没人管的后台自动跑"，不是"收尾叫帮手来折叠"。

3. **权限靠"约定 + 如实说"，不追"工具层硬拦"。**
   想让"复核只能读、更新说明只能写某个文件夹"变成机器层面拦死，技术上做得到一半（限定能用哪些工具），但"只准写哪个文件夹"这种细粒度得再加一层按路径放行的配置。**这一轮不追这个**，权限靠定义里写清规矩 + "叫不起来就如实说、绝不假装做过"兜着（跟现在 `/review` 一样）。硬拦是可选的，留以后。

4. **"复核"帮手的说明要三拆。**
   现在 `60_review`（复核那套规则）里的东西按性质拆开：共享的审查流程留原地；所有帮手都通用的规矩（比如"检查类帮手必须干净上下文""叫不起来如实说"）提到名册总述里当唯一出处；"复核"自己专有的契约放进它自己的文件。
   - 一处要改准的事实：**"叫不起来就如实说"这段话，现在只在一个文件里写了正文**（`review-engine §6.4`），另外两处（`dangerous`、`verify-schema`）是引用它。改的时候按"一处留正文、其余都指过去"来，别当成"好几处各写了一遍"去删。

5. **名册放哪：** 建议单开一个新目录 `Coder/62_Extension_Agents/`（挨着复核那套），**别放进管"AI 是谁、怎么干活"的身份规则那层**（`00_System_Prompt/`）。文件夹里的文件不带数字前缀（叫 `overview.md`，别叫 `00_overview.md`）。落点开题时最终确认。

6. **两个硬事实错要顺手改**（写在设计稿 §7）：
   - "`AGENTS.md` 这个规范是 OpenAI 起的"——错了，是 Sourcegraph 公司的 Amp 团队先发起的（当时叫单数 `AGENT.md`），后来 OpenAI 的 Codex 推广带火。
   - "Agent Skills 三十几家采用"那个数字，加个时间点（"截至 2026 上半年"），免得过一阵就过时。

## 4. 说人话：三条标准 + 怎么落地

**要解决的问题**：butler 的输出（分析、审计、方案、聊天、交付文档）容易堆术语黑话，看着专业其实难懂。**注意"简短"和"好懂"是两码事**——话说短了、结论先行了，照样可能满是黑话看不懂。

### 三条硬规矩

1. **术语先解释**：专业术语、缩写、生造词第一次出现，后面紧跟一句大白话。
2. **比喻要落地**：比喻能用，但紧跟一句"就是说……"把它说实；别用生僻牵强的比喻硬凑。
3. **别让英文 / 变量裸奔**：英文词、变量名、文件名别光秃秃混在中文句子里当正文；要用就带一句它是什么。

外加一个动作：**发长东西（方案 / 审计 / HTML）之前，自己先对着这三条过一遍再发。**

### 覆盖范围

对话和落地文档都要说人话，只是**落地文档措辞再严谨些**（少点口语、精确一点）。

### 怎么落地（一个要在新电脑上做的决定）

现在这三条只写进了原电脑的**个人说话风格设定**（`~/.claude/output-styles/matrix.md`，Claude Code 里控制"AI 怎么说话"的一层，在最靠近模型行为的地方）。但那是**个人配置、不跟 git 走**，换电脑就没了。

→ 所以要让"说人话"真正跟着 butler 走（换电脑、换项目都在），应该**把这三条写进 butler 规则本身**：
- 对话那层写进 `presentation-protocol`（管对话怎么呈现的规则）；
- 文档那层写进 `artifact-style`（管交付文档怎么写的规则，现在只管"四件套"那种正式产物，要扩到所有面向人的输出）。

个人说话风格设定（output style）是"这台电脑上先用着"的临时手段，真正的落点是 butler 规则。这块作为 MILE-0003 的一个子项一起做。
