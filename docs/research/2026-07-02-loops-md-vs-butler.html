1这篇文章是什么

《LOOPS.md: Field Notes on Agents That Run for Days》，署名 Andrej Karpathy，一份"长程 agent loop 工作笔记"，重排成会议论文体，共 9 条原则。核心论点一句话：

大多数 agent 系统死掉，不是因为模型弱，而是因为 harness（外壳）弱。模型能写码、能评码、能对着十分钟前自己认同的 rubric 验收自己。它唯一做不到的，是决定何时停、何时重启、结果写到哪——那才是 loop 的工作。

一句话结论：前四条 butler 做得比他更严；后四条正好戳中 butler 的盲区。

3同频处（butler 甚至更强）

I / III / IV 三条，butler 是这份手记的严肃工程化版本：

  • 契约先行（III）：他说"原始 spec 是边界，被打分的是契约"——正是 butler 的 CONCEPT.md(边界)→AC_LIST.md(被验收)双层。缺一条他的警戒："27 条对小 app 合理，10 条太少、评估者会盖橡皮章。"
  • 写盘不写上下文（IV）：他说 context "会撒谎、会压缩、会 rot"；你们原话"关键状态只存在于对话上下文里"是长任务劣化根因。判据几乎逐字一致，且 butler 走得更远（读序 / 5 条一致性自检 / clean-slate / hook 机械拦截）。
  • 反自欺护栏：butler 的"禁止降级修复"、独立复核"环境不支持就如实标注、不得冒称已独立复核"——这类护栏文章里没有，是 butler 领先的地方。

一个诚实的差异：他主张 3 个文件能描述完的状态才不算太复杂；butler 是 6+ 件套。按他的尺子，butler 状态 schema 偏重——这条直接接到第八条。

4分歧与缺口（真正值得想的部分）

V让 loop 重启 —— 最锋利的分歧

Karpathy 原话很激进："前沿模型最好的行为是愿意把一切推倒重来……第 9 轮删掉整个项目、第 11 轮交出能跑的版本。别打断它。重启就是 loop 在正确工作。只有契约本身错了才插入人类，而不是 build 错了的时候。"

Karpathy

给它干净评估者 + 落盘契约 → 删了重生成。restart 是特性，别打断。

⚔

butler

熔断（5 轮/3 同错/环境阻塞）→ 写 RCA、交还人类。patch-forward，无"弃码重生成"档。

诊断一致（打补丁攒出考古现场），药方相反。关键：他重启的两个前提——干净评估者 + 契约落盘——butler 全都有（AC_LIST 在盘上、独立复核就是干净评估者）。即 butler 技术上完全具备安全重启的条件，只是刻意没扣扳机（与"并行迭代/半自治先按住"的保守取向一致），值得重新过一遍。

VI给主观打分 —— 干净的缺口

"品味是可打分的，只要写下来。四加权轴：design / originality / craft / functionality。用 3 好 + 3 垃圾样例校准。输出 0–1 分 + 一段解释差距的话。模型不发明品味，只朝你描述的品味收敛。"

butler 验收是结构性二元的（pass/fail 绑可测 AC），review-standard 全是客观项。"设计好不好看、文案顺不顺、交互优不优雅"这类无法二元判定的东西，butler 只能推给人在 AC 冻结时拍板，验收阶段无法自动评。你们有 Vue3/前端 profile，这个缺口是实打实的。

VIII删掉 harness —— 直接照进 butler 的镜子

"harness 存在是为了补偿模型。模型一变强，你上季度写的一半变成负重……单调增长的 harness，是一个你已经停止阅读的 harness。拿每个新模型版本重读它，把模型现在能免费做到的都删掉。"

butler 目录就是单调增长的活证据：00→10→20→30→40→50→55→60→65→70→99，每次迭代都在加模块/schema/hook。有 butler-upgrade、migration、版本流——全是"加"和"迁移"，没有一条是"随模型变强而裁剪/收缩"。记忆里那个"待优化清单"也是往里加。

必要的反驳：butler 的 harness 不全是补模型弱——很大一块服务人的治理（审计 / 交付总结 / 跨会话交接 / 门禁）。他的语境是单人放手让一个模型跑几天；你们是团队 / 可复用 / 可审计。所以"删"不能无脑套。但"每逢前沿模型迭代就重读一遍问‘这条现在模型免费做得到吗’"这个纪律动作，butler 完全没有——这才是最该抄的。

VII·IX半对的两条

读轨迹（VII）：他把 debug 洞见全归功于"读原始 transcript、grep 到判断跑偏那一刻、只改那一处、再跑"。butler 有 RUN_LOG/BUG_LOG，但那是产品审计用，不是给 butler 规则自身做元改进用。缺一条"读真实轨迹→定位规则跑偏点→改那一条规则"的成文实践。

瓶颈会移动（IX）：butler 演进史恰好走了他的阶梯（编码→规划→验证→品味），preference-probe 已摸到"品味"层。但他强调"ship 一个更小的 harness"——butler 每次 ship 更大的。按阶梯，butler 现在的前沿瓶颈就是品味，而 butler 有 preference-probe（学人的选择）却没有 taste-scoring（给主观质量打分，即第 VI 条）——两件事在这里交汇。

6一句话的元判断

butler 与 LOOPS.md 在"地基"上高度同频——loop 不是 prompt、状态写盘、契约先行、角色分离，这四条 butler 做得更严、更工业化、更可治理。分歧全在"前沿姿态"上：Karpathy 更激进、极简、信任模型（推倒重来 / 删壳 / 给品味打分）；butler 更保守、全面、以人治理为中心。

这不是"谁对"，是两个不同的设计中心：他优化"单个专家从一个前沿模型榨出最大杠杆，仪式越少越好"；你们优化"跨项目、可审计、可复用、可交接的可靠交付"。借鉴要带判断，别 cargo-cult。

但有一条建议认真当回事

"单调增长的 harness，是一个你已经停止阅读的 harness。" butler 目前只有"加"和"迁移"机制，没有"随模型变强而删"的机制——这恰恰是文章诊断的、也是"待优化清单"越堆越高的病根。第八条比第五、第六条更根本。

LOOPS.md: Field Notes on Agents That Run for Days · A Short List of Rules for Letting the Model Drive · Andrej Karpathy, Independent Researcher · © 2026（reformatting of loops.md, r060726）

Abstract. This file exists because most agent systems die not from a weak model but from a weak harness: the model can write code; the model can review code; the model can verify its own output against a rubric it agreed to ten minutes ago. What it cannot do, on its own, is decide when to stop, when to restart, and where to write the result. That is the work of the loop. The pattern treats the loop as a first-class object: roles are separated, state lives on disk, contracts are negotiated between agents before the first line of code is written, and the harness is read like a stack trace whenever something goes wrong. Short loops, simple state, clean contracts. Everything else is decoration.

I. Write the loop, not the prompt

A prompt is typed once and forgotten; a loop runs while you sleep. The unit of leverage stopped being the prompt the moment models could follow a procedure without supervision. If you iterate on a single message at 3am, you are still in the prompting era. The loop is short: gather, reason, act, verify, repeat — everything else is a footnote to those five verbs.

II. Separate the roles

Three roles, three context windows, three system prompts. A planner that turns a vague sentence into a sprint spec and never touches code. A generator that writes everything and is forbidden from grading its own work. An evaluator that reads diffs, launches playwright, plays the app, and is told from the first message that the code is broken and its job is to prove it. Mixing roles is the most common failure: the model becomes sycophantic the moment it grades itself, and the loop converges on slop.

III. Negotiate the contract first

Before the generator writes a line, it proposes what "done" looks like and the evaluator pushes back. They argue via markdown files until they agree on a checklist of testable assertions. Twenty-seven criteria is reasonable for a small app; ten is too few and the evaluator rubber-stamps. The original spec is the boundary; the contract is what gets graded. This single change moved runs from broken-bones to working products.

IV. Write to disk, not to context

Context windows lie: they compact, rot, and hide what you said an hour ago. A file on disk does not. Keep feature_list.json, progress.md, contract.md, and an append-only log.md with ## [YYYY-MM-DD] | title entries. The model should be able to crash, lose its session, and pick up by reading three files. If you cannot describe your state in three files, your state is too complicated.

V. Let the loop restart

Counter-intuitively, the best behavior of current frontier models is the willingness to throw everything away and start over when a run goes sideways. Older models patched until the codebase resembled archaeology; newer ones, given a clean evaluator and a contract on disk, will delete the project at iteration nine and ship a working version at iteration eleven. Do not interrupt this. The restart is the loop working correctly. Insert a human only when the contract itself is wrong, not when the build is.

VI. Score the subjective

Taste is gradable if you write it down. Four axes, weighted: design, originality, craft, functionality. Calibrate on three reference sites told to be good and three told to be slop. Output is a number between zero and one plus a paragraph explaining the gap. The model will not invent taste; it converges toward the taste you described. The whole game is writing the rubric carefully enough that converging toward it is what you actually wanted.

VII. Read the traces

Every debugging insight about agent loops came from reading the raw transcript, not running another experiment. Pipe the agent's output to a file, grep for the moment its judgment diverged from yours, edit the prompt for that exact moment, run again. Same muscle as reading a stack trace — except the trace is in English and most of it is the model talking to itself. Skip this and you are tuning by vibe.

VIII. Delete the harness

The harness exists to compensate for the model. As the model improves, half of what you wrote last quarter becomes overhead. Context-restarting between sessions was load-bearing for one generation and dead weight for the next; sprint decomposition was the only thing keeping a four-hour build coherent and is now a constraint on a model that holds two hours in its head. Re-read your harness against each new release and delete anything the model now does for free. The harness that grows monotonically is a harness you have stopped reading.

IX. The bottleneck always moves

When coding stops being the bottleneck, planning becomes the bottleneck. When planning is solved, verification becomes the bottleneck. When verification is automated, taste becomes the bottleneck. You do not finish; you find the next thing to fix. The whole point of the loop is to make the next bottleneck visible. Find the new bottleneck, fix it, ship a smaller harness, repeat.
