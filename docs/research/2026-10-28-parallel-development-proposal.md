# Butler 并行开发可行方案

建议先做一个迭代内的两个执行槽：主 Agent 负责需求、方案和最终验收，两个 worker 在独立工作树里实现，检查通过后逐个集成。复用现有阶段门禁、范围检查和证据工具，只新增任务包与结果检查这一层；用真实任务验证收益后，再扩大并发。

这是供讨论的候选方案，不是已批准的 TECH_PLAN，也没有启动里程碑、迭代或并行任务。文中的新工具、路径、字段和验证要求均为拟议设计；仓库现有能力单独列在下一节。本文不是 Decision Map，不维护决定、领取或执行状态。

## 2. 首版范围与使用方式

首版只支持：单仓库、同一台机器、一个 active 迭代、同一批最多两个代码 worker、一个负责集成和验收的主 Agent。一个执行槽就是一份边界明确的 P4 工作包，不是子迭代。

用户可以在正常迭代中说“这次实现允许并行”。主 Agent 在 P3 说明切分和代价，方案准入后再派发；用户已经明确授权该方案内的并行实施时，不逐槽重复询问。

- 主 Agent 独占需求、AC、方案、运行状态和收口判断；worker 不能改变这些权威状态。
- 第一批固定两个槽，不建设自动扩容、任务抢占、分布式队列或自动重试。
- 不新增 `/parallel` 工作流或默认配置项。未启用时，原来的串行路径不受影响。
- 需要多个仓库联动、共享数据库迁移或大量共同修改核心文件的任务，首版使用串行流程。
- 原生消息只作为通知通道。没有消息能力时，用任务包与回执交接；没有可靠的独立工作目录时退回串行。

P1–P3 的资料调查可以利用既有研究能力并行进行，但需求和方案的最终写入仍由主 Agent 串行完成。本次新增范围只覆盖 P4，不扩建另一套研究调度器。

## 3. 什么任务才适合并行

必须同时满足以下条件，才进入一批并行执行：

1. 每个槽都有可检查的产物和验收映射，能够独立推进一段足够完整的工作。
2. 写入路径互斥；接口、数据格式和外部行为约定已明确。
3. 一个槽不需要等待另一个槽的内部实现才能继续。
4. 测试和运行资源能隔离，或者争用环节被明确串行化。
5. 拆分、初始化、集成和返工成本预期低于节省的等待时间。

目录不同不能证明可并行。接口签名、配置默认值、数据库结构、全局注册表和锁文件都可能形成隐含依赖。依赖文件、生成文件和共享配置必须指定一个负责人；首版优先在派发前串行完成这些改动。

不按“前端、后端、测试”机械分成三槽。测试应尽量跟随其行为所在的实现槽；例如两个独立命令各自拥有实现和测试，比“两个实现者共用一个测试槽”更容易划清责任。独立复核另按已有 P5 条件执行。

## 4. 正常执行过程

| 步骤 | 负责人 | 必须得到的结果 |
|---|---|---|
| P3 切分 | 主 Agent | 两个槽的目标、AC、路径、契约、依赖和验证方法明确；方案通过准入 |
| 准备基线 | 主 Agent + 检查工具 | 代码基线可定位，规格与运行输入冻结，工作树和资源分配完成 |
| 并行实现 | 两个 worker | 各自在指定工作树内实现和测试，返回提交与结果声明 |
| 逐槽核对 | 检查工具 + 主 Agent | 机器检查范围和身份，主 Agent 检查契约与行为；问题返回原槽 |
| 临时集成 | 主 Agent | 在可丢弃的集成工作树逐个应用成果，检查组合行为 |
| P5 验证 | 主 Agent + 既有工具 | 在实际集成代码上生成证据，完成现有 Goal 与复核流程 |
| 交付与清理 | 主 Agent | 成果与记录已保留；无未归档工作后清理本次工作树 |

代码提交和合并只在已获授权的范围内执行；并行模式不额外授权推送、发布或修改远端保护。

## 5. 最小合同与记录落点

### 5.1 计划只保存在 TECH_PLAN

在现有 `## Design Decisions` 内增加 `### 并行执行`，内含一个带版本标记的 JSON 代码块。它是槽定义唯一的计划来源，不再手工维护内容相同的第二张表。无该块时，所有并行检查返回不适用，沿用串行行为。

每个槽至少包含：槽 ID、目标、AC ID、可写路径、必要只读输入、契约、依赖、合并顺序、验证命令与停止条件。首版写路径只用明确文件或带尾斜线的目录前缀，不设计复杂的 glob 交集算法。删除和改名必须同时核对原路径与目标路径。

所有槽的写入范围必须落在方案允许范围内；存在 PRD 范围时，再调用既有解析器求交集。没有 PRD 时，不能跳过槽范围核对。真实路径检查拒绝目录逃逸与符号链接绕过；共享目录必须进一步细拆到不重叠的所有权。

代码基线、当前宿主句柄和工作树绝对路径属于派发事实，由主 Agent 在 prepare 时填写，不作为设计方案反复变更的理由。接口、AC、写范围或验证方法变化才回到 P3 重审。

### 5.2 任务包保存派发时的事实

拟新增 `.ai/parallel-work/<ITER>/dispatch-<n>/`。只有主 Agent 通过检查工具写这里；worker 在自己工作树之外的指定临时输出目录交还结果，由主 Agent 校验后收存。

```text
dispatch-<n>/
  packet.json                 # 同一批次的冻结输入、槽定义和基线
  snapshot/                   # 启动所需的白名单文件及摘要
  slot-a/attempt-1/result.json # 第一份不可变结果
  slot-b/attempt-1/result.json
  integration-1.json          # 此次集成、核对和证据关联
```

packet 记录迭代、派发批次、代码基线 B、输入文件摘要、槽合同、宿主实际能力、工作树与资源分配。基线 B 必须包含本批所需源码和依赖锁文件；不能拿“主工作区还有一批未提交代码”冒充可复现基线。规格文件可以未提交，但必须单独冻结和记摘要。

result 绑定 packet 摘要、槽 ID、attempt ID、最终提交 W、实际文件清单、AC 对应关系、已运行验证、偏差与风险。实际路径和提交关系由工具计算，不信任 worker 自报清单。失败或中断也可以返回结果，但不算完成；重新执行写新的 attempt，不覆盖旧回执。

派发记录是历史事实，不是第二套活方案。活进度仍由主 Agent 写进 `task-state.md`，只引用派发路径和下一动作；检查工具依据记录与 Git 事实恢复，不建立全局任务索引或第二个可写状态机。已保存但属于旧批次的结果仅供参考，不能自动进入当前集成。

### 5.3 只新增一个小型检查工具

拟新增 `tools/parallel-work/`，能力收敛为：

| 能力 | 作用 | 不负责 |
|---|---|---|
| prepare | 核对当前迭代和方案、槽边界、代码基线、工作树根与冻结输入，发布一次性任务包 | 不替用户批准方案，不启动 Agent |
| check-result | 检查提交祖先关系、完整改动路径、输入漂移和结果身份，收存不可变回执 | 不把测试声明判为 AC 已通过 |
| inspect | 从现有记录与 Git 恢复当前可继续的动作，报告缺口与旧结果 | 不猜测失联 worker 已结束 |
| check-integration | 核对集成来源、代码状态、证据关联及主线是否仍可接入 | 不修改 Goal 或宣布迭代完成 |

首次实现需要一个本机协调器写锁和只创建不覆盖的文件发布机制，保证两个误开的主会话不能重复发布同一身份。这里只保护记录发布，不是跨机器锁服务，也不承担 Agent 认证。

## 6. 工作树如何启动，隔离到什么程度

每个 worker 从同一代码提交 B 建立独立工作树，集成使用第三个临时工作树。宿主自带可靠工作树管理时调用宿主能力，否则主 Agent 使用普通 Git 工作树；具体实现必须经真实能力探测，不能只按宿主名称推断。

现有门禁需要读取项目 `.ai/`。因此 prepare 必须把**启动所需的最小冻结输入**放进 worker 工作树，并将其标为执行镜像：它没有独立迭代身份，不允许推进生命周期，也永远不参加成果合并。

白名单通常包括当前阶段产物、迭代身份、项目配置，以及这些检查真正读取的 PRD 切片、范围地图和必要入口。确切清单应由首个部署项目的门禁演练确定；缺文件就报告输入不完整，不能关闭 hook 或使用 bypass 继续。

原有多宿主规则强调共同读取一份权威 `.ai/`。实施本方案时必须同步说明“冻结执行镜像”的例外与无写权边界，否则不能仅靠提示词偷偷创建第二套活状态。镜像内容前后核对摘要；`.ai/`、宿主入口、hook 配置及 Git 管理数据默认禁止进入 worker 业务提交。

镜像可能使工作树出现预期的未提交文件。检查工具要区分“准备阶段留下且摘要未变的镜像”和“worker 新增或修改的内容”；源码及测试不得残留未提交成果。worker 使用精确路径暂存，不能用全目录暂存把镜像带入提交。不得修改共享 `.git/info/exclude` 来掩盖变化。

运行资源也按槽分开：端口、数据库或 schema、临时目录、测试输出目录。无法隔离的资源串行使用；首版不共用可变测试数据库。

**工作树不是安全沙箱。** 它隔离检出文件，不隔离 Git 公共元数据、整个文件系统、凭据或外部服务。worker 不操作其他工作树、主线分支、共享 Git 设置和远端。宿主有能力时收窄写入授权；能力不足时如实记录，并依靠范围审计兜底。需要强隔离的项目应使用容器或独立检出，未提供之前不准入本试点。

## 7. 集成和证据如何闭环

先检查每个结果，再按计划顺序集成。检查必须覆盖相对 B 的完整提交范围、改名和删除、未跟踪文件与非预期未提交变更，而不是只看最后一个 commit。最终 diff 只能证明最终内容范围，不能证明 worker 从未做过被撤销的越界写入或外部副作用。

代码在一次性集成工作树里组合；出现冲突保留现场和来源提交，不修改主线来试错。主 Agent 可以处理方案范围内的小型集成调整，但必须记录新增 diff 并重新验证；涉及契约或范围变化则返回 P3，不自行扩大任务。

组合验证通过后，先确认主线源码仍对应预期基线，且没有他人新增的源码、暂存或未跟踪改动。只有可无损衔接时才把已验证的代码接回主工作区，保留主线权威 `.ai/`。主线已变化则重建集成，不使用强制 reset 或覆盖工作区。Git 操作方式由实际分支形态决定，验收要求是代码树一致、无来源不明的附带变更。

正式 P5 在主工作区的最终集成代码上运行既有 evidence 工具。worker 的日志只作反馈，不复制为正式通过证据。

为补足 evidence v1 没有提交绑定的缺口，integration 回执至少记录：

- 输入 packet 摘要和每个槽的提交 W；
- 实际集成提交 I、受验证代码与测试的摘要；
- 正式 evidence ID 与 record 文件摘要；
- 验证前后的代码一致性检查结果。

代码一致性检查包含追踪文件的改动、相关未跟踪文件以及构建或测试会实际读取的本地输入。只有明确列入清单的状态写入与生成输出可以排除；不得把全部 ignored 文件一概忽略。环境配置只记录安全标识或版本，不把密钥复制进回执。

收口前通过既有 evidence 命令捕获一次 `check-integration` 结果，关联本批所服务的 AC，并写入 VERIFY 的既有 Gate Coverage。这条检查核对前面的证据，不把自己作为输入，避免循环引用；任何源码、测试或依赖输入随后变化都使该次关联失效，需补跑相关验证。既有 Goal/P5 规则继续负责最终完成资格。

迭代收口时，把本迭代的 parallel-work 记录整包移到迭代归档，与证据归档共同核对。记录内使用迭代相对身份，避免移动后失效；不长期保留两份活副本。只有提交、回执和必要失败现场已安全保留，才清理本次创建的工作树；不删除用户既有工作树或未交还改动。

## 8. 失败时怎么继续

| 情况 | 首版处理 |
|---|---|
| 一个 worker 失败 | 保留另一槽的结果，仅为失败槽新增 attempt；基线和方案未变时才允许复用 |
| worker 失联或主会话重启 | inspect 读取 packet、结果与实际工作树；有可靠宿主句柄才查询运行状态，不能因没有新日志就重复启动 |
| 不能确认旧 worker 是否还在写 | 先停旧 worker 并确认，或改用新的独立工作树；不让两个 attempt 共写原目录 |
| 结果涉及额外文件 | 检查失败，交还原槽处理；不能静默过滤后假称原结果通过 |
| 接口、AC、路径或验证策略改变 | 回到 P3；首版整批失效并重新派发，不做复杂的局部有效性推理 |
| 主线基线变化 | 旧结果保留参考，重新集成和验证；必要时开新批次 |
| 只有文本冲突 | 在集成工作树解决并记附加改动；仍须验证行为 |
| 测试组合后失败 | 暂不接入主线，定位归属、修复并重新集成 |
| 无独立工作目录或资源隔离条件 | 串行执行，明确记录实际执行方式 |

任务消息只传问题、状态和稳定指针，不能替代持久回执。首版不依赖成员之间频繁讨论；遇到契约冲突交回主 Agent，涉及用户取舍的再说明影响请用户裁决。

## 9. 旁路工作继续沿用现成协议

主 Agent 事先派发的执行槽与用户独立发起的旁路工作保持区分。

- 执行槽属于已准入的当前方案，走上面的 packet 和 result。
- 旁路工作继续写 `.ai/sidework/` 的短回执，由用户明确给主 Agent 接回。
- 宿主消息可减少人工转述，但消息与自动扫描都不构成扩大范围或合并代码的授权。
- 旁路成果若影响当前目标或方案，按既有生命周期处理；不新增模型“接受 / 拒绝贡献”的审批状态。

这一部分无需重建目录、模板或状态机。本轮只需在新并行规则里引用已存在的旁路协议。

## 10. 实施切成三步

下面是建议的交付切片，不预占迭代号。真正开工仍从 P1 开始，验收标准和 TECH_PLAN 经过正常准入。

| 切片 | 交付内容 | 完成条件 |
|---|---|---|
| A：合同与检查 | 槽定义解析、prepare/check-result/inspect、不可变记录、路径检查、冻结镜像与恢复规则 | 临时部署项目内，两个槽能从同基线启动；越界、陈旧、重复身份和缺失输入会被明确拒绝 |
| B：集成与证据 | 集成工作树流程、check-integration、证据关联、主线回接和归档；接入一种实测可用宿主 | 实际两个 worker 同时工作，组合验证与 P5 完整闭环，失败不污染主线 |
| C：真实试点与扩展判断 | 一个真实任务的观察报告，再按需要验证另一宿主和中断恢复 | 可说明节省时间、协调与返工成本，决定保留两个槽、调整或退回串行 |

A 与 B 形成最小可用闭环；A 单独完成不能宣称已具备并行交付。首个宿主选真实可操作和可观测的环境，不承诺 Claude Code、Codex、Pi、Grok 在同一批获得等同能力。

预期变更点：

- `tools/parallel-work/`：新增小型确定性工具、schema 和必要测试。
- `Coder/62_Extension_Agents/`：新增 P4 worker 中立定义，更新名册和入口注册。
- `Coder/20_Workflow_Lifecycle/tech-plan-schema.md`：执行槽语义与现行结构对齐。
- `tools/artifact-pipeline/`：对可选槽块做结构校验；保留现有四个 H2 和无槽路径。
- `Coder/40_Context_Management/context-persistence.md`、相关收口规则：只补主线指针恢复、冻结镜像边界和记录归档，不增加全量扫描。
- 宿主兼容说明与验证入口：记录实测能力、串行降级和新工具回归。

首版不把槽身份硬塞进所有宿主 hook，也不升级 evidence schema；这些只在实际观察证明有必要后另议。规则卡是否需要新增一句路由指针，由 P3 根据常驻上下文代价决定，不复制详细协议进所有入口。

## 11. 候选验收与收益判断

以下是供 P2 使用的候选检查点，尚未冻结为 AC。

| 检查场景 | 应观察到什么 |
|---|---|
| 无并行配置的旧项目 | 原串行行为与产物结构保持兼容 |
| 两个互不依赖的工作包 | 运行时间确有重叠，两个结果都能追溯到各自输入和提交 |
| 删除、改名、符号链接或未跟踪文件越界 | 结果检查失败，不能进入正式集成 |
| worker 修改冻结输入或混入 `.ai/` 提交 | 摘要或范围检查失败 |
| 输入缺失、非 pass 方案或无合法当前迭代 | prepare 不派发可执行任务包 |
| 一个失败、一个成功 | 成功成果保留，失败槽可独立重新尝试 |
| 主会话中断、迟到结果、重复回执 | 恢复不重复派发，不覆盖记录，旧批次不误入当前结果 |
| 组合后才暴露的行为冲突 | 集成检查能够失败，主线仍未受污染 |
| P5 后再次改源码或测试 | 原集成证据关联失效，不沿用旧通过状态 |
| 宿主缺少并行能力 | 明确报告 serial，不算并行试点成功 |

试点优先挑两个边界清楚、各自含实现与测试的小功能。为了覆盖部署后的门禁，再补一个临时项目测试场景；只在 Butler 自身运行不能证明目标项目门禁有效。

收益记录分清实测与估计：实测总墙钟时间、工作重叠时长、准备与集成耗时、冲突返工时间、人工介入次数、宿主能提供的 token/费用。缺失成本数据写未知，不估成零。

串行对照优先来自相近任务的真实记录；只有事前估算时明确标注估算，不把两个 worker 时长相加当成已证明的串行基线。保留方案的条件是：验收可信度不下降、总交付时间确有改善、协调与返工成本可接受。一例成功只证明此场景可行，不证明普遍倍速；扩大到更多槽或多活迭代需后续重复观察。

## 12. 为什么选择这条路线

| 外部参考 | 借鉴点 | 本方案的取舍 |
|---|---|---|
| [Claude Code Subagents](https://code.claude.com/docs/en/sub-agents) | 聚焦任务、独立上下文、返回结果 | 默认采用主 Agent 分派，不要求成员全互联 |
| [Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams) | 共享任务与成员通信；仍为实验功能 | 暂不依赖团队运行时，避免把宿主能力当成 Butler 固有能力 |
| [Cursor Worktrees](https://cursor.com/docs/configuration/worktrees) | 任务独立检出、完成后审阅差异 | 工作树交给宿主或 Git，Butler 定义使用合同 |
| [Vibe Kanban](https://www.vibekanban.com/docs/getting-started) | 把规划、执行工作区与代码审阅串起来 | 借鉴交接方式，不为两个槽另造看板产品 |
| [Cursor 多 Agent 研究](https://cursor.com/blog/scaling-agents) | 明确规划与执行责任，避免共享协调文件争用 | 状态单写，worker 不争写全局任务表 |
| [Cursor 后续实验](https://cursor.com/blog/self-driving-codebases) | 集中集成者可能成为瓶颈，吞吐量与中间正确性存在取舍 | 机械检查交给工具，保留交付门禁，不照搬允许持续错误的实验策略 |
| [GitHub Merge Queue](https://github.blog/news-insights/product-news/github-merge-queue-is-generally-available/) | 测试最新基线与前序改动组成的实际组合 | 本地临时集成与最终重跑即可起步，不依赖未配置的远端队列 |

外部资料沿用本次讨论中已核查的官方文档与工程报告，查阅日期为 2026-10-28；这里不声称已安装或实测这些产品。当前建议是先完成 A+B 的两个槽闭环，再依据 C 的真实结果决定扩展。多活迭代、通用调度平台、自动贡献审批和全面宿主适配均不列入首版。
