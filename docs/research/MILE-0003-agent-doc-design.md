## 0. 一句话

把 butler 派出去干活的几个「帮手 AI」（复核 / 更新说明 / 查过时）立成一份**名册 + 通用规矩**，随 MILE-0003 一起做。

## 1. 起因

MILE-0003 要把项目说明从「薄索引」升级成「随迭代补全的知识文件夹」。讨论中发现一个坑：**更新说明这活如果由刚干完活、快没精力的主线 AI 顺手做，质量差、说明会过时。**

→ 改法：**另起一个干净的帮手 AI 专做更新**。由此发现 butler 的帮手一直是散的——现在真正的帮手只有「复核」一个，可它的说明摊在 5 个文件里各写一遍（logic-protocol / review-engine / verify-schema / local-constraints / dangerous）。该立个名册。

## 2. 定位

- Agent 文档 = butler 派出去的帮手的**名册 + 通用规矩**。
- 它是 butler **自己的机器说明**（butler 到哪个项目都用这几个帮手），**不是**某个项目的知识——所以放 butler 规则里，不塞进某项目的 `.ai/project/`。
- 归属：随 MILE-0003 做（正好 MILE-0003 把帮手从 1 个变 3 个，是立名册最顺的时机）。

## 3. 形式：一个文件夹

套用 MILE-0003 知识文件夹同款「总述 + 分文件 + 登记」：

```
Coder/62_Extension_Agents/     # 拟落点：顶层扩展簇，挨着 60_review
  overview.md            # 总述：帮手是啥 + 通用规矩(唯一真源) + 名册表 + 读法
  independent-review.md  # 复核 · 完整定义
  knowledge-fold.md      # 更新说明 · 完整定义
  drift-check.md         # 查过时 · 完整定义
```

- **落点拟定 `62_Extension_Agents/`**（顶层扩展簇，与 60_review 相邻）。**不放 `00_System_Prompt/`**——那层是「会话级协作身份」，名册是「能派哪些帮手」的能力目录，性质不同，塞进去会破坏分层。开题时最终确认。
- **夹内文件不带数字前缀**（`overview.md` 而非 `00_overview.md`）：`Coder/` 目录的惯例是夹内文件零前缀、顺序交 README 排；数字前缀是 `.ai/` 运行态的习惯，域不同。
- **总述改触发式加载，不进冷启动必读**（与全体扩展模块一致）；主线要「知道有哪些帮手可用」，用一行很轻的指针即可，不占冷启动预算。每个帮手的明细**按需读**（真要派它时才读）。

## 4. 名册（三个帮手，本轮一起立）

| 帮手 | 干嘛的 | 啥时候被叫起来 | 给它啥 → 它还你啥 | 只准碰（权限约定） |
|---|---|---|---|---|
| **复核** | 拿验收标准挨条核对写得对不对，挑出错就拦住收工 | 交付验证阶段（手动 `/review`，或项目设了自动） | 给：验收清单＋技术方案＋这次改动＋作者自评 → 还：每条「过／不过／没法判」＋挑错清单 | **只看**（读＋搜），不改代码 |
| **更新说明** | 把这次的改动折进项目说明文件夹 | 每次收工、且这次动了结构（加/删了东西） | 给：这次改了啥（改动清单） → 还：更新后的说明文件 | **只改说明文件夹**（`.ai/project/`），别的不碰 |
| **查过时** | 对着真实代码查说明有没有过时，过时就报出来 | 冷启动 / 收工时抽查 | 给：项目说明＋真实代码 → 还：哪几处对不上了 | **只看**，不改 |

**三条所有帮手都一样的规矩**（放总述，写一次）：

| 共同规矩 | 说白了 |
|---|---|
| 都是**另开的干净 AI** | 不带主线那边的思路——不然就是自己给自己打分、自己糊弄自己 |
| **叫不起来时如实说** | 起不了子 agent 就写「这步没做、当风险摆出来」，**绝不假装做过** |
| **就是一份定义资料** | 每个帮手 = 一份大白话中立定义（角色/输入/输出/禁止/权限）。butler 用时读它、临时起干净子 agent 执行，**不往项目发文件**（见 §7） |

## 5. 通用规矩（总述里，唯一真源）

- **G1**：检查类帮手必须干净上下文，不带作者思路。
- **G2**：叫不起来时如实标「没做」、当风险摆出来，**绝不假装做过**。
  - **事实校准**：这条兜底的正文现在**只在 `review-engine §6.4` 一处**；`dangerous §7.3`、`verify-schema §4` 是**引用它**（不是各写一遍）。收到总述后，`review §6.4` 正文上提总述、就地改回指，`dangerous §7.3` + `verify-schema §4` 的引用目标从 `review §6.4` 改指总述；改完全仓 grep 确认没有还指着 `review-engine §6.4` 的漏网引用。
- **G3**：谁能改产物、谁只能读（复核只读；更新说明只准写 `.ai/project/`）。这是**契约约定**；要不要在工具层硬拦见 §7「牙齿」。
- **G4**：帮手就是一份中立定义资料，用时读、临时起子 agent（见 §7）。

## 6. 复核帮手：三拆

把现在 `60_review` 里的东西按性质拆开：

| 现在在 60_review | 是什么 | 去哪 |
|---|---|---|
| §1 通用审计视角、§3 流程（识别/口径/多维/评级）、§4 闭环、§5 简评 | `/review` 特性 + 共享标准 | **留 60_review** |
| §1「独立性=上下文隔离」那段、§6.4 诚实兜底 | 所有帮手**通用规矩**（G1/G2） | **→ 总述 §5**（唯一真源，review + dangerous + verify-schema 回指） |
| §2 两个独立复核触发、§3.3 断言核对、§6.1 隔离形态、§6.2 Checker 契约、§6.3 输出衔接 | **复核帮手自己的** | **→ independent-review.md** |

核心判断：**共享的审查流程留 60_review，复核帮手文件回指它**——因为复核本质是「把那套流程放进隔离上下文跑」，流程不归它私有。三拆要写成**带地址的搬家清单**（哪段搬哪去、原地留指针），别只口头说「互相引用」——butler 没有机器手段能发现两处内容写岔了。

## 7. 帮手怎么落地：一份定义资料，用时读

**帮手 = 一份大白话中立定义**：角色 / 输入 / 输出 / 禁止 / 隔离要求 / 权限。跨模型跨宿主通用，哪天不用 Claude Code 也有用。

**怎么用**：butler 要派某帮手时，**读它的定义、临时起一个干净子 agent** 去执行——**跟现有 `/review` 一模一样**（`review-engine §6.1`：主动起 fresh-context 子 agent，如 Claude Code 的 Agent / Task 能力）。**不把帮手文件下发到每个项目、不搞「壳随部署带进项目」那一层。**

**为什么非子 agent 不可、不用更通用的 Skill**：Skill 在**同一个对话里**跑，给不了「干净新脑子」；复核 / 查过时图的就是隔离。（事实核对准确：Skill 的指令载入当前对话并在其中运行；子 agent 另起一个隔离的新上下文、看不到当前对话历史。）

**牙齿（工具层硬拦）——可选、留后续**：

- 想让权限从「嘴上约定」变「工具层拦死」，靠的是起子 agent 时限定它能用哪些工具。**复核**「只给 Read/Grep/Glob、不给 Edit/Write」——工具名白名单能办到，牙是硬的。
- **更新说明**「只准写 `.ai/project/` 这个目录」——工具白名单只到「给不给 Write」的粒度，**管不到目录**；目录锁定还得叠一层 `settings.json` 的 `permissions` 路径规则（先全禁、再放开那个目录，路径带根锚点 `Write(/.ai/project/**)`）。这属于「真想要硬牙齿时」的实现细节。
- **本轮不追这颗牙**：权限靠 §4/§5 的契约约定 + G2 诚实兜底兜着（同现状 `/review`）。硬牙齿是可选增强，等确有需要再单独做，不背「下发文件到每个项目」的复杂度。butler 仓自己（dogfood）可在自身 `.claude/agents/` 放一份供自己用，那是 butler 内部的事，不是每个部署项目都要。

**生态事实校准**（放定义里对外说明时按此措辞）：

- 没有哪家的「子 agent 定义格式」是全行业统一遵守的。`.claude/agents/` 是 **Claude Code 独有**，别家（Cursor / Copilot / Codex）不读。
- Anthropic 真正跨家的是 **MCP**（给 AI 配工具）和 **Agent Skills**（`SKILL.md` 技能包，截至 2026 上半年 30+ 家工具采纳）；**AGENTS.md** 是 **Sourcegraph 的 Amp 团队发起**（当时是单数 `AGENT.md`）、后经 OpenAI Codex 推广成复数带火的**仓库级说明**规范。**都不是「帮手定义」**。

## 8. 维护

agents 文件夹吃 MILE-0003 自己的规矩：加/删/改帮手 → **改帮手的同一次编辑里，顺手一起改总述 + 对应文件**（co-edit）。因为名册说的是 butler 自己的帮手、不随某个项目的代码漂移，同一次编辑就能保持一致；冷启动一致性自检当兜底（加一条：名册每个帮手 ↔ 有对应定义文件 ↔ 权限声明一致）。它其实是知识文件夹模式的一次**内部预演**——先在这 3 个帮手上把「总述+分文件+登记」跑顺，MILE-0003 的大文件夹照抄这结构。
