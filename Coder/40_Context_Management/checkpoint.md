# Checkpoint

## 1. 目标

检查点不是记录所有过程，而是把当前阶段已经沉淀下来的最终结论固化下来，供后续继续执行、验证或交接。

它的作用是：

- 抵抗长对话中的上下文噪音
- 支持 clean-slate handoff
- 让后续执行者直接继承高密度结论，而不是重复阅读历史过程

## 2. 触发时机

以下场景应形成 checkpoint：

- 一个 AC 被勾选后
- 一个子任务完成后
- 一个阶段（Analysis / Acceptance / Design / Verify）结束后
- 准备压缩上下文前
- 准备切换会话、执行者或模式前

## 3. Checkpoint 最小结构

一个有效的 checkpoint 应至少包含：

- 当前已完成项
- 关键设计决策
- 已修改文件
- 尚未完成项
- 剩余风险或待确认问题
- 下一步入口

## 4. Clean-Slate Handoff 规则

当任务链路已经过长，或历史讨论开始干扰当前判断时，应优先进行 clean-slate handoff：

- 先输出 checkpoint
- 再以 checkpoint 作为新上下文入口继续工作
- 新入口优先读取最终结论，而不是旧日志

handoff 的目标不是“保留全部历史”，而是“保留继续推进所必需的最小共识包”。

## 5. 输出约束

- 只保留最终有效结论，不保留失败尝试。
- 不复制大段终端日志。
- 不把临时猜测写成既定事实。
- 文件列表、接口边界、风险与下一步必须明确。

## 6. 与状态文件的区别

- 状态文件回答“现在进行到哪里”。
- checkpoint 回答“这一阶段最终确认了什么”。

状态文件偏运行时，checkpoint 偏阶段交付物。
