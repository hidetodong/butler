# prd-split（PRD 切分机制）

本文件是**产生动作层**：定义"拿到一份大 PRD，怎么把它切成 `.ai/references/prd/` 知识文件夹"的具体程序。它**履行** `references-schema.md` 定下的契约、是该文件 §8 前向指针里标给 **R2** 的那个动作。

## 1. 定位：契约 vs 动作

`references-schema.md` 是**契约**（声明式）——规定 `prd/` 长什么样、切片必须逐字原文、slug 是终身身份、怎么落盘。本文件是**动作**（程序式）——规定怎么一步步把 PRD 变成那个样子。

分工一句话：**契约说"结果该长什么样"，本文件说"怎么动手做出来"。** 因此本文件对以下几点一律**回指 references-schema、不复述不改写**（契约改了，动作不必两头同步）：

| 本机制用到的规矩 | 真源 |
|---|---|
| `prd/` 结构 + `00_INDEX` + 登记表字段 | `references-schema §3` |
| slug（模块的终身英文代号，如 `save-validation`）身份（一次分配、只增不改） | `references-schema §4` |
| 切片必须逐字原文、无损（命门红线） | `references-schema §6` |
| live / `.archive/vN/` 落盘形态 | `references-schema §7` |
| 什么资料才走 `prd/` 知识文件夹态（判据） | `references-schema §2` |

**本文件只管"首切"**（一份 PRD 第一次进来怎么切）。它改版后再切一次（重新派生 + 冻旧版）属 R5、给验收标准钉版本属 R4、模块跨版本认亲属 R6——都不在此。

## 2. 边界识别：怎么切

**按 PRD 自身的结构切，不自造边界。** PRD 天然就有切线——章节、功能模块、"修改项"分组，每一个这样的自然单元就是一个模块。切分原则：

- **一个模块 = 一片 = 一个 slug**：一个自然单元切成一份 `prd/<slug>.md`。
- **顺着 PRD 的骨架走**：PRD 分几章讲几个功能，就大体切几片；PRD 按"V1.1 修改项 1 / 2 / 3"组织，就按修改项切。不把 PRD 没分开的东西强行拆开，也不把 PRD 分开讲的东西硬揉成一片。

**红线：绝不把一条完整的规则 / 校验 / 文案拦腰切碎跨两片。** 比如 PRD 里"信号机 ID 与所属路口不得重复，重复时提示'……'"是一条完整校验，它必须整条落在同一片里，绝不能上半句在 `save-validation.md`、下半句在别处。**判断两难时宁可切得粗**（一片多含一个相邻模块），**也不可切碎**——切碎会让某片验收时找不到完整规则、另一片拿到半条无意义的规则。粗了顶多多读几行，碎了直接废掉切片的权威性。

## 3. slug 首切分配 + 写 00_INDEX / 登记表

切分方案确认后（见 §6），落盘两件事：

1. **给每个模块分一个语义化终身 slug**——英文短横线命名、见名知意（如登录校验 → `login-validation`、信号机保存 → `signal-save`）。slug 是这个模块的**终身身份证号**：一次分配，此后 PRD 怎么改版、章节怎么重编号都不动它（规则守 `references-schema §4`）。
2. **写 `00_INDEX.md`**（守 `references-schema §3` 的字段与结构）：
   - **入口叙述**：一段话讲清这份 PRD 是什么产品/版本 + 模块地图（想找 X 看哪个 slug）。
   - **模块登记表**：每模块一行——slug / 当前标题·章节 / **首见版本 = 当前这份 PRD 的版本号**（如 `v1.0`）/ 当前版本（首切时=首见版本）/ 状态 `active`。

每片 `prd/<slug>.md` 的正文＝该模块的原文（见 §4）。

> **由 `/milestone` 触发首切时**（brief 就是这份大 PRD，见 `20_Workflow_Lifecycle/milestone-schema.md §6.4` 步 6）：`00_INDEX` 入口叙述额外记一句 **所属里程碑号**（这份 PRD 归哪个里程碑）——"本 PRD 服务 `MILE-NNNN`，模块 ↔ 路线项映射见其 §5.3"。这是"references 细节 → 里程碑方向"的回指指针。**只回指、不重列映射**：模块对应哪个路线项，真源单一在里程碑路线图（§5.3 的「相关 slug」标注），此处重列必将来漂移。手动注入（非里程碑触发）的 PRD 无 owning 里程碑，此句省略。

## 4. 逐字保真

**每一片 `prd/<slug>.md` 是对应模块原文的无损投影——照搬，不概括。** 这是 `references-schema §6` 立的命门红线，切分是第一个真踩上它的动作：

- PRD 里的精确文案（提示语原话）、精确校验规则、精确字段约束，**一个字都不能改、不能删、不能"顺手总结成一句"**。少一个字，将来验收就对不上真源。
- 可以做的只有**搬运边界内的取舍**：把属于这个模块的原文整段搬进来。不可以做的是**压缩内容**——绝不能套用 `.ai/project/` 那种"当前真相覆写、有损摘要"的写法（那是项目自身全貌的玩法，不是外部权威规格的玩法）。
- 唯一允许摘要的地方是 `00_INDEX` 的入口叙述（它是找路的地图、不是规格本身）；切片正文永远逐字。

## 5. 小 PRD 单模块退化态

PRD 很小（就一个功能、几段话）时，**不另开特例、也不退回扁平态**（不写成 `<name>.md` 单文件）——走**同一套模型**，只是模块数 = 1：一个 `00_INDEX.md`（入口叙述 + 一行登记表）+ 一片 `prd/<slug>.md`。

这样做的理由：小 PRD 将来一样会改版、一样要钉版本、一样要审计，走统一模型才能无缝享受 R4/R5 的钉版与改版同步；若图省事写成扁平单文件，改版时就得特殊照顾。判据（什么算该走 `prd/` 知识文件夹态）守 `references-schema §2`——是"逐字权威规格"就走 `prd/`，哪怕它小。

## 6. soft 对齐：提议 → 确认 → 落盘

**切分不是全自动黑箱，是"先提议、经你确认、再落盘"三拍。**（"soft 对齐"＝不硬切，把边界决策权交回用户确认。）

1. **提议**：AI 先给出切分方案——模块清单、每个模块拟用的 slug、每片的边界依据（这一片对应 PRD 的哪几节/哪个修改项），一次性摆给用户看。**此时不写盘。**
2. **确认 / 调整**：用户看方案，可以确认、可以调边界（"这两个应该合成一片""这条规则被你切到两片了，并回去"）、可以改 slug 命名。
3. **落盘**：确认后才按 §3/§4 真正写 `00_INDEX` + 各片。

**为什么要这道闸**：切分最大的风险是 AI 自作主张——把一条规则从中间截断、或把两个无关模块并成一片、或 slug 起得词不达意。提议→确认把这些不可逆的边界决策在写盘前交给最懂这份 PRD 的人过目一遍。这与 `[split]` 迁移的"问一句再迁"、`[add-field]` 补字段的"草稿值先给你确认"是**同一套信任模型**——凡是"猜错了代价大、又难回退"的动作，一律先提议后落地，绝不静默硬来。

> **硬约束**：未经用户确认切分方案，**不得**直接把 PRD 写成 `prd/` 切片。宁可停下来问，也不擅自切。
