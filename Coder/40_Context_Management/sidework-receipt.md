# 旁路工作回执协议

## 1. 定位

旁路工作是用户主动发起、脱离当前主 Agent 上下文完成的一段工作。它可能同时产生代码改动、调研、方案、实验结论和验证证据。

回执只解决一件事：让旁路执行者把**最终有效结论、成果位置和续接入口**落成一份短文件，用户再用文件路径把它钩回主 Agent。它不是成果审批流程；模型不建立“接受 / 拒绝”状态，也不替用户决定项目方向。

回执协议也不是代码写入授权或流程绕过。旁路工作的实际读写仍受用户指令、宿主文件权限、当前 Butler 阶段门禁和项目范围约束；这些边界不允许写时，不能因为“之后会写回执”就继续修改。

这项能力按结果交接建模，不绑定某种 Agent。另一个会话、人工操作或外部工具完成的工作，只要能按同一结构落档，也可以使用本协议。

## 2. 与现有载体的边界

| 载体 | 负责什么 | 为什么不承载旁路回执 |
|---|---|---|
| `.ai/02_SESSION_HANDOFF.md` | 当前主线跨会话恢复入口 | 它由权威主线状态派生，不能混入另一条执行线的结果 |
| `.ai/task-state.md` | 当前活跃迭代的运行状态 | 旁路执行者不是主线状态的共同写者 |
| `.ai/references/` | 项目外部权威资料的受控投影 | 旁路回执记录项目内部执行事实；其中的长调研报告可以另存 references，再由回执指向 |
| `deliveries/` | 已完成迭代或里程碑的人类交付 | 旁路工作不自动成为已验收、已收口的迭代交付 |

旁路执行者不得修改当前主线的 `.ai/CONCEPT.md`、`.ai/AC_LIST.md`、`.ai/TECH_PLAN.md`、`.ai/VERIFY_REPORT.md`、`.ai/task-state.md`、ITER/MILE 台账或 `.ai/02_SESSION_HANDOFF.md`。若旁路任务本身就是一个正式 Butler 迭代，则走正常 P1–P5，不使用本协议冒充迭代产物。

允许新建 `.ai/sidework/<receipt>.md` 不等于允许修改任意源码。旁路代码若不在当前活跃迭代的冻结范围内，不得借当前四件套获得名义上的放行，也不得设置 `BUTLER_BYPASS`；应停在研究/补丁建议，或使用用户与宿主已经明确授权、能与主线隔离的分支 / 工作树。回钩后由主 Agent 按正常生命周期决定代码如何进入项目。

## 3. 触发与角色

满足以下条件时使用本协议：

- 用户明确把一项工作交给旁路 Agent、另一个会话、人工或外部工具；
- 该工作完成后需要回到另一个主 Agent 继续推进；
- 仅靠代码 diff 或一段聊天不足以恢复“为什么做、结果在哪里、验证如何、从哪里继续”。

角色边界：

- **用户**：发起旁路工作，持有是否改变主线方向的决定权，并把回执路径交给主 Agent。
- **旁路执行者**：完成工作、写回执、返回路径；只陈述成果与影响，不替用户批准方向。
- **主 Agent**：只在用户给出回执路径后定向读取，核对当前主线并说明可直接使用的事实、冲突和需要用户决定的问题。

## 4. 路径与命名

写入前必须先按 `20_Workflow_Lifecycle/mcv-deployment.md §0.1` 解析唯一 `PROJECT_ROOT`。回执按需落在：

```text
$PROJECT_ROOT/.ai/sidework/<YYYY-MM-DD>-<slug>.md
```

- `.ai/sidework/` 第一次使用时才创建，不是基地车部署种子，也没有 `00_INDEX.md`。
- `<slug>` 使用小写 ASCII 字母、数字和单个短横线表达任务语义，不用 Agent 名、随机串或“misc”冒充主题。
- 写前必须检查目标文件。若同名已存在，依次尝试 `-2`、`-3`；必须使用宿主的 create-only（只创建）写入语义，**只新建，绝不覆盖**既有回执。并发创建返回“已存在”时重新读取目录、选择下一个短序号，不得退成更新旧文件。
- 解析后的目录和目标文件必须留在唯一 `PROJECT_ROOT/.ai/sidework/` 内。目录或既有目标是符号链接、路径逃出项目根、项目根不唯一时，停止写入并回报。

一个旁路任务写一份回执。多个执行者共同完成同一个用户目标时可以共写一份最终回执，但必须由一个明确的收口执行者负责，避免并发争写。

## 5. 固定结构

canonical 骨架是仓库根 `templates/sidework-receipt.md`。回执的 H2 顺序固定为：

1. `用户发起的目标`
2. `成果结论`
3. `成果与改动位置`
4. `验证事实`
5. `对主线的影响`
6. `主 Agent 续接入口`

`成果与改动位置` 使用固定表头：

| 类型 | 路径 / 提交 / 补丁 | 说明 |
|---|---|---|

书写规则：

- 只写最终仍成立的结论，不写冗长思考过程、失败尝试或完整终端日志。
- 代码、长报告和 evidence 留在各自真源；回执写项目内相对路径、提交、补丁或其他稳定指针，不复制正文。
- 同一份回执可以混装 `code`、`research`、`design`、`experiment`、`evidence` 等类型，不按类型拆流程。
- 有代码成果时必须写工作基线、实际改动文件和承载方式。独立提交、补丁或工作树可以作为较强指针；直接写共享工作区时必须明确写“共享工作区”，不能冒称作者归属或独立提交。
- `验证事实` 区分已执行的命令与结果、仅由生产者报告的结论、尚未验证的部分；没有机器证据时不得写成已复现。
- `对主线的影响` 陈述可复用事实、潜在冲突和需要用户决定的问题，不写模型的“接受 / 拒绝”结论。
- `主 Agent 续接入口` 必须让另一个 Agent 不读原会话也知道先读什么、先核什么、下一步从哪里开始。

## 6. 旁路执行者的交还流程

1. 在用户指令、宿主权限和当前 Butler 范围允许的边界内完成实际工作；回执本身不提供额外写权限。整理当前仍成立的结论和成果指针。
2. 解析唯一项目根，检查 `.ai/sidework/` 与候选文件路径，按 §4 选择一个未占用的新文件名。
3. 从 `$BUTLER_PATH/templates/sidework-receipt.md` 取 canonical 骨架，填写六个固定章节；不保留占位符。
4. 自查成果 locator 可读、代码基线与实际文件写清、验证强度没有夸大、主线决策没有被模型代做。
5. 向用户返回项目内相对路径，并用一句话概括成果；不自行写入主线状态文件。

## 7. 主 Agent 的续接流程

1. 只有用户显式给出回执路径或明确要求接回某份旁路工作时才启动；不在冷启动或每轮对话自动扫描 `.ai/sidework/`。
2. 解析唯一项目根，确认回执是项目根内的普通文件且路径没有经符号链接逃逸，再读取回执。
3. 按需读取回执指向的代码、报告和证据，不把回执中的生产者声明直接升级成已复现事实。
4. 对照当前 `.ai/task-state.md` 和活跃阶段产物，向用户报告：可直接使用的事实、与主线的冲突、缺失或漂移的指针、需要用户决定的问题。
5. 无实质冲突且用户指令已经覆盖后续动作时，按正常 Butler 生命周期继续；出现方向冲突、范围扩张或关键取舍时，亮出影响并等用户决定。

读取回执不等于把成果自动并入当前迭代。若成果改变目标、AC 或方案，仍按 `20_Workflow_Lifecycle/lifecycle.md §5` 回到相应阶段；若只是代码实现，也必须经过当前迭代自己的范围检查与验证。

## 8. 失败与可信度

- 回执缺关键章节、locator 不存在、基线已漂移：主 Agent 只消费仍可核实的事实，明确列出缺口，不猜测补全。
- 多个 Agent 直接写同一个脏工作区：回执只能记录其声明和当前路径，无法事后证明逐行作者归属。主 Agent 必须按共享工作区低归属强度处理并重新验证。
- 旁路代码越过当前迭代或宿主写入边界：立即停止；不得用回执、共享工作区或 `BUTLER_BYPASS` 把越界改动包装成合法成果。
- 回执与当前主线互相矛盾：矛盾本身是结果，不是审批状态。模型把两边事实和后果摆给用户，不通过“拒绝贡献”隐藏它。
- 用户暂时不想处理：保留回执原样即可。第一版不维护未读、已读、延后或完成状态。

## 9. 最小用法

发起旁路工作时可以直接说：

> 这是一项旁路工作。完成后按 Butler 的 `sidework-receipt.md` 写回执，不要修改主线状态文件，把回执路径给我。

回到主 Agent 时可以直接说：

> 接回这份旁路工作：`.ai/sidework/2026-07-29-cache-investigation.md`。先对照当前主线说明成果、冲突和需要我决定的地方，再继续。
