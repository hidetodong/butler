# project-digest-schema（.ai/project/ 知识文件夹格式契约）

本文件是 `.ai/project/` 知识文件夹的唯一结构契约。何时把改动折叠进来由 `20_Workflow_Lifecycle/iteration-schema.md §5.5` / `20_Workflow_Lifecycle/milestone-schema.md §7.4` 的收口步负责（折叠**已由 MILE-0003 R3 接线为强制**，见 §6/§9）；冷启动如何读由 `context-persistence.md §6` 负责（第一读**已由 MILE-0003 R5 接线为两态**：采用 `.ai/project/` 的项目先读 `00_INDEX` + 按需主题、仍单文件的项目读 `.ai/PROJECT.md`，见 §9）。

> 文件名沿用旧名 `project-digest-schema.md`（"digest" 是它单文件时代的叫法）；内容本轮已从"单文件薄摘要"升级为"知识文件夹"。不改名是为了不让全仓 5+ 处引用它的地方失效（最小改动定位，见 `30_Quality_Gate/implementation-discipline.md`）。

## 1. 定位

`.ai/project/` 是项目的**常驻知识文件夹**——一组按主题分开的 Markdown 文件，合起来回答"这系统现在整体是什么、有哪些东西、为何如此、有哪些长期约束与欠债"。它是**整体取向**（把所有迭代的改动积分成"现在的全貌"），与变更流取向的 `ITERATIONS.md`、瞬时取向的 `02_SESSION_HANDOFF.md` 互补。

它取代了旧的单文件 `.ai/PROJECT.md`。旧文件是一份 ≤1500 tokens 的**薄索引**（几个关键词 + "细节看代码"），AI 冷启动读完并不真知道"项目里有什么"，容易沦为"报几个关键词假装体系很有用"。知识文件夹要让 AI 读完就**真懂**项目、且**随迭代越补越全**。

冷启动时它是**第一读**：先读 `00_INDEX.md` 拿到全貌与地图，再按需读相关主题文件，然后读 `ITERATIONS.md` 看时间线、读 handoff 看断点，最后按指针钻代码。（"冷启动"=AI 没有任何上下文、从零接手一个项目的时候。）

### 四产物边界（不得越位）

| 产物 | 取向 | 答什么 |
|---|---|---|
| `.ai/project/` | 整体（积分） | 系统现在整体是什么、有什么、为何如此 |
| `.ai/ITERATIONS.md` | 变更流（delta） | 一步步怎么走到今天（迭代时间线） |
| `.ai/02_SESSION_HANDOFF.md` | 瞬时 | 现在卡在哪个断点 |
| `.ai/MILESTONE.md` | 版本范围 | 当前大版本圈了什么、拆成哪些迭代 |

知识文件夹**不得**变成变更流——它记"现在是什么"，不记"改了什么"（那是 `ITERATIONS` / `CHANGELOG` 的活）。

## 2. 核心哲学（先认清这是一次切换）

从"薄索引"到"知识文件夹"是一次**有意的哲学切换**，不是"把一个文件切成几块"。它反转了单文件时代的三条明文价值：`≤1500 tokens`「摘要不是百科」→ 越补越全；「指针化·深内容不内嵌」→ 装消化过的真内容；「多数迭代不动·避免维护膨胀」→ 每次收口按主题折叠。换来的是"真能用"，代价是**更高的维护纪律**。

"完整"与"不膨胀 / 不腐坏"能共存，靠三条**矛盾消解**——理解并守住它们，是这套设计不腐的前提：

1. **完整 = 广度覆盖，不是细节深度**（地图 ≠ 疆域）。知识文件夹是张全项目的地图，每处到深处仍用指针回到真源（代码 / 规则 / `deliveries/`），不把细节搬进来。体积正比于**项目复杂度**，**不**正比于迭代数。
2. **完整 ≠ 变长**。"越补越全"靠**覆盖更多主题 + 把新真相折进旧位置**，不是往文件后面叠历史。当前真相 **overwrite**（覆写）旧结论，被取代的内容**删除、不叠**——**禁历史层**（历史归 `ITERATIONS` / `deliveries`）。
3. **知识地图（要完整）≠ harness 机器（要精简）**，两者正交。这里说的"要完整"只针对这份项目知识地图；它不鼓励代码 / 工具层多写壳——好地图反而帮你看清哪些壳能删。

> **最大风险：陈旧的完整，比诚实的薄更毒。** 薄索引至少不骗人（"细节看代码"）；一个立志完整却没被严格维护的知识库，会变成一份**自信的谎**——AI 信了滞后内容、做出错判。整套设计生死系于"**强制 + 可验证的收口折叠**"（§6 声明模型，强制接线见 §9 的 R3）。它若不硬，这套东西会精确地产出用户最讨厌的"假装有用"，只是更大份。

## 3. 文件夹结构 + 00_INDEX 入口 + 推荐主题集

```txt
.ai/project/
  00_INDEX.md      # 入口：一段话讲清项目是什么 + 文件夹读序/地图 + 主题登记表
  identity.md      # 定位 / 目的 / 使用者 / 边界
  architecture.md  # 模块地图：每个模块 + 它到底管什么 + 关键文件
  capabilities.md  # 当前能做什么：命令 / 引擎 / 触发 / 产物（真清单）
  invariants.md    # 关键长期决策与不变量（含"为什么"）
  constraints.md   # 现行约束（技术 / 流程 / 业务的长期边界）
  debt.md          # 已知长期欠债
  frontier.md      # 当前形态 / 活跃战线 / 下一个瓶颈（变得最快的一层）
```

以上是**推荐核心主题集**，覆盖旧单文件 6 字段（目的 / 架构 / 不变量 / 约束 / 欠债 / 指针）并补上 capabilities 与 frontier 两层。项目按需**受控扩展**（见 §7），非核心主题不强制建。小项目可先只建 `00_INDEX` + 少数几份，随项目长大再拆。

### 00_INDEX.md 契约

`00_INDEX.md` 是文件夹的入口与冷启动第一读，**必须**含三块：

1. **一段话讲清项目是什么**（给谁解决什么问题）。
2. **读序 / 地图**：本文件夹怎么读、哪份管什么。
3. **主题登记表**：每个主题文件一行（文件名 + 一句话职责 + 边界）。新建主题**必须**登记进这张表——这是"注册即真源、无隐式依赖"老不变量在知识文件夹里的落地（同"新规则必须在 `Coder/README.md` 注册"）。

## 4. 每份边界（有界、可整篇读完）

- 每个主题文件**必须有界、能被一次整篇读完**（一屏到几屏，不是长卷）；写满了就**拆成新主题文件**、登记进 `00_INDEX`，不在单份里无限堆。
- 边界靠"广度覆盖 + 指针回真源"守住：一份文件把它这个主题的**当前全貌**说清即可，细节用指针指向真源，不搬进来。
- 体积随**项目复杂度**增长（主题变多、每份写满即拆），**不随迭代数**增长（迭代只把新真相折进已有位置，见 §6）。

## 5. 写作密度：digest-and-point（消化过的真内容 + 指针）

每一项的密度标准是 **digest-and-point**（消化后给全貌、再给指针）：**名 + 它到底干什么 + 真源指针**。三种写法都不合格——① 只写关键词占位（等于旧薄索引的病）；② 逐字复制代码 / 已有真源（等于搬疆域，且会腐）；③ 空泛套话。

**已有真源不逐字抄**：如果某内容已有权威出处（如 `Coder/README.md`、`architecture-overview.md`），知识文件夹**只摘当前全貌 + 补真源里没有的"现状 / 成熟度"层 + 留指针**，不把真源正文搬过来。（这条在 butler 仓自身 dogfood 时最吃劲——butler 的目录与分层说明早已在 README，知识文件夹只摘全貌 + 补"哪些成熟、哪些还欠",见 §9 的 R8。）

密度校准样例（`architecture.md` 该长这样——digest 级、真信息，非关键词）：

```markdown
## SOP Core（00/20/30/40 · 通用主干，所有任务默认走）
- 00 System_Prompt — 协作身份 + 总调度逻辑 + 输出呈现协议（结论先行 / 统一标号 / 表格化）。
- 20 Workflow_Lifecycle — P1→P5 状态机 + 四件套 schema + 迭代 / 里程碑 / 版本 / 迁移 / 交付规则。骨架，最大一层。
- 30 Quality_Gate — linting、测试策略、复核标准、纠错收口契约、最小实现纪律（P4 常驻）。
- 40 Context_Management — 状态外化、冷启动读序、handoff、角色切换。

## 关键真源
- 目录+读序 Coder/README.md ｜ 分层 architecture-overview ｜ 版本 VERSION ｜ 约束 SSOT templates/rule-card.md
```

其余写作口径（讲人话、不啰嗦、分层渐进展开）以 `20_Workflow_Lifecycle/artifact-style.md` 为准（单一来源，不在此重复）。状态取向自检：每写一条先问"这是现在仍成立的整体事实，还是一次变更 / 一个断点？"——后两者分别归 `ITERATIONS` / `handoff`，不写进知识文件夹。

## 6. 折叠维护模型（已接线为收口仪式，见 §9 R3）

知识文件夹靠"**部分喂养整体**"保持既新又不腐：**整体** = `.ai/project/`（当前真相全貌）；**部分** = 每个迭代的 `CHANGELOG`（ADD/EDIT/DELETE 增量）。收口时把本迭代的 delta **按主题路由折进对应主题文件**——不是重写整个文件夹，是**定向折叠**。写代码 = 记"改了什么"，收口 = 把"改了什么"折进"现在是什么"。

- **形态**：overwrite 当前结论（改动落在它该在的主题文件里），不堆历史层。
- **成本可控**：delta 已在 `CHANGELOG` 记好、绑 AC，折叠是**路由**不是重推导——成本正比于**本迭代改动量**，**不**正比于文件夹大小。

> 本 §声明折叠模型（该怎么维护）；其**强制接线已由 MILE-0003 R3 落地**：收口步④已泛化为"文件夹态按主题**必做**折叠 / 单文件暂态按需前滚"（`20_Workflow_Lifecycle/iteration-schema.md §5.5` / `20_Workflow_Lifecycle/milestone-schema.md §7.4`），冷启动一致性自检已加**第 6 条"知识文件夹漂移自检"**（`context-persistence.md §冷启动一致性自检`，条件不变量、单文件项目 N/A）。故采用知识文件夹的项目每次收口**必**折叠 delta 并自检漂移——不再是"要求了却没人强制"。

## 7. 受控扩展登记

项目长出新内容时——**新主题 → 新主题文件 → 登记进 `00_INDEX.md` 主题表**。这个"新增即登记"的动作本身就是"越补越全"的引擎：文件夹通过受控地添主题变完整，而每次添都留在 `00_INDEX` 有据可查、无隐式依赖。**不得**把不相干内容硬塞进已有主题文件撑大它——该拆就拆。

## 8. 模板骨架

**`00_INDEX.md` 骨架**：

````markdown
# <项目名> · 项目知识文件夹

<!-- 一段话：这系统是什么、给谁解决什么问题。 -->

## 读序 / 地图
<!-- 本文件夹怎么读、冷启动先看哪份。 -->

## 主题登记表
| 主题文件 | 管什么 | 边界 |
|---|---|---|
| identity.md | 定位 / 目的 / 使用者 / 边界 | … |
| architecture.md | 模块地图 | … |
<!-- 每个主题文件一行；新建主题必须在此登记。 -->
````

**主题文件骨架**（每份主题文件通用）：

````markdown
# <主题名>

<!-- digest-and-point：每项 = 名 + 它到底干什么 + 真源指针。有界、可整篇读完、满则拆新文件。 -->
````

模板规则：

- `00_INDEX.md` 三块（一段话 / 读序地图 / 主题登记表）不得缺；主题登记表须与实际文件一致。
- 主题文件按 digest-and-point 密度写、有界；某主题本项目暂无内容则不建该文件（非"建空文件写无"）。
- H1 用项目名 / 主题名，不套死措辞。
