# State Tracking

## 1. 目标

长任务质量下降的根因之一，是关键状态只存在于对话上下文里，而没有被外部化。

本规则要求在需要时，将执行状态同步到仓库内的外部载体中，降低上下文压缩、任务切换与多轮协作导致的漂移。

## 2. 适用范围

以下场景必须启用状态同步：

- 长任务或多阶段任务
- 存在多个子任务并行或串行推进
- 准备压缩上下文前
- 准备切换执行者、模式或会话前
- 已经出现目标漂移、接口遗忘、边界模糊等迹象时

极小、低风险、一次性即可完成的任务可不强制维护外部状态。

## 3. 状态载体协议

推荐使用以下任一载体：

- `.ai/task-state.json`
- `SESSION.md`

说明：

- 这里定义的是**协议级载体**，不是仓库预置模板。
- 是否使用 JSON 或 Markdown，可按任务复杂度与协作方式选择。
- 状态文件的目标是保留**当前有效结论**，而不是保存完整思考过程。

## 4. 最小状态集合

状态文件至少应记录：

- 当前子任务是什么
- 已完成的逻辑点有哪些
- 尚未处理的边缘情况有哪些
- 当前已确认的接口契约、关键变量或结构边界
- 当前剩余风险与阻塞项是什么
- 下一步应从哪里继续

## 5. 同步时机

以下时机必须更新状态：

- 切换子任务前
- 完成一个阶段结论后
- 准备压缩上下文前
- 准备 clean-slate handoff 前
- 长任务出现方向修正时

## 6. 记录原则

- 只记录当前仍然成立的结论。
- 不记录冗长日志、失败尝试与噪音过程。
- 优先记录边界、契约、风险与下一步入口。
- 若代码或文档已成为权威来源，状态文件只补充“当前推进状态”，不重复复制实现细节。

## 7. 与其他规则的关系

- 本规则负责“当前状态持久化”。
- `checkpoint.md` 负责“阶段快照与交接摘要”。
- `20_Workflow_Lifecycle/progressive-handoff.md` 负责“长链路任务如何拆分与接力”。
