# Mode Switch

## 1. 目标

长任务中最常见的问题之一，是把需求理解、方案设计、代码实现与结果验证混在同一轮注意力里处理，导致边界失焦。

本规则要求按职责切换模式，降低上下文污染与执行漂移。

## 2. 模式定义

### 2.1 Architect Mode

职责：

- 理解目标、约束与影响范围
- 输出分析结论、验收项与技术方案
- 明确接口契约、状态边界与扩展点
- 维护关键文档与结构约束

限制：

- 不直接承担具体业务代码实现
- 不跳过验收与设计直接进入编码

### 2.2 Coder Mode

职责：

- 读取已确认的 AC、方案与约束
- 在既定边界内完成实现
- 保证实现与方案、验收项一一映射
- 在执行过程中同步必要状态

限制：

- 不擅自重写目标
- 不在未回到设计阶段前扩张影响范围

### 2.3 Reviewer / Verifier Mode

职责：

- 检查实现是否满足 AC
- 核对验证动作与验证结果
- 汇总剩余风险、例外与未覆盖点
- 形成 checkpoint 或 handoff summary

限制：

- 不把验证环节变成新的需求扩张入口
- 不以主观偏好替代既有验收标准

## 3. 切换时机

- 进入 P1 / P2 / P3 时，以 Architect Mode 为主
- 进入 P4 时，切换到 Coder Mode
- 进入 P5 时，切换到 Reviewer / Verifier Mode
- 当目标、验收或设计发生变化时，应退出当前模式并回到对应阶段

## 4. 协作规则

- 不同模式应共享同一份已确认约束，而不是共享冗长对话历史。
- 模式切换前，应同步状态文件或 checkpoint。
- 若采用多 Agent / 多实例协作，应按模式分工，而不是让所有实例同时承担全链路职责。

## 5. 使用原则

- 模式切换的目标是收敛职责，不是增加流程表演。
- 模式越清晰，交付越稳定。
- 若任务极小，可由同一执行者完成多个模式，但仍要在思维上区分当前职责。
