# 最小实现纪律

## 1. 定位

本纪律是 P4「按方案实现」时的**常驻底线**：**默认对每一次迭代生效，不是模式、无需指令触发、始终在线**。它和同目录的 `correction-contract.md` 并列——一个管**写新码时怎么少写、写准**，一个管**修错时怎么挖根因、不假绿**。

它只约束"怎么实现"，不改"实现什么"（那是 `.ai/TECH_PLAN.md` 定的）。核心一句话：**能不写的代码就是最好的代码**；但"少写"永远是缩短解决方案，绝不是缩短对问题的理解（见 §5）。

## 2. 最小实现阶梯

动手写一段实现前，**应**从上往下爬，**停在第一个成立的档**——成立即用它、别继续往下；两级都成立取更高（更省）的那级，别纠结。

1. **这功能需要存在吗？** 投机的、"以后可能要"的需求——**不写**，用一行说明为什么跳过（YAGNI）。
2. **本仓已经有了吗？** 已在库里的 helper / util / 类型 / 既有模式——**复用**，不重写。动手前先找；把几个文件外就有的东西又实现一遍，是最常见的浪费。
3. **标准库能做吗？** 能就**用标准库**。
4. **平台原生特性覆盖吗？** 原生优先——如 `<input type="date">` 胜过日期选择器库、CSS 胜过 JS、数据库约束胜过应用层代码。
5. **已装的依赖能解吗？** 能就**用它**；**不得**为几行代码就能做的事新增一个依赖。
6. **能一行搞定吗？** 能就**一行**。
7. **到这一步才轮到**：能跑起来的最小新代码。

> 阶梯是**反射，不是研究项**：它在你**读懂问题、走通真实流程之后**才跑，不是代替理解。先把任务和它触及的代码读明白，再爬。第一个能用的最小解就是对的解——但前提是你已经确知这次改动要碰哪些地方。

## 3. 有意简化的标记

**应**给有意为之的简化留一个可 grep 的标记注释 `butler-min:`，让读代码的人（和未来的你）把它读作**意图**、不是**疏忽**。标记正文**必须**含两要素：**已知天花板**（这个简化在什么情况下会不够）+ **升级路径**（到时候换成什么）。

```js
// butler-min: 全局锁；吞吐吃紧再拆成按账户锁
// butler-min: O(n²) 扫描；列表破千再上索引
```

```python
# butler-min: 朴素启发式，够当前用例；badcase 变多再换正式解析器
```

无天花板、无升级路径的裸简化不算合格标记——那只是没写完。

## 4. 修根因，不修症状

工单报的是**症状**，改的**必须**是**根因**。动手前**应** grep 你要改的那个函数的**所有 caller**：

- **把守卫 / 修正放在所有调用都汇聚的那一处**（共享函数里）——这比在每个 caller 各补一遍 diff 更小，且不会漏掉兄弟调用点。
- **不得**只补工单点名的那一条路径就收工——那样其它 caller 仍是坏的，等着下一张工单。

最省事的修法恰好就是根因修法：一处到位，全线归位。

## 5. 何时不许偷懒

以下**绝不简化掉**，阶梯到这里让路：

- **信任边界的输入校验**（外部输入、跨系统入口）。
- **防数据丢失的错误处理**。
- **安全措施**、**无障碍（accessibility）基线**。
- **用户明确要求的东西**——用户坚持要完整版就做完整版，不重新论证。

还有一条最高优先：**绝不对"理解问题"偷懒**。阶梯缩短的是代码长度，**从不**缩短读代码。为了交一个小 diff 而跳过理解，是最危险的偷懒——它伪装成高效，却交出一个自信的错误修改。**先读透，再偷懒。**

> 非平凡逻辑（含分支 / 循环 / 解析 / 涉钱或安全的路径）的最小实现，**应**留一个能跑的最小检查（一个 `assert` 自检或一个小测），"最小"到逻辑一坏它就失败即可；平凡一行不必配测（对测试也适用 YAGNI）。探测强度与分道口径仍以 `testing-strategy.md` 为准。

## 6. 与其他规则的关系

- **与 `correction-contract.md`**：并列的 P4 常驻底线。本纪律管"写新码少写、修 bug 挖根因"，纠错契约管"验证失败后修到真过、禁降级修复、诚实停"；§4 修根因是"最小改动"论证、与纠错契约的"修到真过"互补不重叠。
- **与 `20_Workflow_Lifecycle/maintenance-boundaries.md`**：那份管 `.ai/` 维护文件"何时更新"的成本边界；本纪律管"实现代码怎么写"，层面不同、只呼应"防过度工程"这一共同取向。
- **与 `20_Workflow_Lifecycle/tech-plan-schema.md`（任务粒度）**：那份约束拆任务的粒度别过度细化；本纪律约束每个任务落地时的实现繁简，二者一个管"拆多细"、一个管"写多少"。
- **探测**：非平凡逻辑的最小检查、UI / 交互的自动化与人测分道，见 `testing-strategy.md`；置信档见 `20_Workflow_Lifecycle/verify-schema.md`。
- **压缩口径**：`templates/rule-card.md` 执行纪律段收录本纪律的一句话压缩版，全文单源在此、不重抄。
