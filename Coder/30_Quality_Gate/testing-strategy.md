# Testing Strategy

## 1. 目标

测试与验证的目标不是证明“代码能跑”，而是证明：

- 功能已完成
- 结构是正确的
- 验收项可回溯
- 风险是可说明的

## 2. 测试分层建议

### 2.1 单元测试

适用于：

- 领域纯函数
- 数据转换函数
- 规则判断逻辑
- 小范围算法或状态变换

重点验证：

- 输入输出稳定
- 边界条件覆盖
- 错误状态可识别

### 2.2 组件测试

适用于：

- 组件 props / emits 映射
- 表单联动
- 工具栏或面板状态切换
- 关键交互路径

重点验证：

- 输入是否正确反映到 UI
- 输出事件是否按预期触发
- 用户关键路径是否可复现

### 2.3 集成测试

适用于：

- 多模块协同
- 页面状态与领域模型联动
- 插件能力与主流程协作
- 关键端到端路径

重点验证：

- 模块之间是否保持语义一致
- 修改 / 删除 / 回滚等场景是否一致
- 扩展机制是否遵守契约边界

## 3. 最小验证集合

至少完成以下检查再交付：

- 类型检查通过
- 构建或关键运行链路通过
- 关键路径手动验证完成
- 与本次改动相关的核心规则已有验证依据
- 无明显死代码、调试日志、无关改动

## 4. 验收映射

验证结果必须能映射回 AC：

- 每个 AC 都应对应至少一个验证动作。
- 验证结论要么通过、要么明确失败原因。
- 剩余风险不可隐藏，应显式列出。

## 5. 可接受交付的标准

一个可接受的交付结果应满足：

- 可运行
- 可解释
- 可验证
- 可维护
- 可扩展

## 6. 验证结论回写要求

验证完成后，结论不应只停留在当前对话里，还应按需要回写到 checkpoint 或 handoff summary。

至少应回写：

- 已验证通过的 AC
- 每项 AC 对应的验证动作
- 未通过项或剩余风险
- 下一步是否可以继续推进
