# Testing Strategy

## 1. 目标

测试与验证的目标不是证明"代码能跑"，而是证明：

- 功能已完成
- 结构是正确的
- 验收项可回溯
- 风险是可说明的

## 2. 自动化优先（硬纪律）

**凡机器能测的，必须自动化。** 测试与验证默认走自动道；人工只承接机器确实测不了的极少残余（判定见 §3）。这是一条硬纪律、不是建议——不得因"手动更快"而把本可自动化的验证推给人。

- **UI / 交互也属自动道**：界面渲染、表单联动、关键交互路径可用浏览器自动化 / headless（如 Playwright）+ 可编程视觉断言（截图对基线比对）覆盖，不得默认推人工点检。
- **拿不准归哪道时先尝试自动化**（默认归自动道）；只有确证机器不可测，才落人测道。

以下分层是**自动道要覆盖的层次**；具体采用哪些，结合当前项目类型与已激活的 profile 决定。

### 2.1 单元测试

适用于：

- 领域纯函数
- 数据转换函数
- 规则判断逻辑
- 小范围算法或状态变换

重点验证：

- 输入输出稳定
- 边界条件覆盖
- 错误状态可识别

### 2.2 组件测试

适用于包含 UI 组件层的项目，例如 Web 前端、客户端界面或其他存在明确交互组件的工程形态：

- 组件 props / emits 映射
- 表单联动
- 工具栏或面板状态切换
- 关键交互路径

重点验证：

- 输入是否正确反映到 UI
- 输出事件是否按预期触发
- 用户关键路径是否可复现（**优先用浏览器自动化复现，而非人工点击**）

### 2.3 集成测试

适用于：

- 多模块协同
- 页面状态与领域模型联动
- 插件能力与主流程协作
- 关键端到端路径

重点验证：

- 模块之间是否保持语义一致
- 修改 / 删除 / 回滚等场景是否一致
- 扩展机制是否遵守契约边界

## 3. 分道口径（自动道 / 人测道）

每条 AC 的验证显式归入一条道，并回填 `VERIFY_REPORT.md`（回填格式见 `20_Workflow_Lifecycle/verify-schema.md`）：

- **自动道**：butler 可执行、可复现的验证——单测 / 集成 / 类型检查 / 构建 / 浏览器自动化 / 可编程视觉断言等。**默认道**。
- **人测道**：机器确实测不了、只能由人判定的**残余**。允许落人测道的类目**仅限**：
  - **主观审美**：视觉美感、品牌调性、动效"顺不顺"等主观感受。
  - **物理设备**：真机触感、外设、硬件交互等需要实物的验证。
  - **真人感知 / 决策**：需人主观感知或价值判断才能拍板的项。
  - **外部人工闸**：依赖第三方人工审核 / 线下流程等 butler 无法驱动的环节。

判定纪律：

- **默认归自动道**。归人测道必须能对应上述某一类目，并在 `VERIFY_REPORT.md` 说明为何机器不可测；说不出类目 = 应回自动道。
- 不得因"暂时没写自动化"就归人测道——那是自动道的欠债，不是人测残余。

## 4. 最小验证集合

最小验证集合由**通用质量门禁 + 已激活的 profile 要求**共同组成。

至少完成以下检查再交付：

- 类型检查通过
- 构建或关键运行链路通过
- **关键路径默认自动验证完成**（浏览器自动化 / 集成测试覆盖；人测仅承接 §3 的例外残余）
- 与本次改动相关的核心规则已有验证依据
- 无明显死代码、调试日志、无关改动

## 5. 验收映射

验证结果必须能映射回 AC：

- 每个 AC 都应对应至少一个验证动作，并显式归入自动道 / 人测道（§3）。
- 验证结论要么通过、要么明确失败原因。
- 剩余风险不可隐藏，应显式列出。

## 6. 可接受交付的标准

一个可接受的交付结果应满足：

- 可运行
- 可解释
- 可验证
- 可维护
- 可扩展

## 7. 验证结论回写要求

验证完成后，结论不应只停留在当前对话里，还应按需要回写到 checkpoint、handoff summary，或在完整交付时汇总到人类可读的 Delivery Summary。

至少应回写：

- 已验证通过的 AC（含其所属道：自动 / 人测）
- 每项 AC 对应的验证动作
- 未通过项或剩余风险
- 人测道残余（若有）及其状态
- 下一步是否可以继续推进
