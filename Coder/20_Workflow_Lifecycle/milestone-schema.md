# Milestone Schema

## 1. 目标

迭代 (Iteration) 把单轮需求固定为可追溯的 `P1 -> P5` 闭环，但一个**大可交付版本**往往需要若干迭代持续推进才能成形。缺少版本层时，"这个大版本到底圈定了什么范围、拆成了哪几个迭代、整体交付了没有"无处沉淀。

本规范引入**里程碑 (Milestone)** 作为套在迭代之上的**版本范围单元**：

```
Milestone (大可交付版本, MILE-NNNN)
  └─ Iteration (小可交付版本, ITER-NNNN) ×N
       └─ P1 -> P2 -> P3 -> P4 -> P5
```

核心原则：

- 里程碑是**松耦合可选**层：处于 `active` 里程碑期间开启的迭代自动归属它；无里程碑时独立迭代仍合法。极小、零信号的简化路径任务既不开迭代也不开里程碑。
- 里程碑**方向性、不冻结**：它承载范围评估与理解阐释，可随推进演进，**不进入 ACK 冻结门、不被 hook 机械拦截**。冻结纪律仍只作用于迭代的 `AC_LIST.md`（见 `iteration-schema.md` §5）。
- 里程碑是**大版本可交付单元**：收口时聚合其下各迭代，产出版本级交付总结。
- **文档有界，历史横向归档**：里程碑工作区单份文档只承载当前里程碑内容；跨里程碑历史靠 `milestones/MILE-NNNN/` 目录横向铺开，严禁纵向堆进同一文件。

## 2. 里程碑号

- 格式：`MILE-NNNN`，四位零填充、单调递增（`MILE-0001`、`MILE-0002`……）。
- 分配来源：从 `.ai/MILESTONES.md` 台账读取最大已用号 + 1，**不依赖对话记忆推断**。
- 单调性：里程碑号只增不减、不复用；废弃的里程碑在台账标记 `abandoned`，号不回收。
- 唯一性：同一时刻最多只有一个 `active` 里程碑。

## 3. 四层落盘结构

里程碑相关文档分四层，职责互不重叠。注意它与迭代的落盘形态不同：迭代归档需容纳四件套多文件故按号分目录，里程碑每个单元只有一份总结文件，故**交付层平铺、归档层才分目录**。

| 层 | 位置 | 角色 |
|---|---|---|
| 里程碑台账 | `.ai/MILESTONES.md` | 脊柱与索引。记录 `current` 指针与全部里程碑的号/标题/状态/时间/含迭代/交付链接，是"当前里程碑号是几、有哪些历史里程碑、各含哪些迭代"的唯一真源 |
| 当前里程碑工作区 | `.ai/MILESTONE.md` | active 里程碑的活产物：范围评估 + 理解阐释 + 拆分路线图 + 范围演进记录 |
| 里程碑归档 | `.ai/milestones/MILE-NNNN/MILESTONE.md` | 里程碑收口时工作区的冻结快照，只读，供复盘审计 |
| 人类交付 | `deliveries/milestones/MILE-NNNN-<slug>.md` | 收口后给人看的版本级交付总结，**只链接**其下各迭代交付，不全文嵌入 |

约束：

- 里程碑工作区路径固定为 `.ai/MILESTONE.md`，**不得**改成按号分目录。
- `.ai/milestones/` 与各 `MILE-NNNN/` 子目录不在基地车部署时创建，而是在**首次里程碑收口**时按需产生。
- `deliveries/milestones/` 目录不在部署时创建，而是在**首次里程碑收口**写版本级交付时按需产生。
- 迭代交付文档仍平铺在 `deliveries/ITER-NNNN-<slug>.md`，**不随里程碑归属移动**，以保证迭代历史在 `deliveries/` 文件树中始终是一条按号连续的时间线。

## 4. 里程碑台账 `.ai/MILESTONES.md`

### 4.1 必填字段

- `current`：当前活跃里程碑号；无活跃里程碑时为 `none`。
- 里程碑表，每行一个里程碑，含：`里程碑号`、`标题`、`状态`、`开启日期`、`收口日期`、`含迭代`、`交付链接`。

### 4.2 状态取值

- `active`：当前进行中，`.ai/MILESTONE.md` 属于它。
- `closed`：已收口，已归档并已交付。
- `abandoned`：已废弃，号不回收，需在备注说明原因。

### 4.3 标准模板

```md
# 里程碑台账

current: MILE-0002

| 里程碑号 | 标题 | 状态 | 开启 | 收口 | 含迭代 | 交付 |
|---|---|---|---|---|---|---|
| MILE-0002 | <本里程碑标题> | active | YYYY-MM-DD | — | ITER-0004, ITER-0005 | — |
| MILE-0001 | <上一里程碑标题> | closed | YYYY-MM-DD | YYYY-MM-DD | ITER-0001~0003 | deliveries/milestones/MILE-0001-<slug>.md |
```

### 4.4 编写规则

- 台账只记结论性索引信息，不写里程碑内的过程细节（过程细节归 `.ai/MILESTONE.md` 拆分路线图与各迭代工作区）。
- 每次开启 / 收口 / 废弃里程碑，必须同步更新本表与 `current` 指针，二者不得不一致。
- 「含迭代」列在每个承接迭代开启时追加其迭代号，与 `.ai/ITERATIONS.md` 的「所属 milestone」列互为对账（见 `iteration-schema.md` §4.1）。

## 5. 里程碑工作区 `.ai/MILESTONE.md`

active 里程碑的活产物，承载下列四段。它是**方向性产物**：内容随推进演进，修改只需更新本文件并在「范围演进记录」追加一行，**不重新走 ACK**。

### 5.1 范围评估

- `In Scope（版本级）`：本大版本承诺交付的能力边界。
- `Out of Scope（版本级）`：本大版本显式不做的部分。
- `关键交付目标`：版本收口时必须达成的结果。

### 5.2 理解阐释

- 本里程碑要解决的核心问题。
- 背景与价值。
- 对系统的整体影响判断（涉及哪些模块、契约、关键路径的宏观研判）。

### 5.3 拆分路线图

把范围评估落成一串有序迭代，是里程碑承上启下的核心看板。

- 路线项按**主题切片**排序（`R1` / `R2`……），每项是"方向 → 一个迭代"的映射。
- **开启时绑号**：迭代号单调递增、开启时才从台账分配，故路线项的「实际 ITER」列**留空，待该迭代开启时再绑定真实号**，不得预先占号。
- 段首可标「预计跨度 ITER-NNNN ~ ITER-NNNN」作方向性说明，但**真源以「实际 ITER」列 + 台账为准**，预计跨度与实际不符时以实际为准、不需校正预计值。
- 路线图**规划性、非冻结**：增删改顺序只更新本表并在 §5.4 追加一行，无需 ACK。

模板：

```md
## 拆分路线图

预计跨度：ITER-0002 ~ ITER-0005（4 个迭代承接）

| 路线项 | 主题 / 范围切片 | 实际 ITER | 状态 |
|---|---|---|---|
| R1 | <切片一> | ITER-0002 | closed |
| R2 | <切片二> | ITER-0003 | active |
| R3 | <切片三> | — | planned |
| R4 | <切片四> | — | planned |
```

- 路线项状态取值：`planned`（已规划未开启）、`active`（对应迭代进行中）、`closed`（对应迭代已收口）、`abandoned`（路线项取消或对应迭代废弃）。
- 路线项状态必须与台账中该迭代的实际状态对账，不得不一致。
- **与迭代状态消歧**：「路线项状态」是路线项自身的命名空间，**与迭代行状态不是同一字段**——迭代行状态是 `iteration-schema.md §4.2` 的封闭三态（`active`/`closed`/`abandoned`，无 `planned`）。`planned` 路线项的「实际 ITER」恒为 `—`、**不产生迭代台账行**；故 `planned` 不应出现在 `.ai/ITERATIONS.md`（部署项目由 `ledger_status` hook 机械拦截）。路线项绑定真实迭代号时，台账里那一行的状态走 §4.2 三态。

### 5.4 范围演进记录

- 每次范围评估、理解阐释或拆分路线图发生方向性变化时，追加一行：`YYYY-MM-DD：<一句变更摘要>`。
- 这是里程碑"不冻结但可追溯"的依据，替代迭代侧的 ACK 修订记录。

## 6. 启动信号与时机

里程碑松耦合可选，不得为每个任务都开。AI 收到任务时跑一遍**启动信号清单**，命中任一即**主动提议**开里程碑，经用户 soft 对齐后开启；零命中则直接走独立迭代，不开里程碑。

### 6.1 启动信号（命中任一即提议开里程碑）

| 信号 | 判断依据 |
|---|---|
| 跨迭代体量 | 需求预计需 ≥ 2 个可独立交付的迭代才能闭环 |
| 版本主题 | 存在统一的版本主题，需要版本级范围评估与聚合交付 |
| 先评估后拆分 | 用户要求先整体圈定范围/方向，再拆分推进 |
| 显式里程碑 | 用户显式要求按里程碑 / 大版本组织 |

### 6.2 时机

- 在**第一个承接迭代进入 P1 之前**开里程碑：先写 `.ai/MILESTONE.md`（范围评估 + 理解阐释 + 拆分路线图）并向用户呈交对齐，再从台账领第一个迭代号进入 P1。
- soft 对齐是方向确认，**不是硬门**：用户认可方向即可推进，不要求逐条 ACK，里程碑随后仍可演进。
- 里程碑不是新阶段、不阻塞流程，迭代的 `P1 -> P5` 推进规则仍以 `lifecycle.md` 为准。

### 6.3 补开 / 回挂（例外路径）

- 若先开了独立迭代，推进中才发现它属于一个更大的版本，可显式开里程碑，并在 `.ai/MILESTONES.md`「含迭代」列与 `.ai/ITERATIONS.md`「所属 milestone」列把已有迭代回挂。
- 这是例外路径，不是常态；常态是里程碑先开、迭代后归属。

### 6.4 录入：里程碑意图书 (Brief)

里程碑的录入支持"一次性表达大版本意图，由模型合成概述"。用户把想推进的大版本想法**在一处说清**，模型据此生成 `.ai/MILESTONE.md`，省去边问边拼的零散对话。

**两条录入通道（等价，任选其一）**：

| 通道 | 用法 |
|---|---|
| 对话 | 用户在对话里直接讲清大版本意图（可配合 §6.5 的 `/milestone` 命令）。 |
| 文件 | 用户把原始概念文件投放到项目根 `origin/` 收件箱（自由格式、任意命名/数量），由模型读取。 |

**Brief 定位**：

- **可选、非权威、一次性输入**：brief 只是合成 `.ai/MILESTONE.md` 的原材料，**不属 §3 四层落盘结构、不归档、不跨里程碑纵向堆积**。
- `origin/` 文件由用户自管，AI **只读、不写不改不重塑不归档**（与 `.ai/references/` 的区分见 `mcv-deployment.md` §2）。
- 合成完成后，**`.ai/MILESTONE.md` 是唯一真源**；origin 文件用户可保留作溯源或自行清理，不影响里程碑产物。

**合成协议（brief → `.ai/MILESTONE.md`）**：

1. **收集输入**：读取对话意图，或 `origin/` 中用户指明的概念文件；多份未指明时汇总相关文件并回述确认范围，不擅自取舍。
2. **解析落三段**：把意图映射到 §5 的范围评估（In/Out Scope + 关键交付目标）、理解阐释（核心问题/背景价值/系统影响）、拆分路线图（按主题切片排序 R1/R2…）。
3. **缺口显式化**：brief 信息不足处，在相应段落显式标"待澄清"，**不臆造范围或目标**。
4. **拆分路线图沿用 §5.3 不预先占号**：路线项给主题切片 + 段首「预计跨度 ITER-NNNN ~ ITER-NNNN」，「实际 ITER」列**留空**待各迭代开启时绑真号。这是"拆分规划"而非"硬占全局号"，与 §5.3 一致。
5. **soft 对齐**：产出后向用户呈交方向确认（**非硬门**，不要求逐条 ACK）；认可即按 §7.1 开启，后续仍可按 §5.4 / §7.3 演进。

### 6.5 命令（轻量入口，与语义触发并存）

里程碑提供两个轻量命令作为显式入口糖；它们**触发的仍是既有生命周期，不新增阶段、不阻塞流程**，与 §6.1 信号语义触发**等价**。

| 命令 | 语义 |
|---|---|
| `/milestone`（可带意图文本或指向 `origin/` 文件） | 开启 / 录入里程碑：按 §6.1 跑启动信号判定，命中则走 §6.4 合成 + §7.1 开启；无参时从对话或 `origin/` 取 brief。 |
| `/milestone status` | **只读看板**：读 `.ai/MILESTONES.md` + `.ai/MILESTONE.md`，汇报当前里程碑标题/状态、范围评估摘要、拆分路线图各路线项进度、已含迭代、下一个 `planned` 路线项；**不写任何文件、不改状态**。无 active 里程碑时如实报"当前无 active 里程碑"。 |

- 命令面只覆盖最高频的 open / status；**收口、废弃、演进仍走语义**（§7.3 / §7.4 / §7.5），不命令化。
- 命令是可选糖：不输命令、直接用自然语言表达同样生效。

## 7. 里程碑生命周期

### 7.1 开启 (Open)

- 时机：命中 §6.1 启动信号、准备启动一个大版本时。
- 动作：从台账领下一个 `MILE-NNNN`，写入台账并置 `active`、`current` 指向它；产出 `.ai/MILESTONE.md`（范围评估 + 理解阐释 + 拆分路线图）并向用户呈交 soft 对齐。`.ai/MILESTONE.md` 的录入通道（对话 / `origin/` 文件）与 brief→产物合成协议见 §6.4，显式命令入口见 §6.5。
- **overwrite-only（硬约束）**：开启新里程碑时，`.ai/MILESTONE.md` 必须以本里程碑内容**整体覆写**，严禁保留或追加上一里程碑内容；上一里程碑的产物只在收口时归档的 `milestones/MILE-NNNN/` 中存续。
- 上一里程碑若已收口，`current` 应为 `none`；开启即把 `current` 指向新号。若上一里程碑未收口就要开新里程碑，先按 §7.4 / §7.5 处理旧里程碑，不得跳过。

### 7.2 推进 (Advance)

- 里程碑处于 `active` 期间开启的每个迭代**一律自动归属**之（无需逐次征求确认）。每开一个承接迭代：① 在该迭代的 `.ai/ITERATIONS.md` 行「所属 milestone」列填 `current` 里程碑号；② 在 `.ai/MILESTONES.md`「含迭代」列追加其号；③ 把它绑定到 `.ai/MILESTONE.md` 拆分路线图对应路线项的「实际 ITER」列。归属判定只认台账 `current`：`current = 本里程碑号` 即归属。
- 每个承接迭代各自走完整 `P1 -> P5` 并各自收口、各自交付（小版本交付落在 `deliveries/ITER-NNNN-<slug>.md`），迭代收口纪律以 `iteration-schema.md` §5 为准。

### 7.3 演进 (Evolve)

- 适用：里程碑范围、理解或拆分路线图发生方向性变化。
- 动作：更新 `.ai/MILESTONE.md` 相应段，并在 §5.4 范围演进记录追加一行。**无需 ACK、无需另开里程碑**。
- 与迭代的关系：里程碑范围演进不直接松动已冻结迭代的验收范围；某个迭代自身的修订/扩张仍按 `iteration-schema.md` §5 处理。

### 7.4 收口 (Close)

- 时机：版本范围达成、其下迭代均已 `closed`（或显式 `abandoned`）、确认大版本可交付时。
- 动作（三步，缺一不可）：
  1. 把 `.ai/MILESTONE.md` 快照复制到 `.ai/milestones/MILE-NNNN/MILESTONE.md`。
  2. 生成版本级交付总结 `deliveries/milestones/MILE-NNNN-<slug>.md`，聚合其下各迭代交付，并按 `delivery-summary.md` §9 用固定模板填槽并列产出同名 `deliveries/milestones/MILE-NNNN-<slug>.html` 阅读视图（含里程碑专用「拆分路线图回填」段）；结构与触发参考 `delivery-summary.md`（聚合口径见其 §4.8）；`.md` 与 `.html` 均**只链接各迭代交付路径与里程碑产物路径，不得全文嵌入**（见 `delivery-summary.md §4.7` 与本规范 §9）。
  3. 台账该行置 `closed`、填收口日期与交付链接，`current` 置 `none`。
- 版本级整体验收：收口前必须确认拆分路线图各路线项均 `closed`/`abandoned`、其下迭代验收闭环；存在 `planned`/`active` 路线项时不得收口（除非显式废弃该路线项）。
- **收口后归属边界**：`current` 置 `none` 后，再开启的迭代**不再自动归属本（已收口）里程碑**、不回写其「含迭代」与路线图，按独立迭代处理；已收口里程碑不接收新迭代、不被回挂。若新迭代属于另一个大版本，按 §7.1 另开里程碑或 §6.3 回挂到另一个 `active` 里程碑。

### 7.5 废弃 (Abandon)

- 时机：里程碑中途确认方向推翻、不再继续。
- 动作：台账该行置 `abandoned` 并备注原因，`current` 置 `none`；已收口的承接迭代交付保留原位，不回收。可选择是否快照归档（若有复盘价值则归档）。

## 8. 与迭代 / 执行流程的关系

- 里程碑不是新阶段，而是套在"迭代（套在 `P1 -> P5` 外）"之外再外一层的版本范围单元；阶段推进规则仍以 `lifecycle.md` 为准，迭代锁定纪律仍以 `iteration-schema.md` 为准。
- 里程碑层**不被 hook 机械拦截**：phase_gate 仅校验迭代工作区四件套，里程碑保持松耦合、可选、方向性。
- `.ai/ITERATIONS.md`「所属 milestone」列与本规范的 `.ai/MILESTONES.md`「含迭代」列互为对账，两者真源各管一侧、不得不一致。
- 全量迭代时间线的真源是 `.ai/ITERATIONS.md` 台账（单调递增 + 「所属 milestone」列），一张表同时给出时间线与版本归组；`deliveries/` 文件树布局只决定大块交付文档存放位置。

## 9. 交付文档结构

`deliveries/` 同时承载迭代交付与里程碑交付，布局如下：

```txt
deliveries/
  ITER-0001-<slug>.md          # 迭代交付（小版本），平铺按号即时间线
  ITER-0002-<slug>.md
  ...
  ITER-0006-<slug>.md          # 独立迭代（无里程碑）同列时间线
  milestones/
    MILE-0001-<slug>.md        # 里程碑交付（大版本），链其下各迭代交付
    MILE-0002-<slug>.md
```

- 每份交付（迭代级与里程碑级）都另有一份**同目录、同 slug、仅扩展名为 `.html`** 的固定格式阅读视图（如 `ITER-0001-<slug>.html`、`milestones/MILE-0001-<slug>.html`）；`.md` 为引用真源，`.html` 生成协议见 `delivery-summary.md` §9。上图省略 `.html` 兄弟文件以保持时间线清晰。
- 迭代交付平铺在 `deliveries/` 根，无论是否归属里程碑都不移动，保证迭代历史在文件树中是一条连续时间线。
- 里程碑交付集中在 `deliveries/milestones/`，不污染迭代时间线。
- 版本级交付的结构、聚合口径与对话层风格以 `delivery-summary.md` 为准。
