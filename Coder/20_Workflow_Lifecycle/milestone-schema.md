# Milestone Schema

## 1. 目标

迭代 (Iteration) 把单轮需求固定为可追溯的 `P1 -> P5` 闭环，但一个**大可交付版本**往往需要若干迭代持续推进才能成形。缺少版本层时，"这个大版本到底圈定了什么范围、拆成了哪几个迭代、整体交付了没有"无处沉淀。

本规范引入**里程碑 (Milestone)** 作为套在迭代之上的**版本范围单元**：

```
Milestone (大可交付版本, MILE-NNNN)
  └─ Iteration (小可交付版本, ITER-NNNN) ×N
       └─ P1 -> P2 -> P3 -> P4 -> P5
```

核心原则：

- 里程碑是**松耦合可选**层：处于 `active` 里程碑期间开启的迭代自动归属它；无里程碑时独立迭代仍合法。极小、零信号的简化路径任务既不开迭代也不开里程碑。
- **讨论不等于开工**：brief 已合成、但用户尚未决定推进的内容先进未编号候办区；只有明确开始推进时才领取 `MILE-NNNN`。
- 里程碑**方向性、不冻结**：它承载范围评估与理解阐释，可随推进演进，**不进入 ACK 冻结门、不被 hook 机械拦截**。冻结纪律仍只作用于迭代的 `AC_LIST.md`（见 `iteration-schema.md` §5）。
- 里程碑是**大版本可交付单元**：收口时聚合其下各迭代，产出版本级交付总结。
- **文档有界，历史横向归档**：里程碑工作区单份文档只承载当前里程碑内容；跨里程碑历史靠 `milestones/MILE-NNNN/` 目录横向铺开，严禁纵向堆进同一文件。
- **Goal 分层**：里程碑范围/关键交付目标组成版本级 Goal，路线项与归属迭代提供 obligations/proof；状态按 `goal-contract.md` 派生。里程碑 Goal 聚合迭代，不覆盖单迭代 AC，也不另建 GOAL 台账。

## 2. 里程碑号

- 格式：`MILE-<数字>`，至少四位、四位内零填充、超过四位自然增长且单调递增（`MILE-0001`、`MILE-9999`、`MILE-10000`）。编号比较一律取数字部分，不按字符串排序。
- 分配时机：**正式开启时才分配**。只讨论、合成或暂存 brief 都不得预占号。
- 分配来源：未分片项目从 `.ai/MILESTONES.md` 正式表读取最大号；已分片项目从 `.ai/state-index.json` 的 `max_used` 读取并由 `state-ledger check` 对账，再 +1。不计候办键或草稿名，**不依赖对话记忆或只扫热表推断**。
- 单调性：里程碑号只增不减、不复用；废弃的里程碑在台账标记 `abandoned`，号不回收。
- 开启前撤销例外：若当前 active 里程碑是**正式表最新号**，且尚未绑定任何迭代、未归档、未产生交付，则它仍属“误开的开启前草稿”，可按 §7.6 退回候办并移除该临时行。这不是复用历史号，因为该号尚未形成任何历史引用。
- 历史红线：只要已绑定任何迭代、已归档或已产生交付，号码就永不回收；暂停/取消只能走 §7.4 收口或 §7.5 废弃。
- 唯一性：同一时刻最多只有一个 `active` 里程碑。

## 3. 候办暂存 + 四层正式落盘

里程碑正式开启前有一个**未编号候办暂存层**；开启后仍按原有四层管理。候办不是第五种里程碑状态，而是尚未成为里程碑的候选草稿。

| 层 | 位置 | 角色 |
|---|---|---|
| 候办索引 | `.ai/MILESTONES.md` 的“待办区” | 只列未编号的稳定 slug、标题、暂缓日期、草稿路径和原因；不参与 `current` 或正式号分配 |
| 候办草稿 | `.ai/milestone-backlog/<slug>.md` | 保留已合成的范围、理解、路线图和演进记录；候办期间的唯一详情真源 |
| 里程碑台账 | `.ai/MILESTONES.md` + `.ai/state-index.json` + `.ai/history/milestones/*.{md,json}` | 复合真源：根表保存 `current`、近期正式行和未编号待办；有界 index 保存固定路由公式，每个冷片由同名 `.json` 独立校验 |
| 当前里程碑工作区 | `.ai/MILESTONE.md` | active 里程碑的活产物：范围评估 + 理解阐释 + 拆分路线图 + 范围演进记录 |
| 里程碑归档 | `.ai/milestones/MILE-NNNN/MILESTONE.md` | 里程碑收口时工作区的冻结快照，只读，供复盘审计 |
| 人类交付 | `deliveries/milestones/MILE-NNNN-<slug>.md` | 收口后给人看的版本级交付总结，**只链接**其下各迭代交付，不全文嵌入 |

约束：

- 里程碑工作区路径固定为 `.ai/MILESTONE.md`，**不得**改成按号分目录。
- `.ai/milestones/` 与各 `MILE-NNNN/` 子目录不在基地车部署时创建，而是在**首次里程碑收口**时按需产生。
- `.ai/milestone-backlog/` 不在部署时预建，首次把讨论稿暂缓入库时按需创建。一个 slug 必须恰好对应待办区一行和一份同名 `.md`，禁止孤立索引或孤立草稿。
- `deliveries/milestones/` 目录不在部署时创建，而是在**首次里程碑收口**写版本级交付时按需产生。
- 迭代交付文档仍平铺在 `deliveries/ITER-NNNN-<slug>.md`，**不随里程碑归属移动**，以保证迭代历史在 `deliveries/` 文件树中始终是一条按号连续的时间线。

## 4. 里程碑台账 `.ai/MILESTONES.md`

### 4.1 必填字段

- `current`：当前活跃里程碑号；无活跃里程碑时为 `none`。
- 里程碑表，每行一个里程碑，含：`里程碑号`、`标题`、`状态`、`开启日期`、`收口日期`、`含迭代`、`交付链接`。

### 4.2 状态取值

- `active`：当前进行中，`.ai/MILESTONE.md` 属于它。
- `closed`：已收口，已归档并已交付。
- `abandoned`：已废弃，号不回收，需在备注说明原因。

### 4.3 标准模板

```md
# 里程碑台账

current: MILE-0002

| 里程碑号 | 标题 | 状态 | 开启 | 收口 | 含迭代 | 交付 |
|---|---|---|---|---|---|---|
| MILE-0002 | <本里程碑标题> | active | YYYY-MM-DD | — | ITER-0004, ITER-0005 | — |
| MILE-0001 | <上一里程碑标题> | closed | YYYY-MM-DD | YYYY-MM-DD | ITER-0001~0003 | deliveries/milestones/MILE-0001-<slug>.md |
```

### 4.4 编写规则

- 台账只记结论性索引信息，不写里程碑内的过程细节（过程细节归 `.ai/MILESTONE.md` 拆分路线图与各迭代工作区）。
- 每次开启 / 收口 / 废弃里程碑，必须同步更新本表与 `current` 指针，二者不得不一致。
- 「含迭代」列在每个承接迭代开启时追加其迭代号，与 `.ai/ITERATIONS.md` 的「所属 milestone」列互为对账（见 `iteration-schema.md` §4.1）。
- 正式表的数字号必须从 `MILE-0001` 到当前最大号连续。`abandoned` 行仍保留在正式表，所以不会造成缺号；只有 §7.6 的最新未开工临时行可移除。
- 采用 state-ledger 后，本条“正式表”指热表与受管目录中全部固定区间冷分片的合并结果；有界 index 只保存路由公式，不逐片列目录。待办区始终只留在根 `.ai/MILESTONES.md`，不得移入冷分片。

### 4.5 待办区（未编号）

`.ai/MILESTONES.md` 在正式表后可按需包含待办区。老项目从未暂缓过里程碑时可没有本节；首次入库时一次性补上。

**候办块定义**：一个候办块只承载一个能够被用户**独立决定开工、独立提升为正式里程碑**的版本方向。一次讨论若同时出现多个这样的方向，必须先切成多个平级候办块，分别命名、分别落盘；不得用一份草稿里的多个二级标题混装。反之，同一版本方向内部的 R1/R2 路线项仍属于一个候办块，不因路线项多而误拆。

```md
## 待办区（未编号）

| 候办键 | 标题 | 暂缓日期 | 草稿 | 暂缓原因 |
|---|---|---|---|---|
| goal-cleanup | <候办标题> | YYYY-MM-DD | .ai/milestone-backlog/goal-cleanup.md | <一句话原因> |
```

- `候办键` 是稳定、可读的 kebab-case slug，不是新的数字时间线；不得使用 `MILE-NNNN` 或伪装成正式号。
- `草稿` 必须精确等于 `.ai/milestone-backlog/<候办键>.md`，路径不得越出该目录。
- **一方向一文件**：每个候办块必须恰好对应一个候办键、一行索引和一份 `.ai/milestone-backlog/<候办键>.md`；不同候办块禁止共用草稿，也不得在一个文件里声明多个候办键。
- 候办草稿沿用 §5 的四段结构，但顶部必须恰好标明一次 `候办键: <文件名 slug>` 和一次 `候办状态: deferred`，不写 `MILE-NNNN`。
- 候办项不是 `active / closed / abandoned` 中的任何一态，不参与 `current`、Goal 推导、迭代自动归属、版本收口或发布。

## 5. 里程碑工作区 `.ai/MILESTONE.md`

active 里程碑的活产物，承载下列四段。它是**方向性产物**：内容随推进演进，修改只需更新本文件并在「范围演进记录」追加一行，**不重新走 ACK**。

### 5.1 范围评估

- `In Scope（版本级）`：本大版本承诺交付的能力边界。
- `Out of Scope（版本级）`：本大版本显式不做的部分。
- `关键交付目标`：版本收口时必须达成的结果。

### 5.2 理解阐释

- 本里程碑要解决的核心问题。
- 背景与价值。
- 对系统的整体影响判断（涉及哪些模块、契约、关键路径的宏观研判）。

### 5.3 拆分路线图

把范围评估落成一串有序迭代，是里程碑承上启下的核心看板。

- 路线项按**主题切片**排序（`R1` / `R2`……），每项是"方向 → 一个迭代"的映射。
- **路线项扁平、原子**：一路线项 ≈ 一迭代，**不设子项**（`R1a` / `R1b`）。某路线项若大到值得再拆，即拆成两个**平级**路线项、编号顺延（原 `R1` → `R1` + `R2`，其后各项依次后移），而非在项内分子项。
- **开启时绑号**：迭代号单调递增、开启时才从台账分配，故路线项的「实际 ITER」列**留空，待该迭代开启时再绑定真实号**，不得预先占号。
- 段首可标「预计跨度 ITER-NNNN ~ ITER-NNNN」作方向性说明，但**真源以「实际 ITER」列 + 台账为准**，预计跨度与实际不符时以实际为准、不需校正预计值。
- 路线图**规划性、非冻结**：增删改顺序只更新本表并在 §5.4 追加一行，无需 ACK。

模板：

```md
## 拆分路线图

预计跨度：ITER-0002 ~ ITER-0005（4 个迭代承接）

| 路线项 | 主题 / 范围切片 | 实际 ITER | 状态 |
|---|---|---|---|
| R1 | <切片一> | ITER-0002 | closed |
| R2 | <切片二> | ITER-0003 | active |
| R3 | <切片三> | — | planned |
| R4 | <切片四> | — | planned |
```

- 路线项状态取值：`planned`（已规划未开启）、`active`（对应迭代进行中）、`closed`（对应迭代已收口）、`abandoned`（路线项取消或对应迭代废弃）。
- 路线项状态必须与台账中该迭代的实际状态对账，不得不一致。
- **与迭代状态消歧**：「路线项状态」是路线项自身的命名空间，**与迭代行状态不是同一字段**——迭代行状态是 `iteration-schema.md §4.2` 的封闭三态（`active`/`closed`/`abandoned`，无 `planned`）。`planned` 路线项的「实际 ITER」恒为 `—`、**不产生迭代台账行**；故 `planned` 不应出现在 `.ai/ITERATIONS.md`（部署项目由 `ledger_status` hook 机械拦截）。路线项绑定真实迭代号时，台账里那一行的状态走 §4.2 三态。
- **Decision Map 来源引用**：路线项仍必须先由本 Milestone 工作流显式创建。用户选定 resolved Decision slice 后，可用驻留 `tools/decision-promotion/` 的 `route-reference` 把它引用到当前 Milestone 中已存在、未绑定 ITER 的 planned route；该动作只写不可变 promotion receipt，不给本表加列、不镜像 Decision 状态，也不自动开启 Iteration。引用视图由工具扫描 receipts 派生；路线的创建、排序、取消和状态仍只由本文件拥有。
- **（PRD 派生里程碑专用）「相关模块」标注**：当里程碑由大 PRD 派生（§6.4 步 6），新路线项**可选**在主题后写完整锚点（如 `→ prd: 2026-07-22-signal-editor#save-validation, 2026-07-22-signal-editor#signal-list`），作为「里程碑方向 → references 细节」的唯一指针；路径解析为 `references/prd/<prd_id>/<module_slug>.md`。`module_slug` 只在所属需求内唯一，因此新指针不得省略 `prd_id`。**模块 ↔ 路线项映射以此处为单一真源**，单需求 `00_INDEX` 只回指里程碑号、不重列映射。旧的 slug-only 标注仅作历史兼容读取，不回写 closed 里程碑；非 PRD 里程碑无需标注。

### 5.4 范围演进记录

- 每次范围评估、理解阐释或拆分路线图发生方向性变化时，追加一行：`YYYY-MM-DD：<一句变更摘要>`。
- 这是里程碑"不冻结但可追溯"的依据，替代迭代侧的 ACK 修订记录。

## 6. 启动信号与时机

里程碑松耦合可选，不得为每个任务都开。AI 收到任务时跑一遍**启动信号清单**，命中任一即**主动提议**开里程碑，经用户 soft 对齐后开启；零命中则直接走独立迭代，不开里程碑。

### 6.1 启动信号（命中任一即提议开里程碑）

| 信号 | 判断依据 |
|---|---|
| 跨迭代体量 | 需求预计需 ≥ 2 个可独立交付的迭代才能闭环 |
| 版本主题 | 存在统一的版本主题，需要版本级范围评估与聚合交付 |
| 先评估后拆分 | 用户要求先整体圈定范围/方向，再拆分推进 |
| 显式里程碑 | 用户显式要求按里程碑 / 大版本组织 |

### 6.2 时机

- 在**第一个承接迭代进入 P1 之前**开里程碑：先写 `.ai/MILESTONE.md`（范围评估 + 理解阐释 + 拆分路线图）并向用户呈交对齐，再从台账领第一个迭代号进入 P1。
- soft 对齐是方向确认，**不是硬门**：用户认可方向即可推进，不要求逐条 ACK，里程碑随后仍可演进。
- 里程碑不是新阶段、不阻塞流程，迭代的 `P1 -> P5` 推进规则仍以 `lifecycle.md` 为准。

### 6.3 补开 / 回挂（例外路径）

- 若先开了独立迭代，推进中才发现它属于一个更大的版本，可显式开里程碑，并在 `.ai/MILESTONES.md`「含迭代」列与 `.ai/ITERATIONS.md`「所属 milestone」列把已有迭代回挂。
- 这是例外路径，不是常态；常态是里程碑先开、迭代后归属。

### 6.4 录入：里程碑意图书 (Brief)

里程碑的录入支持"一次性表达大版本意图，由模型合成概述"。用户把想推进的大版本想法**在一处说清**，模型据此生成 `.ai/MILESTONE.md`，省去边问边拼的零散对话。

**两条录入通道（等价，任选其一）**：

| 通道 | 用法 |
|---|---|
| 对话 | 用户在对话里直接讲清大版本意图（可配合 §6.5 的 `/milestone` 命令）。 |
| 文件 | 用户把原始概念文件投放到项目根 `origin/` 收件箱（自由格式、任意命名/数量），由模型读取。 |

**Brief 定位**：

- **可选、非权威、一次性输入**：brief 只是合成里程碑草稿的原材料，**不属 §3 候办/正式落盘结构、不归档、不跨里程碑纵向堆积**。
- `origin/` 文件由用户自管，AI **只读、不写不改不重塑不归档**（与 `.ai/references/` 的区分见 `mcv-deployment.md` §2）。
- 合成后的唯一详情真源随阶段切换：暂缓时是 `.ai/milestone-backlog/<slug>.md`，正式开启后是 `.ai/MILESTONE.md`。origin 文件用户可保留作溯源或自行清理，不影响里程碑产物。
- **若 brief 材料本身是大 PRD**（逐字权威规格）：它**同时喂两个海拔**——作 brief 合成 `.ai/MILESTONE.md` 路线图（方向层、有损压缩），并经 `40_Context_Management/prd-split.md` 派生 `.ai/references/prd/` 切片（细节层、逐字无损，见下 §6.4 合成协议步 6）。注意两者身份不同：`origin/` 里那份 PRD 仍是用户自管的**非权威原始输入**（AI 只读不归档、可清理）；`.ai/references/prd/` 切片才是 AI 派生、供 P2/P3/P5 引用对账的**权威投影**、独立生命周期跨迭代常驻——别把两者混为一谈（身份区分同 `40_Context_Management/references-schema.md §1`）。

**合成协议（brief → `.ai/MILESTONE.md`）**：

> **合成前必过 · PRD 分类闸（不可跳）**：收集到 brief 后、动手合成三段之前，**先判这份 brief 的内容是不是大 PRD**（逐字权威规格，判据回指 `40_Context_Management/references-schema.md §2`——大、结构化、逐字为准）。判**是** → 本次是"PRD 派生里程碑"，除合成路线图外还要经 `40_Context_Management/prd-split.md` 切 `.ai/references/prd/`（详见下方步 6 并进细则），切分方案与路线图方向**合并为一次呈交**确认；判**否** → 普通 brief，走常规合成到步 5 即止。**这道闸是必过判定、不是可跳的 opt-in 附录**——外部结构化文档（含经 MCP 直读的 Confluence / 需求平台 PRD）当 brief 时尤其不可略过：不判就合成，正是"MILESTONE 建了、`references/prd/` 没切"的漏切老毛病。判据只看**内容**是不是逐字权威规格，与 brief 从哪来（对话 / `origin/` / MCP）无关。

1. **收集输入**：读取对话意图，或 `origin/` 中用户指明的概念文件；多份未指明时汇总相关文件并回述确认范围，不擅自取舍。
2. **解析落三段**：把意图映射到 §5 的范围评估（In/Out Scope + 关键交付目标）、理解阐释（核心问题/背景价值/系统影响）、拆分路线图（按主题切片排序 R1/R2…）。
3. **缺口显式化**：brief 信息不足处，在相应段落显式标"待澄清"，**不臆造范围或目标**。
4. **拆分路线图沿用 §5.3 不预先占号**：路线项给主题切片 + 段首「预计跨度 ITER-NNNN ~ ITER-NNNN」，「实际 ITER」列**留空**待各迭代开启时绑真号。这是"拆分规划"而非"硬占全局号"，与 §5.3 一致。
5. **soft 对齐与开工分开**：产出后向用户呈交方向确认（**非硬门**，不要求逐条 ACK）。认可只表示“内容理解正确”，**不自动等于现在开工**：
   - 用户在本轮已明确说“开始/推进/开里程碑” → 按 §7.1 正式开启并领号。
   - 用户表示暂缓，或只是讨论而没有开工意图 → 按 §7.6 放入未编号待办区，不改 `current`。
6. **大 PRD 并进执行细则（承上方 PRD 分类闸判"是"时执行；判"否"则本步整体不适用）**：分类闸已判定 brief 是大 PRD，本步给出"怎么并进切分"的执行细则——在三段合成之外，**触发 `40_Context_Management/prd-split.md`** 把同一份 PRD 切成 `.ai/references/prd/` 知识文件夹（这就是"一份输入喂两个海拔"：方向层路线图 + 细节层切片）。要点：
   - **切分机制以 prd-split 为准、此处不复述**：边界识别、逐字保真、slug 分配、soft 对齐拆法全走 `prd-split §2–§6`，本步只负责"在里程碑录入点把它触发起来"。
   - **两次 soft 对齐合并成一次**：步 5 的路线图方向对齐，与 prd-split §6 的切分方案提议（模块清单 + slug + 边界），**并作一次呈交**给用户确认——不让用户先确认路线图、再确认切分分两轮点。
   - **落交叉指针**：把切分产出的 `<prd_id>#<module_slug>` 回填到 §5.3 路线图对应路线项的「相关模块」标注（方向→细节）；单需求 `<prd_id>/00_INDEX.md` 记所属里程碑号（细节→方向，见 `prd-split §6`）。
   - **非回归**：**非大 PRD 的普通 brief 到步 5 即止、不进本步**，合成路径与本分支完全无关、不受任何影响。

### 6.5 命令（轻量入口，与语义触发并存）

里程碑提供两个轻量命令作为显式入口糖；它们**触发的仍是既有生命周期，不新增阶段、不阻塞流程**，与 §6.1 信号语义触发**等价**。

| 命令 | 语义 |
|---|---|
| `/milestone`（可带意图文本或指向 `origin/` 文件） | 录入/开启里程碑：按 §6.1 判定、按 §6.4 合成；只有指令或上下文已明确要“现在推进”才按 §7.1 领号，否则按 §7.6 进未编号待办区。 |
| `/milestone start <候办键>` | 从待办区提升：读指定草稿，确认无 active 里程碑后按 §7.1 领号，再原子移除待办索引与草稿。 |
| `/milestone status` | **只读看板**：汇报当前正式里程碑的范围/路线/迭代进度，并附待办区标题、暂缓日期与原因；**不写任何文件、不改状态**。 |

- 命令面覆盖最高频的录入 / 候办提升 / status；**收口、废弃、演进与误开退回仍走语义**（§7.3–§7.6），不另加命令。
- 命令是可选糖：不输命令、直接用自然语言表达同样生效。

## 7. 里程碑生命周期

### 7.1 开启 / 候办提升 (Open / Promote)

- 时机：命中 §6.1 启动信号、准备启动一个大版本时。
- 动作：从正式表领下一个 `MILE-NNNN`，写入台账并置 `active`、`current` 指向它；将已对齐内容写入 `.ai/MILESTONE.md`。若来源是待办草稿，则在正式表、`current` 和工作区都写成功后，同一次变更中删除对应待办行与草稿；任一步失败都不得留下半提升状态。
- **overwrite-only（硬约束）**：开启新里程碑时，`.ai/MILESTONE.md` 必须以本里程碑内容**整体覆写**，严禁保留或追加上一里程碑内容；上一里程碑的产物只在收口时归档的 `milestones/MILE-NNNN/` 中存续。
- 上一里程碑若已收口，`current` 应为 `none`；开启即把 `current` 指向新号。若上一里程碑未收口就要开新里程碑，先按 §7.4 / §7.5 处理旧里程碑，不得跳过。

### 7.2 推进 (Advance)

- 里程碑处于 `active` 期间开启的每个迭代**一律自动归属**之（无需逐次征求确认）。每开一个承接迭代：① 在该迭代的 `.ai/ITERATIONS.md` 行「所属 milestone」列填 `current` 里程碑号；② 在 `.ai/MILESTONES.md`「含迭代」列追加其号；③ 把它绑定到 `.ai/MILESTONE.md` 拆分路线图对应路线项的「实际 ITER」列。归属判定只认台账 `current`：`current = 本里程碑号` 即归属。
- 每个承接迭代各自走完整 `P1 -> P5` 并各自收口、各自交付（小版本交付落在 `deliveries/ITER-NNNN-<slug>.md`），迭代收口纪律以 `iteration-schema.md` §5 为准。

### 7.3 演进 (Evolve)

- 适用：里程碑范围、理解或拆分路线图发生方向性变化。
- 动作：更新 `.ai/MILESTONE.md` 相应段，并在 §5.4 范围演进记录追加一行。**无需 ACK、无需另开里程碑**。
- 与迭代的关系：里程碑范围演进不直接松动已冻结迭代的验收范围；某个迭代自身的修订/扩张仍按 `iteration-schema.md` §5 处理。

### 7.4 收口 (Close)

- 时机：版本范围达成、其下迭代均已 `closed`（或显式 `abandoned`）、确认大版本可交付时。
- 动作（三步必做、缺一不可）：
  1. 把 `.ai/MILESTONE.md` 快照复制到 `.ai/milestones/MILE-NNNN/MILESTONE.md`。
  2. 生成版本级交付总结 `deliveries/milestones/MILE-NNNN-<slug>.md`，聚合其下各迭代交付，并按 `delivery-summary.md` §9 用固定模板填槽并列产出同名 `deliveries/milestones/MILE-NNNN-<slug>.html` 阅读视图（含里程碑专用「拆分路线图回填」段）；结构与触发参考 `delivery-summary.md`（聚合口径见其 §4.8）；`.md` 与 `.html` 均**只链接各迭代交付路径与里程碑产物路径，不得全文嵌入**（见 `delivery-summary.md §4.7` 与本规范 §9）。
  3. 台账该行置 `closed`、填收口日期与交付链接，`current` 置 `none`。
- 版本级整体验收：收口前必须确认拆分路线图各路线项均 `closed`/`abandoned`、其下迭代验收闭环；存在 `planned`/`active` 路线项时不得收口（除非显式废弃该路线项）。
- 完成归档、交付与台账后，运行 `$BUTLER/scripts/audit-project-state.py --project-root "$PROJECT_ROOT"`；Butler 规则仓处于提交/发布前时可加 `--allow-unreleased`，但必须保留 `UNRELEASED` 亮牌；后续切版仍按 `versioning-schema.md` 在干净工作树无豁免复核。确定性漂移未清零不得宣告里程碑收口。
- **收口后归属边界**：`current` 置 `none` 后，再开启的迭代**不再自动归属本（已收口）里程碑**、不回写其「含迭代」与路线图，按独立迭代处理；已收口里程碑不接收新迭代、不被回挂。若新迭代属于另一个大版本，按 §7.1 另开里程碑或 §6.3 回挂到另一个 `active` 里程碑。

### 7.5 废弃 (Abandon)

- 时机：里程碑中途确认方向推翻、不再继续。
- 动作：台账该行置 `abandoned` 并备注原因，`current` 置 `none`；已收口的承接迭代交付保留原位，不回收。可选择是否快照归档（若有复盘价值则归档）。

### 7.6 暂缓入库 / 开启前退回 (Defer / Withdraw Before Work)

**普通暂缓**（尚未正式开启）：

1. 先按 §4.5 判断输入含几个可独立启动的方向；有 N 个方向就切成 N 个平级候办块，不把多个方向揉成一份草稿。
2. 为每个方向分别选一个稳定 kebab-case `候办键`，不含 `MILE-NNNN`。
3. 每块各自把已合成的 §5 内容写入 `.ai/milestone-backlog/<候办键>.md`，顶部标明唯一候办键和 `候办状态: deferred`。
4. 每块在 `.ai/MILESTONES.md` 待办区各追加一行索引。若台账尚不存在，创建 `current: none` + 空正式表 + 待办区。
5. 不写 `.ai/MILESTONE.md`，不改 `current`，不产生 Goal 或迭代归属；各块后续可被分别修改、删除或按键提升。

**误开后退回**（已有 active 正式行）只有同时满足下列条件才允许：

- 它是正式表最大号，删掉后不会留下中间缺号。
- 「含迭代」为 `—`，且 `.ai/ITERATIONS.md` 没有任何行的「所属 milestone」指向它。
- `.ai/milestones/MILE-NNNN/` 不存在，交付列为 `—`，`deliveries/milestones/` 也没有它的交付。

通过后，先把 `.ai/MILESTONE.md` 写入候办草稿并补索引，再从正式表删除临时行、置 `current: none`，最后删除 `.ai/MILESTONE.md` 活工作区。任一预检不通过，都不得回收号码，改走 §7.4/§7.5。

## 8. 与迭代 / 执行流程的关系

- 里程碑不是新阶段，而是套在"迭代（套在 `P1 -> P5` 外）"之外再外一层的版本范围单元；阶段推进规则仍以 `lifecycle.md` 为准，迭代锁定纪律仍以 `iteration-schema.md` 为准。
- 未编号候办项尚不是里程碑；不得为它派生 Goal、自动归属迭代或参与版本完成裁决。
- 里程碑层**不被 hook 机械拦截**：phase_gate 仅校验迭代工作区四件套，里程碑保持松耦合、可选、方向性。
- `.ai/ITERATIONS.md`「所属 milestone」列与本规范的 `.ai/MILESTONES.md`「含迭代」列互为对账，两者真源各管一侧、不得不一致。
- 全量迭代时间线的真源是 ITER 热表 + state index + 固定区间冷分片的复合台账；单调递增号与「所属 milestone」列共同给出时间线和版本归组。根 `.ai/ITERATIONS.md` 只是有界热视图。

## 9. 交付文档结构

`deliveries/` 同时承载迭代交付与里程碑交付，布局如下：

```txt
deliveries/
  ITER-0001-<slug>.md          # 迭代交付（小版本），平铺按号即时间线
  ITER-0002-<slug>.md
  ...
  ITER-0006-<slug>.md          # 独立迭代（无里程碑）同列时间线
  milestones/
    MILE-0001-<slug>.md        # 里程碑交付（大版本），链其下各迭代交付
    MILE-0002-<slug>.md
```

- 每份交付（迭代级与里程碑级）都另有一份**同目录、同 slug、仅扩展名为 `.html`** 的固定格式阅读视图（如 `ITER-0001-<slug>.html`、`milestones/MILE-0001-<slug>.html`）；`.md` 为引用真源，`.html` 生成协议见 `delivery-summary.md` §9。上图省略 `.html` 兄弟文件以保持时间线清晰。
- 迭代交付平铺在 `deliveries/` 根，无论是否归属里程碑都不移动，保证迭代历史在文件树中是一条连续时间线。
- 里程碑交付集中在 `deliveries/milestones/`，不污染迭代时间线。
- 版本级交付的结构、聚合口径与对话层风格以 `delivery-summary.md` 为准。
