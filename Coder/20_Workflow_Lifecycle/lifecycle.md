# Workflow Lifecycle

## 1. 目标

所有非极小任务默认走**验收导向流程**，而不是直接进入编码。

核心原则：

- 先对齐问题理解。
- 再对齐完成定义。
- 再确认技术方案。
- 最后进入实现与验证。

## 2. 状态机

默认流程如下：

`P1 Analysis -> P2 Acceptance -> P3 Design -> P4 Execute -> P5 Verify`

### P1 Analysis

交付物：`CONCEPT.md` 风格的问题理解说明。

AI 必须回答：

- 我对目标、约束、影响范围的理解是否完整？
- 目前有哪些显性约束和隐性约束？
- 是否存在需要先澄清的问题？

若任务属于新项目接入、显式要求部署基地车，或需要建立跨会话维护设施，应在 P1 同步参考 `mcv-deployment.md` 完成侦察与部署判断。

### P2 Acceptance

交付物：`AC_LIST.md` 风格的验收清单。

AI 必须回答：

- 如果以下条目全部勾选，任务是否可视为完成？
- 每条验收项要如何验证？

强制规则：

- **必须等待用户 ACK，才能进入 P3。**
- 长任务或多子任务场景下，P2 结束后应形成一次阶段 checkpoint，明确当前 AC、验证映射与下一步入口。

### P3 Design

交付物：`TECH_PLAN.md` 风格的技术方案。

AI 必须回答：

- 我打算改哪些模块或文件？
- 接口契约、状态边界、扩展点分别是什么？
- 我会如何验证这些改动？

强制规则：

- **必须等待用户 ACK，才能进入 P4。**
- 若任务链路较长，应在 P3 结束时明确子任务拆分、handoff 方式与状态同步策略。

### P4 Execute

交付物：代码、配置或文档实现。

执行原则：

- 实现必须能映射回已确认的验收项。
- 不得在执行阶段偷偷扩张范围。
- 若影响面变化，应回到 P3。
- 若本阶段涉及 `.ai/` 维护文件写入，应遵守 `maintenance-boundaries.md` 中定义的触发阈值与批处理策略。

### P5 Verify

交付物：验证结果与剩余风险说明。

AI 必须回答：

- 哪些验收项已满足？
- 每项是如何验证的？
- 是否还存在未关闭风险？

长任务在 P5 结束后，应补充 checkpoint 或 handoff summary，确保验证结论可直接被下一阶段继承。
若生成 `SESSION_HANDOFF.md`，其内容结构应符合 `40_Context_Management/handoff-spec.md`。

## 3. 强制回退规则

出现以下情况时，必须回退流程：

- 目标理解变化：回到 P1。
- 验收标准变化：回到 P2。
- 设计影响面扩大：回到 P3。
- 新业务扩展文档出现：重新执行 Context Discovery，并至少回看 P1 / P2。

## 4. 极小任务例外

对极小、低风险、影响范围明确的任务，可合并 `P1 + P2`。

但即使合并，也不能跳过：

- 目标理解
- 完成定义
- 验证方式

## 5. 研发与扩展原则

- 一次改动只解决一个明确问题。
- 先分边界，再写代码。
- 先定契约，再做扩展。
- 先保语义，再谈复用。
- 先本地验证，再进入交付。
- 长任务应子任务化推进，并为每个阶段保留可交接结论。
