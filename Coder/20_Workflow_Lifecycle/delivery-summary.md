# Delivery Summary

## 1. 目标

用于在一次开发已经完成并可交付时，生成一份给人看的交付总结，让读者快速理解：这次交付解决了什么、做了哪些改动、如何验证、还剩哪些风险。

它服务于人类回看、交付确认与归档，而不是 AI 的运行态续接。

## 2. 触发时机

仅在以下条件同时满足时生成：

- 当前任务已经完成主要目标
- 验收项已经达到可验收状态
- 已有明确验证结论
- 本轮输出已经形成可交付闭环

以下场景不生成：

- 中途暂停
- 等待用户 ACK
- 等待外部结果
- 只是形成阶段 checkpoint
- 只是为了跨会话恢复状态

上述场景继续使用 checkpoint、handoff 或 `.ai/` 维护文件。

## 3. 存放位置与命名

- 存放位置：项目根目录 `deliveries/`
- 命名建议：`deliveries/ITER-NNNN-<task-slug>.md`（迭代收口时，迭代号取自 `.ai/ITERATIONS.md`）
- 未开迭代号的简化路径任务，可沿用 `deliveries/YYYY-MM-DD-<task-slug>.md`

`deliveries/` 用于归档已经完成的、人类可阅读的交付总结，不放运行态状态文件。一份 Delivery Summary 对应一次迭代收口，迭代号与归档机制以 `iteration-schema.md` 为准。

## 4. 最小结构

每份 Delivery Summary 至少应包含以下内容：

### 4.1 本次交付目标
- 这次交付要解决什么问题
- 对应的业务目标或工程目标

### 4.2 已完成内容
- 本次已经落地的功能、规则、修复或结构调整
- 只写最终完成项，不写中间尝试

### 4.3 关键变更 / 用户可感知变化
- 使用者、调用方或维护者会感知到什么变化
- 若是规则系统或基础设施调整，说明行为口径变化

### 4.4 高层影响范围
- 涉及的模块、目录、文件或流程
- 用高层描述说明影响面，不要求复制实现细节

### 4.5 验证方式与结果摘要
- 使用了哪些验证动作
- 每类验证的结论是什么
- 结论应能映射回已确认 AC 或验证报告

### 4.6 已知剩余风险 / 延后事项
- 当前仍未关闭的风险
- 明确延后处理的事项
- 不得把未完成项伪装成已完成

### 4.7 可选引用
可按需引用：

- `AC_LIST.md`
- `TECH_PLAN.md`
- `VERIFY_REPORT.md`
- 相关 PR / commit
- 其他最终交付所需链接

## 5. 非目标与边界

Delivery Summary 不负责以下内容：

- 不记录唤醒指令
- 不记录环境脏点
- 不记录上下文断点
- 不复制大段终端日志
- 不替代 checkpoint
- 不替代 `02_SESSION_HANDOFF.md`
- 不替代 `.ai/CHANGELOG.md`、`BUG_LOG.md` 等运行态维护文件

边界原则：

- `.ai/` 负责 AI 维护、决策链、问题沉淀与续接状态
- checkpoint / handoff 负责阶段快照与跨会话恢复
- Delivery Summary 只负责完整交付后的对人总结

## 6. 编写原则

- 优先写结果与影响，而不是流水账过程
- 内容应让未参与本轮实现的人也能快速看懂
- 对验证与风险要显式说明，不能只写“已完成”
- 若交付尚未闭环，应先补足验证或保持在 checkpoint / handoff 层，不提前生成 Delivery Summary

## 7. 与执行流程的关系

- 生命周期阶段仍保持 `P1 Analysis -> P2 Acceptance -> P3 Design -> P4 Execute -> P5 Verify`
- Delivery Summary 不是新阶段，只是 P5 完整交付后的收尾产物
- `VERIFY_REPORT.md` 继续作为验证真源
- Delivery Summary 应基于已确认的 AC、方案与验证结论进行人类可读汇总
- 生成 Delivery Summary 是迭代收口三步之一（快照归档 + 交付总结 + 更新台账），三步以 `iteration-schema.md` §5.5 为准；只交付总结而不归档、不更新台账，视为收口不完整

## 8. 对话内人话摘要

### 8.1 触发

与 §2 相同时机。若不满足 §2 触发条件（中途暂停、等待 ACK、等待外部结果、只是 checkpoint、只是跨会话恢复），也不生成本节规定的对话摘要，继续使用 checkpoint / handoff 口径。

### 8.2 形式

- 必须是 3–6 句中文散文。
- 禁止输出任何编号小节标题，不得复述 §4 的 4.1 / 4.2 结构。
- 禁止铺排长 bullet 清单；若非用 bullet 不可，至多 2 条，且每条不得超过 1 句。
- 措辞应口语化、可带判断词（如"基本没风险"、"建议下一步"），避免"已完成 / 已交付 / 已闭环"等模版套话单独出现。

### 8.3 内容核心

每段对话摘要必须同时覆盖以下三项，缺一不可：

1. **做了什么**：用户视角的最终结果，一句话说清。
2. **有没有风险 / 延后事项**：有就明说有；没有必须显式声明"本轮无剩余风险"，不得用"一切顺利"、"已完成"、"已闭环"等模糊套话替代。
3. **建议下一步**：例如"交付即止"、"需要你 ACK"、"建议后续迭代 X"。

### 8.4 收尾引用

对话摘要最后必须单独一行，按以下固定格式引用正式版文件：

```
正式版：deliveries/ITER-NNNN-<slug>.md
```

路径应指向本轮实际写入的 Delivery Summary 文件，不得省略、不得改写格式。未开迭代号的简化任务沿用 `deliveries/YYYY-MM-DD-<slug>.md`。

### 8.5 与 §4 的关系

- §4 定义 `deliveries/` 文件的书面结构（文件层）。
- §8 定义对话框内的收尾表达（对话层）。
- 两者同源、同触发，但风格分层：文件正式、对话口语。
- 不得用文件结构覆盖对话风格，也不得用对话口吻替代文件结构。
- 结论真源以 `deliveries/` 文件为准，对话摘要只是其口语化投影。
