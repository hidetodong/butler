# Artifact Style

## 1. 目标与定位

- 本口径管**所有面向人的落地文档**怎么写：讲人话、不啰嗦。**面向人的落地文档**＝会有人读、会被复盘的产物——四件套（`CONCEPT` / `AC_LIST` / `TECH_PLAN` / `VERIFY_REPORT`）、交付总结正文、`.ai/project/` 知识文件夹、`02_SESSION_HANDOFF` 等；四件套是其中最常写的一类，不再是唯一。
- 其中 `§2`「说人话三条硬标准」是**跨对话与文档的通则**、本口径是它的单一真源；对话层（`00_System_Prompt/presentation-protocol.md`）引用同守，不另写一份。`§3` 起的反啰嗦 / 分层则针对落地文档层。
- 本口径与**字段结构**各管各的：**不得**增删或改动任何字段（四件套字段以四个 schema 为准），只约束往字段 / 文档里写的内容。
- 为什么需要：这些文档首先是给 AI 续接用的，但人也会读、会复盘。没有书写纪律时，正文会越积越多内部黑话、把一件事重述好几遍，读起来像机器日志、不像给人看的东西——这正是迭代化本想消除的"产物膨胀"在内容层的翻版。
- 三层分工：`presentation-protocol.md` 管对话框里把方案说清楚（对话层）、`delivery-summary.md §8` 管 P5 交付摘要的散文口吻、**本口径管落地文档层**。三者分层、互不覆盖；说人话三条则贯穿三层（真源在本口径 `§2`）。

## 2. 说人话三条硬标准（跨对话与文档的通则）

面向人的输出都要过这三条——对话层由 `00_System_Prompt/presentation-protocol.md` 引用同守，落地文档层（本口径）直接管。三条是"**简短≠好懂**"的解药：把话砍短之后，还得让不在你脑子里的人也接得住。本节是三条的**单一真源**，别处引用、不另写一份。

### 标准一 · 术语先解释

- 术语 / 内部黑话 / 承重符号第一次出现，**必须**顺带一句话说清它是什么，不靠读者自己懂。
- 判据——**这个词是在指代任务的真实对象，还是只是偷懒的简写？**
  - 是真实对象（这次任务改的就是它，如 `schema`、`rule-card`、`ack-frozen`）：**应**照常用它的名字，但加一句话解释。
  - 只是简写（一个大白话词就能替代）：**必须**换成大白话。典型反面词（不限于）：`零改动护栏`、`护栏`、`正交`、`高注意力区`、`BLUF`、`fresh-context 子 agent`。
- 结构锚点不算黑话、必须保留：字段名（`Goal` / `AC Status`…）、AC 编号、文件路径——跨阶段读取的锚点，不是给人读的散文。
- 渐进展开层的对应做法（承重引用首次出现给一句话解释）见 `§4.3`，两处是同一件事，别重复写。

### 标准二 · 比喻要落地

- 用比喻 / 类比帮读者理解时，比喻**必须落到具体对象**：说"像 X 的 Y"，就得点明这里的 X 到底对应本任务里的谁。
- **不得**抛一个悬空比喻让读者自己接。比喻是帮人过河的**脚手架**、不是装饰——搭不到对岸（接不回真实对象）就删掉、直说。

### 标准三 · 别让英文 / 变量裸奔

- 英文术语、变量名、函数名、表名第一次出现**不得裸奔**——要么中文解释在旁，要么一句话点明它在本项目里是什么。不止 butler 黑话，也含**项目领域**的符号（如 `getCaptureText`、`captures` 表）；别假设读者脑子里已装着代码。
- 结构锚点（字段名 / AC 编号 / 路径）本就是锚点，保留不算裸奔。

## 3. 反啰嗦（反注水）

- **必须**一律用 bullet，不写大段铺陈；一条能说清的就一条，一句能说清的就一句。
- 嵌套**不得**超过 2 层。
- **不得**复述模板里的提示语（如把 `# Goal 本次任务要解决什么问题` 原样抄进正文），也**不得**把上一阶段产物已写过的内容再抄一遍——引用即可（如"目标见 CONCEPT，不重述"）。
- 宁缺毋滥：某字段本轮没有内容，写"无"或"N/A"，**不得**为凑字数硬编。
- 分流行的升级信号**只列名**（如"多文件改动、设计取舍"），**不得**给每条加括号小作文。
- VERIFY 的 AC 回填用紧凑式 `[x] ACn ✓ <一句话证据>`，**不得**把 AC 原文整条重抄再展开成一段。

## 4. 渐进展开与分层（同时对人和 AI 友好）

「对人友好」和「对 AI 友好」不是取舍、是同一件事：让人读着累的（信息糊成一团、关系藏着不挑明、引用默认你懂），同样让 AI 干得不稳。唯一偏差是 AI 比人更需要精确引用（路径 / 符号 / payload）——用分层吸收掉，不靠删精度来讨好人。

把产物当**一份文档、多种阅读深度**来写：

1. **顶部先放一句话意图（gist）**：用 2-3 句白话说清"干嘛 + 为什么"，让冷读者（人或 fresh-context 的 AI）先抓住意图再看细节。**不得**让读者自己从背景 + 标题 + 一堆目标里拼意图。
2. **一行一个意思**：**不得**把多步 / 多约束用箭头链（`A → B → C`）或括号串塞进一行；多步就列成有序步骤，每步一个干净锚点。
3. **承重引用首次出现给一句话解释**：被反复指代的关键符号 / 文件 / 表，第一次出现时一句话说清它是什么——不止 butler 黑话，也含**项目领域**的（如 `getCaptureText`、`captures` 表）；别假设读者脑子里已装着代码。
4. **不串层**：散文层就纯散文（**不**夹密集符号），精度层就用干净引用列表（路径 / 符号 / payload 各占一行）。串在一起两头不讨好——精度打断叙述、关系又藏进密集行里。
5. **不啰嗦 ≠ 极限压缩**：§3 的"反啰嗦"针对**填充与重述**，不是让你把关系压没、把台阶撤掉。该展开的关系要展开、该铺的 gist 要铺；省的是冗余，不是确定性。

分层骨架样例（CONCEPT，可照抄）：

```md
> 分流: 完整 | 命中升级信号: 多文件改动、契约变更 | YYYY-MM-DD

# 一句话
把 X 和 Y 彻底解耦：以前 X 要跨进去用 someFn 读数据，现在改成 Y 建任务时
就把数据写进任务里、X 只读任务。顺手删掉已搬走、现在没用的旧代码。

# Goal
- G1 …（一行一个意思）
- G2 …

# 影响范围（执行依据，精度单独成层）
- 改 tools/x/src/db.ts：删 someFn
- Payload: {a, b} → {a, b, data}
```

反例（别这样）：把 `重建镜像 → 服务器 pull → 切换（守单消费者 + --remove-orphans）→ 端到端验证等价` 全塞进一行——人看着累、AI 执行到中间没干净锚点；应拆成有序步骤。

## 5. Execution Steps 任务清单书写

`TECH_PLAN.md` 的 `Execution Steps` 字段在完整路径下写成可勾选任务清单（字段结构见 `tech-plan-schema.md`，本节只管怎么写）：

- **一行一任务**：每条一个可独立执行的动作，动词开头（"改 X" / "加 Y" / "删 Z"），不把多步塞进一行。
- **绑 AC**：每条结尾标它服务的验收项（`→ ACn`），让计划态任务能回溯到验收脊柱；一条服务多 AC 就都列上。
- **标记克制**：依赖只在确有先后时标（"依赖 T<m>"）、可并行只在确能并行时标 `[P]`；没有就不标，不为形式凑标记。
- **编号可选**：任务编号 `T<n>` 便于 `task-state.md` 精确引用，建议给但不强制——小迭代可省。
- **不过度拆分**：粒度随迭代大小，小 / 简化迭代保持粗粒度实现顺序即可，别把三行能说清的拆成十条任务；过度拆分与注水同样是产物膨胀。
- **计划态不反复改勾**：任务清单是计划态单一存放处，P4 的活进度（已完成 / 进行中 / 下一条）镜像到 `task-state.md`（见 `40_Context_Management/context-persistence.md §4`），不在 TECH_PLAN 里反复改这些勾选框。

## 6. before / after 对照（可照抄）

取自本仓真实历史产物，左边啰嗦 / 黑话，右边讲人话。

分流行（CONCEPT 顶部）——只列名，不加括号小作文：

```md
before
> 分流: 完整 | 命中升级信号: 契约变更（新增对话层呈现行为契约，贯穿各阶段输出）、跨模块影响（影响 P1-P3 所有方案输出 + 须与 §8 划清边界）、多文件改动（≥5）、设计取舍（落点：新建文件 vs 扩 identity） | 2026-06-22

after
> 分流: 完整 | 命中升级信号: 契约变更、跨模块影响、多文件改动、设计取舍 | 2026-06-22
```

AC 回填（VERIFY）——紧凑式，黑话换大白话：

```md
before
- [x] AC17: 零改动护栏——git status 改动名单不含 VERSION/CHANGELOG/四 schema/hooks/…；上述文件 git diff --stat 零行变更。

after
- [x] AC17 ✓ 不该动的文件确实都没碰（版本号、改动记录、四件套模板等逐个核对过）。
```

## 7. 边界

- 不改字段结构——四件套字段以四个 schema 为准。
- 不管对话层的**呈现结构**（结论先行 / 标号 / 表格）——那以 `presentation-protocol.md` 为准；交付摘要的散文口吻以 `delivery-summary.md §8` 为准。**例外**：`§2` 说人话三条是跨对话与文档的通则、真源在本口径，`presentation-protocol` 引用它、不另写。
- 书写质量不做 hook 机械门禁——它不是封闭枚举那种可机械校验的项，靠本规则 + 收口前自检兜底。

## 8. 发长文 / 收口前自检

发任何面向人的长文档前（收口四件套、交付总结、知识文件夹折叠、handoff……），**应**扫一遍：

- **说人话三条**（`§2`）逐条过：术语有没有先解释、比喻有没有落地、英文 / 变量有没有裸奔；命中 `§2` 标准一的反面词一并换掉。
- **反啰嗦 / 分层**（`§3`）：有没有整段重述、超 2 层嵌套、把多步塞进一行。
- 命中就地改掉再发 / 再归档，不留到读者踩坑。
