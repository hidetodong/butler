# Vue 3 Profile

## 1. 适用条件

- 仅在当前项目明确使用 Vue 3 时启用。
- 未命中 Vue 3 技术栈时，不应将本文件内容视为默认通用约束。

## 2. 基线

- 默认使用 Vue 3。
- 默认使用 Composition API + `<script setup lang="ts">`。
- 组合式逻辑优先沉淀到 `composables`。
- 组件只负责 props、emits、局部交互状态与模板渲染。

## 3. 组件契约

### 3.1 推荐写法

- 使用 `defineProps` / `defineEmits` 明确输入输出边界。
- props 类型应显式、稳定、可推导。
- emits 应表达清晰的业务动作，而不是暴露内部实现细节。
- 优先保持“父组件组织数据，子组件表达界面”的单向数据流。

### 3.2 不推荐写法

- 直接修改 props。
- 用一个组件同时承担数据获取、状态编排、领域判断和视图渲染。
- 用大量布尔开关堆出难以理解的组件模式。
- 把外部接口的原始返回结果直接暴露给模板。

## 4. 响应式与状态规则

### 4.1 响应式选择

- `ref` 用于单值或局部可变状态。
- `reactive` 用于稳定对象结构。
- `computed` 用于派生状态，不要把派生结果反复手动同步到别处。
- `watch` 只用于副作用，不用于替代正常的数据建模。

### 4.2 watch 使用约束

- 不要在 `watch` 中串联过多副作用。
- 不要用深层监听兜底所有状态变化。
- 如果逻辑本质是“根据输入推导输出”，优先改成 `computed`。
- 如果逻辑本质是“状态变化后触发外部动作”，才使用 `watch`。

### 4.3 状态分层

#### 临时视图态

例如：

- 当前 hover 的节点
- 当前选中的元素
- 面板展开折叠状态

这类状态应放在组件局部或 composable 中。

#### 页面级编辑态

例如：

- 当前选中的业务对象
- 当前工作区缩放级别
- 编辑中的草稿数据

这类状态应放在页面级 store 中统一维护。

#### 领域持久态

例如：

- 核心业务实体
- 实体之间的关系定义
- 规则配置与校验结果
- 可提交或可发布的数据模型

这类状态应进入领域模型层，不应仅存在于 UI 状态里。

## 5. Composable 规则

- composable 命名使用 `useXxx`。
- composable 应暴露稳定、最小化的返回接口。
- UI 交互型 composable 与领域规则型 composable 应分开。
- composable 可以封装副作用，但副作用边界必须清晰。
- 不要把一次性页面逻辑抽成伪复用 composable。

## 6. 模板与渲染规则

- 模板只保留展示所需的最小表达式。
- 复杂判断应上移到 `computed` 或脚本逻辑中。
- 避免在模板中堆叠大段三元表达式或多层条件分支。
- 列表渲染必须使用稳定 key，不依赖易变索引兜底。
- 样式切换、显隐切换、禁用态应有明确状态来源。

## 7. 分层与职责

- 展示组件：只关心输入和渲染。
- 容器组件：负责状态编排与事件协调。
- 页面组件：负责路由级组合、数据入口和权限/上下文接入。
- Domain Sync 层：负责把 UI 行为转换成领域动作或数据更新。

复杂系统建议拆为：

- Workspace 层
- Inspector 层
- Toolbar 层
- Domain Sync 层

## 8. 异步与数据访问

- 数据获取优先放在页面层、容器层或 composable 中。
- 服务调用通过 `services/` 或适配层统一管理。
- 组件内可以处理小范围 UI 异步，但不要把接口编排散落到各个展示组件里。
- 加载态、空态、错误态应是明确状态，而不是临时拼凑条件。

## 9. 反模式清单

- 在单个 SFC 中堆积大量业务判断。
- 用 `ref<Record<string, any>>` 承载核心领域状态。
- 用模板事件直接驱动复杂领域逻辑。
- 在多个兄弟组件之间隐式复制同一份状态。
- 通过临时变量和 watcher 维持本可由模型表达的数据关系。

## 10. 与业务规则协作

技术实现必须给业务语义让路：

- 先保证“数据关系正确”，再优化交互动画。
- 先保证“类型可推断”，再压缩代码行数。
- 先保证“规则可测试”，再追求极致封装。
- 先保证“状态边界清晰”，再讨论复用颗粒度。
