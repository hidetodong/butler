# MILESTONE — MILE-0013 · 项目级 Butler 配置结构化

> 方向性产物（非冻结、不走 ACK）。把 Butler 需要稳定读写的项目级设置从 `.ai/local-constraints.md` 拆到 `.ai/butler.config.json`；第一版保持顶层扁平，不建设包罗万象的总配置中心。

## 5.1 范围评估

**In Scope（版本级）**

- 新增 `.ai/butler.config.json`，作为项目级 Butler 机器配置的唯一真源。
- 第一版采用顶层扁平结构：`schema_version`、`dangerous`、`independent_review`、`preference`、`profiles`，不增加 `features`、`settings` 等中间分组。
- 为配置提供明确的字段类型、默认值、未知字段、缺字段和非法值处理规则，并确保危险模式配置异常时不会误开自治。
- `.ai/local-constraints.md` 回归人类可读职责，只保留项目类型、本地约束、范围例外和外部资料指针等需要解释原因的内容。
- 新部署直接生成配置文件；旧项目升级时从 `local-constraints.md` 无损迁移现有开关与 Active Profiles。
- 兼容期内支持旧 Markdown 回退读取；新 JSON 存在时以它为真源，冲突必须显式报告，不做长期双写。
- 更新危险模式、独立复核、偏好探针、进度查询、双宿主入口、部署升级与相关文档测试的读取和回写位置。

**Out of Scope（版本级）**

- 不把当前迭代、任务阶段、授权上限、handoff 或运行日志搬进配置文件。
- 不把跨项目偏好 consent、signals 或 profile 数据从外置 `$BUTLER_PREF` 搬回项目。
- 不把 Local Constraints、Scope Exceptions 等自然语言规则强行结构化为 JSON。
- 不在第一版引入嵌套领域配置、插件注册、环境覆盖、用户级配置继承或通用配置合并算法。
- 不把目标项目自己的业务配置、构建配置或宿主私有权限设置纳入 Butler 配置。
- 不在本里程碑删除 legacy Markdown 回退；彻底移除兼容读取留给后续破坏性版本评估。

**关键交付目标**

- Butler 的机器配置不再依赖模型从 Markdown 段落中提取和改写值。
- 配置结构足够小且含义直接，用户可以安全手改，工具可以确定性校验和迁移。
- 旧项目升级后保持原行为，尤其现有 `dangerous: on` 不得被默认值覆盖或静默关闭。
- 新旧入口、命令和工具共享同一份读取语义，不各自实现一套解析规则。
- 完整 CI 与迁移负向测试证明无配置、旧配置、合法新配置、冲突和损坏配置均有明确结果。

## 5.2 理解阐释

当前 `.ai/local-constraints.md` 同时承担两类职责：一类是需要人解释的项目规则差异，另一类是 Butler 要跨会话稳定读取和自动回写的布尔开关。Markdown 适合表达原因和例外，却不适合作为越来越多工具共同依赖的机器配置接口；继续混用会让解析、迁移、冲突检测和 schema 演进都依赖散文格式。

本里程碑只切开这条边界：机器设置进入扁平 JSON，本地约束继续留在 Markdown，任务运行状态仍由既有台账负责。选择 JSON 是为了让目标项目无需额外解析依赖，并能使用标准工具做严格校验；选择顶层扁平结构，是因为第一版字段很少，提前套 `features` 或 `settings` 只会增加层级而不增加语义。

这份对话输入是普通工程 brief，不是需要逐字保真的大 PRD，因此不触发 PRD 切分。
