# MILESTONE — MILE-0009 · 需求收件箱、多 PRD 与 Monorepo 范围治理

> 方向性产物（非冻结、不走 ACK）。本里程碑把生产项目建模为“独立需求持续进入、每份需求独立改版”，建立从原始材料收件箱到多 PRD 规格、版本引用和 monorepo 修改范围的完整链路。

## 5.1 范围评估

**In Scope（版本级）**

- **需求集合模型**：把 `.ai/references/prd/` 从“单份项目级 PRD 的模块目录”升级为“项目内多份独立需求规格的集合入口”，明确新需求与已有需求改版是两个不同动作。
- **日期化稳定身份**：每份需求使用 `YYYY-MM-DD-<requirement-slug>` 作为稳定 `prd_id` 和目录名；日期取首次进入当前项目 Butler 体系的日期，需求改版或标题变化均不改目录身份。
- **分层目录与版本**：项目级 `prd/00_INDEX.md` 登记所有需求；每份 PRD 在自己的目录维护 `00_INDEX.md`、模块切片和 `.archive/vN/` 全量历史。
- **多 PRD 引用**：引用能够唯一表达 `prd_id + prd_version + module_slug`；一个迭代可以同时钉住多份 PRD 的不同版本，一份 PRD 也能被多个迭代承接。
- **原始需求收件箱**：把项目根 `origin/` 明确为用户原始需求材料的可选收件箱，支持文件、对话和外部文档等输入来源，而不把 `origin/` 变成必经流程。
- **收件箱处理与回执**：增加 `/butler:inbox`，支持扫描、内容指纹、分类、去重、确认后路由；用 `.ai/INBOX.md` 记录源文件、状态、建议去向、实际产物和来源关系，不复制整份原文。
- **分类路由**：收件箱先判断材料属于全新需求、已有需求新版、补充材料、模糊想法或无需推进内容，再分别路由到 PRD 首切、PRD 更新、需求脑暴、里程碑候选或仅记录状态。
- **更新闭环**：为每份 PRD 独立执行 diff、认亲、先归档后更新、影响面扫描和状态查看；补持久更新回执，使 `/butler:prd status` 不依赖对话记忆。
- **Monorepo 工作区地图**：为多目录仓库建立稳定工作区键到实际包路径的项目级地图，优先复用 package manifest 身份，目录移动时只改地图、不改历史 PRD。
- **需求级代码范围**：每份 PRD 声明主要实现包、允许配套修改包、只读上下文包和明确排除包；模块工作区只能是总范围子集，范围外修改必须先确认扩张。
- **兼容迁移与工程验证**：迁移现有扁平 PRD 结构，保证已冻结或已收口 AC 的历史引用仍可解析；补确定性校验、fixture、双宿主接线和端到端回归。
- **新版 PRD 迁移指南**：随迁移能力交付独立的人类操作指南 `docs/prd-migration-guide.md`，并从 `HUMAN_GUIDE.md` 建立入口；指南必须讲清迁移前盘点、日期化 `prd_id` 生成、目录搬迁、MILESTONE 指针改写、冻结/已收口 AC 的兼容策略、迁移后验证与失败恢复，不能只提供机器配方。

**Out of Scope（版本级）**

- 不强制所有个人、小需求或对话输入经过 `origin/`、`/butler:inbox` 或 PRD；快速路径继续合法。
- Butler 不新增、改写、移动、归档或删除 `origin/` 内的用户原稿。
- 不按 monorepo 包目录嵌套或复制 PRD；跨包需求仍只有一份稳定 PRD，以显式工作区范围表达影响面。
- 批量扫描不自动开启里程碑、迭代或需求脑暴，不覆盖 `.ai/MILESTONE.md`、`.ai/CONCEPT.md`、`.ai/00_IDEATION.md` 等单一活工作区。
- 不自动修改已冻结或已收口 AC；进行中迭代仍走 amend 重冻，已收口工作仍以新迭代承接。
- 不为每份原稿生成内容重复的“万能整理稿”，也不把 AI 分析摘要冒充逐字权威 PRD。
- 当前只开启里程碑，不预分配任何承接迭代号；各路线项开始时再从迭代台账领号。

**关键交付目标**

- 新需求进入时创建新的日期化 `prd_id`，已有需求新版进入时准确匹配原 `prd_id`，两条路径不再混淆。
- 每份 PRD 独立维护模块、版本、归档和更新记录；项目级索引可以按需求、状态和工作区找到规格。
- 任一 AC 都能明确还原自己引用了哪几份 PRD、各自哪个版本和哪些模块，历史验收不随 live 最新版漂移。
- `/butler:inbox` 能识别未处理、已处理、源文件已变化和忽略的材料，并从一份原稿追到一个或多个派生产物。
- `/butler:prd update <prd_id>` 能产生可持久恢复的更新回执，记录版本变化、模块认亲、归档、三态影响面和用户处置。
- Monorepo 需求进入方案与执行阶段后，计划文件和实际改动都能与确认过的工作区写范围对账；AI 需要越界时必须先亮明原因。
- 旧单 PRD 项目可以兼容迁移，旧路径和已收口 AC 仍可回溯；不用 PRD 的项目行为保持不变。
- 使用者可以仅按 `docs/prd-migration-guide.md` 完成一次旧项目迁移，并核对活跃、排队、归档 MILESTONE 与冻结/已收口迭代的引用均未断链；`WorkCode.nosync/apps` 作为多目录、单旧 PRD 服务多个里程碑的真实回归样例。

## 5.2 理解阐释

- **核心问题**：现有 Butler 把 PRD 当作“一份项目规格书不断从 v1.0 升到 v1.1”，而实际生产项目通常是需求 A、B、C 持续进入，每份需求还有自己的版本。单一 `prd/00_INDEX`、全局 `.archive/vN/` 和单值 `prd_version` 无法表达这种需求堆叠。
- **输入端缺口**：`origin/` 名义上是收件箱，现行能力却主要是供 `/milestone` 读取 brief；它没有未处理识别、来源指纹、分类路由和处理回执，团队协作时无法稳定回答“产品同事这份材料处理过没有、成为了哪个需求”。
- **落盘端缺口**：第一份 PRD 的模块直接散落在 `prd/` 根后，第二份独立需求没有身份边界，模块 slug、版本号和归档会混在一起；更新流程也无法指定到底更新哪份需求。
- **Monorepo 缺口**：多应用、多公共包仓库中，一个需求可能主要属于某个 app，同时涉及共享 UI、API client 或类型包。只靠自然语言描述，AI 容易顺手修改相邻包；若按包嵌套 PRD，又会让跨包需求无家可归或被重复存储。
- **设计判断**：PRD 目录保持项目级、按日期化需求身份扁平排列；代码边界通过项目工作区地图和每份 PRD 的显式范围声明表达。目录身份解决“它是哪份需求”，工作区范围解决“这份需求允许改哪里”。
- **个人使用边界**：这套能力按需求复杂度启用，而不是按团队人数启用。小任务可以直接对话；长期项目、多需求并行、频繁改版或跨会话恢复时，个人用户同样受益。
- **权威性边界**：`origin/` 保存用户原话，`.ai/INBOX.md` 保存处理回执，里程碑和脑暴产物允许有损归纳，PRD 模块切片必须逐字无损；各层不得互相冒充。
- **整体影响**：预计涉及 references、PRD split/update/status、AC/TECH_PLAN/VERIFY 引用契约、origin/milestone/ideation 入口、项目知识文件夹、命令注册、Codex skills、Claude commands、hooks、迁移与状态审计。
- **讨论视图**：`docs/research/2026-07-22-prd-inbox-monorepo-design.html` 展示了“需求材料 → 收件箱 → 身份判断 → 日期化 PRD → 工作区范围 → 受限执行”的视觉基线；规则真源仍以本里程碑后续迭代产物为准。
