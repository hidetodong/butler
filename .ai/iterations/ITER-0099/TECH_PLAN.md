## Design Decisions

**改动落点**：`tools/butler-upgrade/upgrade.py`（摘要口径）、`migrations/manifest.json`（白名单）、`scripts/test-butler-upgrade.py`（测试）。

**决定一：排除清单收敛为单一定义。** 现在 `hook_source_files()` 与 `target_hook_files()` 各写一遍过滤条件，本次缺陷正是两处口径可以各自漂移的直接后果。新增模块级常量 `NON_DEPLOYED_HOOK_FILES = frozenset({"conftest.py", "pytest.ini"})` 与判定函数 `skip_hook_file(rel)`，把现有的 `tests/`、`__pycache__`、`.pytest_cache`、`.pyc` 判断连同新增的清单查表收进同一处，两个收集器都只调它、各自不再持有条件。常量旁注明理由：这两个文件仅供仓内跑 hook 单测，不随部署铺设，计入摘要会让项目侧永远无法与白名单对齐。

排除按 posix 相对路径整串匹配，不按文件名匹配，避免误伤子目录下的同名文件。

**这不是新开例外，而是把一条本就不完整的排除补完整。** 已验证：`conftest.py` 是 0 字节空文件，`pytest.ini` 全文只有 `[pytest]` / `pythonpath = .` / `testpaths = tests` 三行，其存在的唯一目的就是驱动 `tests/` 目录——而 `tests/` 早已在排除清单内。排除这两个文件与既有的排除 `tests/` 完全同构。

**决定二：白名单以「历史版本按新口径的去重摘要」为唯一定义域**，覆盖 v0.2.0 起每个改动过 `templates/hooks` 的 tag，共 10 个值，含此前缺失的 v2.18.0 / v3.0.0 / v3.1.0。当前源摘要仍由代码 `known | {tree_digest(source)}` 自动并入，不硬编码。

**不再对任何单值作特殊处置。** P2 与 P3 初稿都把 `4ff6400939b6cabf…` 当成来源不明项讨论过（先倾向保留、后判定移除），两次都是错的：复算证明它就是新口径下 v2.2.0–v2.13.0 的摘要，按决定二重算会自然产出它，不需要任何特殊分支。原判断之所以出错，是因为归因时用旧口径去匹配它。

**原白名单是混口径脏数据，这是本缺陷的旁证。** 旧白名单 7 个值里 6 个按旧口径（含脚手架）算，唯独 `4ff64009` 按新口径算，且 v2.2.0–v2.13.0 这一段同时存在两种口径的值。最合理的解释是：当年已有项目撞过同一堵墙，有人把该项目的实测摘要手工补进白名单救急，未追根因。重算白名单同时消除这处历史污染。

**AC 覆盖**：AC1 由决定一直接满足；AC2 由决定一 + 测试 B；AC3 由决定二 + 测试 D；AC4 由复算脚本的命中矩阵；AC5 由 butler-radar 实跑 plan；AC6 由测试 C；AC7/AC8 由测试运行与 CI。AC3 原本含「对来源不明项作出显式决定」，该子项因归因纠正而消解——不存在来源不明项，AC3 收敛为「白名单等于历史版本新口径去重摘要集」。

**关键假设及验证方式**：假设「`conftest.py` 与 `pytest.ini` 不影响 hook 运行时行为」。**已在 P3 内验证成立**：grep 确认 `butler_gate.py`、`butler_advisor.py`、`lib/` 与 `rules/` 全无对二者的引用，且 `conftest.py` 为空文件。假设已闭合，P4 不需重复证伪。

**替代方案与取舍**：
- 往白名单加 butler-radar 现有摘要 `a8f61cf…`：正是当年对 v2.2.0 那批项目做过的事，白名单里那个混口径的值就是它的遗留。它只救撞上门的那一个版本段，其余各有各的文件集，等于要为每种部署裁剪各补一次，且口径分叉依然存在、下次照样复发。放弃——本次要修的就是这种打补丁方式积累出来的结果。
- 改成逐文件比对（项目每个文件内容命中「该路径的历史已知内容集合」即放行）：比树摘要更宽容且不受文件集差异影响，但要维护全历史逐文件内容清单，实现与存储都重得多。本次缺陷不需要这个量级的改造。放弃，记为将来若再出现文件集差异时的升级路径。
- 不改代码、要求用户手工把缺失文件补进项目：把工具缺陷转嫁给用户，且违反「不写被观测项目」的边界。放弃。

**影响面与更小可行方案审查**：改动只影响 `sync_hooks` 前置校验的判定输入，不触碰写入集合、备份恢复与 journal。更小的方案（只加白名单）已在替代方案中否决——它治不了根因。范围没有可再缩小的余地，也不应扩大到 profile 解析（已在 Out of Scope）。

## Failure Paths

- **白名单重算算错** → 全部项目继续失配。不比现状更坏，但会白费一次发布。测试 D 断言当前源的新口径摘要在白名单内，可捕获算法与数据不一致；复算脚本输出命中矩阵作为人读复核。
- **排除清单写错文件名**（例如写成 `pytest.cfg`）→ 排除静默失效，摘要口径回到出错前状态。测试 A 断言清单里每个名字在 `templates/hooks` 下真实存在，写错即红。
- **两个收集器只改了一个** → 口径重新分叉，本缺陷复现。测试 B 对同一棵目录树断言两个函数返回完全相同的文件集，是防复发的核心一道。
- **新代码配旧白名单的中间态** → 依然全项目失配。因此代码与白名单必须同一次提交落地，不接受分两次发布（已写入 AC 风险）。
- **项目侧存在 `conftest.py`**（某些跑过 `sync_hooks` 的项目确实被铺过）→ 新口径忽略它，摘要仍能匹配。这是预期行为：这两个文件不参与 hook 判定，忽略它们不构成防护缺口。
- **真被篡改的 hook 树被放过** → 这是本次改动唯一的安全风险方向。排除项仅限两个测试脚手架，任何 `butler_gate.py` / `lib/` / `rules/` 下的内容改动仍进摘要、仍被拒绝；测试 C 用改动过的 fixture 断言拒绝行为未削弱。

## Test Strategy

新增用例挂在 `scripts/test-butler-upgrade.py`，与既有用例同一入口，保证一条命令全跑。

- **测试 A（清单有效性）**：`NON_DEPLOYED_HOOK_FILES` 中每个相对路径在 `templates/hooks` 下真实存在。防止清单腐化成空操作。
- **测试 B（口径一致性 → AC2）**：构造一棵含 `conftest.py`、`pytest.ini`、`tests/`、`__pycache__`、`.pyc` 与正常规则文件的目录树，断言 `hook_source_files()` 与 `target_hook_files()` 返回的相对路径集合完全相同，且均不含被排除项。
- **测试 C（负向防护 → AC6）**：以当前源铺一棵项目侧 hook 树，分别制造两种偏差——① 修改 `rules/phase_gate.py` 内容，② 增加一个项目独有的 `rules/custom.py`——断言两种情况下 `plan` 仍抛 `UpgradeError` 且不产生任何写入。
- **测试 D（白名单自洽 → AC3）**：断言当前 `templates/hooks` 的新口径摘要出现在 manifest 白名单或由代码自动并入；并断言白名单内不存在无法被任何历史版本复现的值（用复算脚本产出的集合做对账，避免测试内跑 git 拖慢）。这一条正是能机械捕获混口径污染的检查——旧白名单在它面前会立刻红，因为 6 个旧口径值都无法被新口径复现。
- **回归**：`python3 scripts/test-butler-upgrade.py` 既有用例全绿；`scripts/verify-ci.sh` 涉及本次改动的检查项通过。
- **端到端**：在 butler-radar 上跑 `plan --json`，确认不再出现 hook 树失配（AC5）。证据按 verification-evidence 记录。

**验证盲点（不写成已覆盖）**：
- 本机只有 6 个已部署项目，无法证明新白名单覆盖了世界上所有部署裁剪变体。其他机器上若存在别的裁剪组合，仍会失配。真正的收敛要等部署侧也有机械定义，本迭代不做。
- 测试 D 依赖复算脚本的产出做对账，脚本本身的正确性靠人读命中矩阵确认，不是机器闭环。
- 部署路径在 v1.0.0 时代由 AI 照文档手工执行，没有历史记录能证明每个项目当年到底铺了什么；「9 文件与 v1.0.0 逐字全等」是事后比对的结论，不是部署时的凭据。
