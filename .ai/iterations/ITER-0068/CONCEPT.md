# 一句话意图

讨论好但尚未开工的里程碑先放进候办区，不占用 `MILE-NNNN`；只有真正推进时才领取下一个连续号。

# Problem

- 当前里程碑录入和开启几乎是同一个动作，讨论结束就可能写入正式号。
- 用户暂时不想做这个方向时，现有语义只能把它留在 active，或标成 abandoned 并永久消耗号码。
- 这会让后来真正开工的内容拿到更大号，不符合“正式开工顺序就是里程碑顺序”的直觉。

# Users and Scenarios

- 用户与 AI 已把一个大方向讨论清楚，但决定暂不开工：保留草稿，不领号。
- 用户随后要推进另一个大方向：新方向领取当前下一个正式号。
- 以前的流程过早开了里程碑，但还没有任何迭代开工：可退回候办并释放这个最新号。

# Constraints

- 已被迭代、归档或交付引用的里程碑号不能回收。
- 候办内容必须可跨会话恢复，不能只留在对话记忆。
- 候办不得参与 active 里程碑、Goal 或迭代自动归属判定。
- 不为候办内容引入另一套单调数字号码。

# Scope

- 增加未编号候办区和候办草稿的落盘契约。
- 拆分“录入/讨论”与“正式开启/领号”。
- 定义可回收与不可回收的边界，并补状态审计。
- 同步 Claude 命令、Codex skill、规则卡和项目能力摘要。

# Out of Scope

- 不让已经绑过迭代的里程碑换号。
- 不新增多 active 里程碑或暂停态。
- 不实现自动排期、优先级计算或候办清理器。
- 本迭代不切版、不生成 migration、不升级外部项目。

# Risks

- 如果退回条件过宽，会产生已有迭代指向不存在里程碑的历史断链。
- 如果候办详情仍写在 `.ai/MILESTONE.md`，新里程碑 overwrite 时会丢失。
- 如果审计只看最大号，无法及时发现中间缺号或孤立候办草稿。

# Open Questions

- 无。用户已明确要求：暂不做的讨论项进待办区，并把下一个正式号留给真正开工的内容。
