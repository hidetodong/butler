# Codex 结构化提问卡片：让 Butler 的有限选项确认可点击，并在宿主不支持时可靠降级

候办键: codex-structured-question-cards
候办状态: deferred
规模: milestone

## 范围评估

### In Scope（版本级）

- 为 Butler 定义统一的结构化提问合同：当宿主提供原生选择卡片时优先使用；宿主不提供时，回退为简短、编号清楚的文字选项。
- 建立 Codex 各运行模式和产品界面的能力表，区分单选、多选、自由输入、一次可问问题数、选项数，以及卡片不可用时的真实表现。
- 盘点 Butler 中适合卡片化的有限选项决策，例如 P2 验收清单确认、P3 技术方案确认、升级分流和候办提升；开放式需求探索仍用自然语言提问。
- 为当前只支持单选的宿主定义多选降级规则：少量独立判断可拆成多个“是 / 否”问题；选项较多或彼此关联时改用文字输入，不把单选伪装成多选。
- 保持确认语义和审计结果不变。无论用户点击卡片还是输入文字，最终都必须物化为同一份 Butler 状态，例如 `ack-frozen` 或方案确认记录。
- 保持 Claude Code、Codex、ChatGPT 桌面端和 Pi 的兼容边界：各宿主使用自己的原生能力，没有原生卡片的宿主继续使用文字交互。
- 用真实 Butler 会话验证卡片触发率、少打字的实际收益、错误选择后的修改路径和文字降级是否稳定。

### Out of Scope（版本级）

- 不替换或绕过宿主的命令执行、网络访问、文件写入和外部操作审批；这些安全确认继续由宿主控制。
- 不要求所有 Butler 对话都切到 Plan mode，也不让卡片能力阻塞 P4 实施或其他正常流程。
- 不把宿主内部工具名当成 Butler 的永久公开接口；规则描述能力和行为，适配层负责映射当前可用工具。
- 不在缺少真实使用证据前建设 MCP server、自定义 ChatGPT UI 或通用表单系统。
- 不删除用户 ACK，也不借交互优化自动开启危险模式；只是改变用户提交同一决定的方式。

### 关键交付目标

- 在支持结构化提问的 Codex 会话里，适合有限选项的 Butler 确认可以直接点击完成，不再要求用户重复输入“确认”。
- 在默认模式、其他宿主或能力不可用时，同一流程自动退回文字选项，不丢问题、不误判回答，也不改变阶段门禁。
- 单选、多选和开放式问题有明确分流，Butler 不会展示一个看似可多选、实际只能单选的误导界面。
- 卡片回答与文字回答产生相同的状态记录，并能通过现有阶段检查、审计和跨会话恢复。
- 真实使用数据能够回答自定义 UI 是否值得做；若原生能力已经覆盖主要场景，就以轻量适配收口，不继续扩大架构。

## 理解阐释

Claude Code 的 `AskUserQuestion` 可以把问题和选项显示成可点击界面。Codex 也有宿主提供的结构化提问能力，但当前可用范围更窄：本次确认到的能力只在 Plan mode 暴露，每个问题提供少量互斥选项和自由输入，不原生支持多选。

Butler 当前主要由 Markdown skill、规则文件和 hook 组成。skill 可以要求模型在能力可用时发起结构化提问，但不能自己绘制卡片，也不能保证每个 Codex 模式都暴露同一个工具。因此正确落点不是把某个内部工具名散写到所有规则里，而是先定义“有限选项优先卡片、不可用就文字降级”的共同合同，再由 Codex 适配层执行。

P2 和 P3 的整体确认最适合先做，因为它们通常只有“确认 / 修改 / 暂停”这类互斥结果。真正的多选需求不能硬塞进单选卡片：项目较小时可拆成几个独立判断，复杂时应保留文字输入。只有真实使用证明这些场景频繁且文字降级明显拖慢流程，才值得评估带自定义界面的 MCP 插件。
