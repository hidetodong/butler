# PRD 改版的实现面对账：从切片变化推到代码落点，并证明没有漏

候办键: prd-impact-reconciliation
候办状态: deferred
规模: milestone

## 触发这个方向的真实漏项（2026-08-06）

在 `apps` 仓的 signal-assistant 应用上，PRD `2026-07-10-ai-signal-assistant` 当天连做两轮改版（Confluence doc version 37 → 42 → 43）。逐字 diff、事务化 apply、归档快照、回执，这些都做对了。

漏在下一步。改版之后我给用户列了一份「代码要改什么」的清单，把 v42 新增的三层保存机制的落地范围**只算到了策略和调度**，漏掉了同样在这个模型里的**渠化图和相位**。

> 三层保存机制是 v42 新加的一章：L1 是页面上的工作副本（编辑中的状态，没落库）、L2 是已保存到服务端的配置、L3 是当前真正在跑的配置。规矩是编辑只改 L1，点「保存配置」才写 L2。

用户看完清单直接问「怎么没有渠化图和相位的保存」。回去核了才发现，漏掉的那半边问题比我写出来的那半边还严重：渠化图在编辑向导第 1 步切到第 2 步时就已经写进后端了，而渠化页底部那个「保存配置」按钮一个字节都不写、只是跳页。

**兜住这次的是用户的一句话，不是任何流程。**

### 四个具体原因

**一、让一张子表定义了范围。**
源文档 §4.1 是一张很干净的「操作 → Toast / 表现」表，列了策略抽屉保存、策略复制删除、调度抽屉保存、调度删除四行，看上去就是「哪些操作只写 L1」的全集。它其实不是——那一节的标题是「**策略运行计划页面**各操作写到哪一层」，带页面限定词。渠化那半边写在 §2 的散文段落里，以及 §4.2 另一张表的一行里。表格抢注意力，散文不抢，于是散文那半边整节掉了。

**二、原文自己的定义把人往错方向带。**
§1 那张 L1/L2/L3 表里，L1 行的「谁读它」列写的是「策略列表、调度列表、月历、当日时段、图例」——全是计划页的东西，渠化图和相位面板一个没列。这既助长了我的误判，本身也是源文档的一处缺口。**从这里能推出一条通用教训**：切片里对某个概念的定义性描述，可能本来就是不完整的，不能当边界用。

**三、没有枚举这一步。**
我从「读完切片」直接跳到「凭印象去代码里 grep」。中间缺的那一步是：先把这一章提到的所有实体列成一张表——涉及哪些页面、哪些编辑入口、哪些按钮、哪些数据层级、哪些接口——再逐个下钻。有这张表，渠化和相位不可能掉。

**四、清单写完没有回检。**
我没做正反两个方向的配对：正向是「源里每一条规则，在清单里都有归宿吗」，反向是「清单里每一项，都指得回源里的具体条目吗」。任何一条配不上就是漏。这一步只要做了，当场就能发现 §2 整节没有对应项。

### 但更该记的是流程层的缺口

`prd-update.md` 的三态影响扫描，问的是「哪些**产物**受影响」——里程碑路线项、当前 AC、已归档的 AC。它**从来不问「哪些代码受影响」**。

于是从「切片变了」到「代码要改哪」这一跳，完全在 butler 的管辖之外：没有要求产出什么、没有覆盖标准、没有留痕，全靠模型当场发挥。发挥对了是运气，发挥漏了没有任何东西会拦。这次逐字 diff 和事务化 apply 都做对了，漏就漏在这块无人区。

还有一个副作用：这份分析只以对话里一段话的形式存在过。会话一结束就没了，下一轮改版也没法复用——想知道「上一轮改版判过哪些代码落点、每一条的结论是什么」，无处可查，只能从头再判一遍。

## 范围评估

### In Scope（版本级）

- 在 `prd-update` 的 apply 之后增加一步「实现面对账」：对本轮每个变更过的模块，产出一张「规则条目 → 代码落点 → 现状判定」的表。
- 判定用封闭枚举四态：`已实现`（须给文件与行号）、`要改`（须给落点）、`待定`（须给待谁拍板）、`不适用`（须给理由）。没有第五种，也不许留空。
- 强制双向覆盖检查。正向：源里每条规则都要配到清单的某一行。反向：清单每一行都要指回源里的具体条目。配不上就报缺口，不许出结论。
- 枚举先于判断：先从切片派生「本轮涉及的实体清单」（页面 / 编辑入口 / 按钮 / 数据层级 / 接口），再逐实体下钻代码，禁止直接凭印象检索。
- 结果落盘成可回查产物，绑本轮 `update_id`，与改版回执并列存放。
- 把「一张表不等于全集」写进读纪律：标题带限定词的表、以及散落在正文里的同机制规则，必须显式收集后再判范围。

### Out of Scope（版本级）

- 不自动改代码、不生成补丁。对账产出的是判断，不是改动。
- 不替代 P1–P5。对账结果是 P1/P2 的输入，AC 与方案仍走既有生命周期。
- 首版不做静态分析或调用图推导。代码落点由模型检索加人工复核，只要求给出可验证的文件与行号。
- 不对未变更的模块做全量重扫，只覆盖本轮新增 / 变更 / 移除的那几片。
- 不把「找不到代码落点」伪装成 `不适用`。找不到就是缺口，如实报。
- 不因为对账未完成就阻断改版本身；改版事务与对账是两件事，前者失败必须回滚，后者缺失只能记账。

### 关键交付目标

- 改版结束就能回答「这一轮代码要动哪些地方」，而且这个答案带覆盖证明，不是模型现场发挥的产物。
- 漏一条能被机械发现，而不是靠人恰好看出来。
- 下一轮改版能读到上一轮的判定结论，不必从零重判。
- 不使用 PRD 的项目、以及现有 `split / update / status` 三条路由的行为保持不变。

## 理解阐释

现在这条链只走了一半。改版工具把「原文变了什么」这件事做得很硬：逐字切片、先冻后更、哈希回执、可验证可回滚。但「原文变了，所以代码要改哪」这一跳，交付物是零——它只活在对话里，而且没有任何标准约束它是否完整。

漏一条规则和漏一整节的代价差别很大，但两者被发现的概率是一样的：全看有没有人恰好读出来。这次是用户读出来的。把这一步产物化、并且给它一个能机械检查的完整性标准，正是为了把「有没有人看出来」换成「配不上就报错」。

双向覆盖是这里的关键。单向的检查挡不住这次的漏法——我列出来的每一项都指得回源，正向检查一路绿灯；漏掉的是源里有、清单里没有的那部分，只有反过来从源往清单查才看得见。所以两个方向缺一不可。

首版刻意不碰静态分析。这个问题的难点不在「找不到代码在哪」，而在「根本没想到要去找」——是范围枚举的失败，不是检索能力的失败。先把枚举和覆盖这两件便宜的事做扎实，真实使用如果证明检索本身也不够准，再单独评估要不要上更重的工具。
