# 关键节点状态可信闭环：防止 AI 宣称已更新但落档仍陈旧

候办键: state-transition-trust-gate
候办状态: deferred

## 范围评估

### In Scope（版本级）

- 定义迭代开启、阶段切换、迭代收口、提交、切版、里程碑/候办变化与会话交接等关键节点的状态一致性合同，明确真实环境、权威台账、派生摘要和对话声明各自的真源与同步责任。
- 把可确定计算的事实从叙述缓存中剥离：active/current、backlog 数量、版本、Git 提交/tag/推送可用性等优先实时派生或跨源机械对账，不允许同一事实多份静态副本长期漂移。
- 扩展状态审计与 reconcile 能力，识别“已提交但仍写等待提交”“同一文件同时写 backlog 有/无”“版本/tag/发布状态不一致”等确定性矛盾，并返回具体陈旧文件、冲突事实和修复动作。
- 为迭代 CHANGELOG → `.ai/project/` topic 的折叠增加逐条处置覆盖：每条 delta 必须路由到对应 topic，或明确标记不影响长期知识并给出理由，不能只靠 topic 路径与哈希证明“更新过”。
- 建立完成声明门槛：AI 在对外声称“已更新 / 已完成 / 已提交 / 已发布”前必须回读并通过相应节点检查；检查失败时 fail-closed，亮明 stale/unknown，不得用写操作成功代替状态一致。
- 将关键负向场景接入审计、双宿主工作流、progress 输出和真实仓 dogfood，确保查询进度时优先展示当前事实并暴露记录漂移。

### Out of Scope（版本级）

- 不要求每次迭代机械修改所有项目文档，不以无意义 touch 或改写时间戳冒充同步。
- 不尝试用自然语言解析器理解所有叙述内容；可确定事实走结构化/机械校验，剩余语义继续保留显式 drift review。
- 不新增第二套项目状态台账，不让 reconcile receipt 反客为主成为新的事实真源。
- 不自动执行 Git commit、push、tag、发布或远端保护配置；只读取、核对并如实报告能力与状态。
- 不因网络或远端 API 不可用伪判成功或失败；无法确认时输出 `unknown`，不得沿用陈旧缓存冒充当前事实。

### 关键交付目标

- AI 只有在真实状态、权威落档、派生摘要和回读检查一致后，才能向用户宣称关键节点已经完成。
- 可计算矛盾必须被机械审计阻断，并准确指出“哪份文件、哪条事实、与哪个真源冲突”。
- 项目知识折叠从“记录了若干 topic 哈希”升级为“每条变更都已处置且有覆盖依据”，同时不强迫触碰无关文档。
- progress、handoff 与收口报告不再静默展示已经过时的提交、版本、backlog 或下一动作信息。
- ITER-0090 暴露的陈旧案例全部成为永久负向 fixture，现有结构审计全绿但语义冲突的情况不再被判为可信完成。

## 理解阐释

当前 Butler 已经具备较强的结构门禁：迭代收口会检查归档、delivery、evidence、台账、handoff、fold receipt 与 topic 哈希。但这些检查主要证明“文件存在、格式正确、某些文件曾被更新”，不能证明记录描述的仍是当前事实。

ITER-0090 提供了直接反例：Git 已存在提交，但 `task-state` 与 `frontier` 仍写“等待提交 / 尚未提交”；`frontier` 同时声称 milestone backlog 有 1 项和为空；现有 `audit-project-state.py --allow-unreleased` 仍能整体通过。用户看到 AI 口头宣称已更新，而落档继续展示旧状态，会对整套可追溯机制失去信任。

这个方向解决的是“状态变化后的可信投影”，不是增加更多文档。设计重点应是少缓存、节点对账、写后回读和矛盾阻断：稳定长期事实写进既有权威产物；动态事实查询时派生；需要跨文件投影的内容在关键节点统一 reconcile；AI 的完成声明必须以检查结果为前置条件。

系统影响预计涉及 lifecycle/iteration close 合同、project digest/fold receipt、task-state/handoff、state auditor、progress 工作流、双宿主完成汇报协议与验证 fixture。实现需特别处理 Git 提交发生在迭代收口之后、远端状态不可用、非迭代候办写入以及语义检查无法完全机械化等边界，避免建立新的状态副本或把所有维护动作强塞进迭代。
