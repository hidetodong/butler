# TDD 证据增强：防测试改弱、有效 Red、跨语言 Adapter 与实际改动对账

候办键: tdd-evidence-hardening
候办状态: deferred

## 范围评估

### In Scope（版本级）

- 在 MILE-0012 轻量 Red→Green 配对已有真实使用反馈后，增强 TDD 过程证明的可信度，而不是预先一次建设完整平台。
- V2 固定 cycle 起点与测试内容：引入必要的 baseline/文件指纹，识别 Red 后测试变化，并为合法重做提供 supersede 语义。
- V3 识别“有效 Red”：区分目标行为缺失与语法、依赖、收集、超时等基础设施失败；按真实需求引入 adapter 或机器可校验的失败 oracle。
- V4 对账最终实际改动：把非平凡生产代码 diff 映射到有效 cycle 或明确 N/A，并处理 Monorepo workspace、并行 cycle 和同文件测试等复杂边界。
- 所有增强继续复用现有 P1–P5、AC、TECH_PLAN、verification evidence 与 Goal 真源，不建立平行生命周期。

### Out of Scope（版本级）

- 不重复建设 MILE-0012 已交付的轻量 Red/Green 配对检查。
- 不在缺少真实 badcase 前承诺所有语言零配置支持，也不为理论完整性预建 adapter DSL。
- 不全面强制所有任务采用 TDD；纯文档、生成投影和无运行逻辑修改继续允许 N/A。
- 不把 coverage 百分比或 mutation testing 设为通用硬门；需要时另行评估。

### 关键交付目标

- 每一项增强都必须对应 MILE-0012 dogfood 或外部项目暴露的真实绕过案例，不能只因“以后可能需要”而实现。
- 测试被改弱、无关失败冒充 Red、配置或测试集合漂移、计划外生产改动等具体问题，按最小必要机制逐项关闭。
- 新语言支持优先通过项目提供明确测试命令和失败 oracle 接入；只有重复需求出现后才沉淀标准 adapter。
- 增强开启时能提高证明强度，未开启时不改变轻量 V1 和普通项目行为。

## 理解阐释

轻量 V1 的价值是先让“采用 TDD”从口头声明变成同一命令先失败、后通过的机器记录。它故意不解决所有作弊或误判路径，因为在没有真实使用前，很难判断 baseline、文件哈希、adapter、并发锁和 diff 对账中哪些真的值得承担长期复杂度。

本候办保存后续增强方向，但不把它们提前绑成一个必须整体启动的大版本。每一阶段都应从真实 badcase 出发，优先增加最小检查；若简单规则已经够用，就不继续向完整过程审计平台扩张。
