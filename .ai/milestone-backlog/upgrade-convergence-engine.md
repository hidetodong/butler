# Butler 升级收敛引擎：文件所有权、确定性迁移与可恢复诊断

候办键: upgrade-convergence-engine
候办状态: deferred

## 范围评估

### In Scope（版本级）

- 把 Butler 项目升级从“严格但容易被现场状态卡住的文件更新器”改为“有明确所有权、可重建基线和确定性迁移链的机械收敛引擎”。
- 把目标项目文件分为三类：可由最新模板重新生成的 Butler 产物、需按 `schema_version` 迁移的结构化状态、必须原样保留的用户与语义内容，三者分流处理。
- 建立项目级部署回执（候选路径 `.ai/butler-deployment.json`），登记已安装版本、Butler 管理的具体文件或 marker 片段及其指纹；把版本机器真源与人读入口版本戳明确分工。
- 将 hook 所有权从“整棵 `.claude/hooks/` 目录”收窄到 Butler 登记的具体文件；用户自己的 hook 和 settings 条目原样保留。
- 重构升级计划器为虚拟文件图：全部 action 按版本与声明顺序从上一步内存结果读取，产生唯一最终 diff 后再一次事务落盘。
- 对可重新生成的入口、hooks 和宿主投影直接收敛到最新版本，不逐版反复落盘 `regen / sync / restamp`；只有结构化数据按 schema 迁移链逐步转换。
- 将普通漂移从“第一个异常即停”改为一次列全的结构化诊断；每项给出稳定错误码、路径、所有权、预期/实际状态和 `可安全修复 | 需确认 | 必须人工处理` 分类。
- 可重建的 Butler 管理内容纳入同一升级 diff 和一次用户确认；计划与诊断保持零写入，apply 继续使用 hash 复核、lock、backup、journal 和失败恢复。
- 对无部署回执的旧项目建立受控认领路径：能根据旧版戳、marker 和 Butler 稳定文件身份证明的部分自动建回执，无法证明的待写目标亮出逐文件差异后等待确认。
- 将 `.ai/PROJECT.md → .ai/project/` 等需理解自然语言的语义迁移移出核心升级链；保持 legacy 兼容读取，以 `semantic_pending` 告知用户另行执行有人迁移，不阻断其他机械升级。

### Out of Scope（版本级）

- 不让升级器或模型在用户电脑上解析 Markdown 散文、推断业务语义或临时发明迁移步骤。
- 不为 migration 开放通用 shell 或无边界文件写入；继续只允许有限 typed action、白名单路径与可验证前后置条件。
- 不把“更顺滑”曲解为静默覆盖所有未知文件、删除安全阻断或绕过 symlink/路径越界检查。
- 不支持在 Butler 全托管文件中保留任意本地改动；合法定制必须放入 user-managed 区、独立用户文件或明确的扩展点。
- 不把修复项目文件的确认顺带扩大为机器级 `global-install`；修改 HOME 继续是独立、显式确认的执行域。
- 不自动改写 PRD、需求四件套、历史迭代/里程碑归档、交付文档或 `origin/` 原稿。
- 不在未经真实旧项目验证前删除 legacy 读取支持或强制所有项目立即完成语义迁移。

### 关键交付目标

- 从任一 manifest 已知部署版本直接升到当前版本，其最终受管状态必须与按发布链逐版升级完全一致。
- 正常老项目不因用户自有 hook、settings 条目或入口 user-managed 内容而阻断升级，也不丢失这些内容。
- 一次 plan 列出所有问题与修复路线；用户不需通读 migration 或源码，就能知道哪些会自动修复、哪些需确认、哪些必须人工处理。
- 可证明归 Butler 管理的缺失、旧版或漂移内容可从最新模板安全重建；无法证明所有权的文件绝不被静默覆盖。
- 计划、修复、结构化迁移、最新产物重生成和部署回执更新位于同一项目事务；任一步失败后项目与回执一起恢复到升级前。
- 完成跨版本矩阵，覆盖直跳/逐版等价、用户扩展保留、受管漂移修复、旧项目认领、语义待办不阻塞、失败恢复和重复执行幂等。
- 现有新项目初始化、机器级 setup、非 PRD 对话流、P1–P5 产物链和不使用 Butler 升级的项目行为保持不变。

## 理解阐释

现有升级器对数据安全较严格：plan 零写入，遇到未知状态 fail-closed，apply 前重核 hash，执行使用 lock、backup、journal 和失败恢复。体验问题不是它会乱写，而是它把“不确定”大多退化成首个异常字符串，既不一次列全问题，也不说明文件归谁、可否重建和下一步怎么做。

根因是三类状态被混在同一发布版本迁移链中：入口和 hooks 本是可从最新模板重建的派生产物；`.ai/butler.config.json` 等是需维护 schema 的结构化状态；`.ai/PROJECT.md` 等项目知识则是不能由机器理解后随意重组的语义内容。三者共用 `regen / migrate / split` 的粗粒度模型，导致可安全修复的产物被整体漂移卡死，不可机械迁移的内容又进入核心升级决策。

新模型以“最终收敛”取代“逐版重放文件写入”。发布版本链仍用来选出结构化 schema 迁移和兼容义务，但可重建产物只用当前最新模板生成一次。直跳与逐版的等价性由虚拟文件图和跨版本矩阵证明，而不靠“现在 action 刚好不冲突”的偶然性。

部署回执不是安全边界或防篡改机制，而是本地所有权与已安装状态证据。新项目由 init 生成；旧项目只能根据旧版戳、marker、稳定文件身份和可验证指纹受控认领。受管文件被本地改动时，计划必须亮出 diff；用户对整体计划的一次确认可同时授权重建，但无法证明归 Butler 所有的内容仍不得覆盖。

语义迁移与机械升级的边界必须硬分。像 `.ai/PROJECT.md → .ai/project/` 这样需把自然语言内容按主题路由的动作，应作为不阻塞的 `semantic_pending` 待办告知用户；核心升级只承诺机械可验证的转换。这样既不弱化安全停机，也不让无关的入口、hook 和配置升级被语义任务卡住。

这份对话输入是 Butler 自身的普通工程 brief，不是需要逐字保真的外部 PRD，因此不触发 PRD 切分。
