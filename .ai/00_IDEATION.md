# 一句话结论

Butler 应保留一个负责冻结需求、方案和状态的控制中心，同时把 P4 实现拆成多个边界明确的执行槽并行推进；先实现“单迭代、多 Agent 并行 P4”，验证稳定后再考虑多个迭代同时执行。

# 当前问题

现有 Butler 把以下三件事绑定成一个全局单例：

1. 同一时刻最多一个活跃迭代。
2. 项目根只有一套当前工作区四件套。
3. 一个主 Agent 同时负责决策、实现、集成和验证。

这种模式安全、容易审计，但 P4 中原本可以独立进行的实现也被迫串行。长迭代或跨模块迭代因此不能充分利用多个 Agent。

# 设计目标

- 保留 P1 理解、P2 验收冻结、P3 方案准入和 P5 整体验证。
- 允许多个 Agent 同时实现互不冲突的工作包。
- 保证每项实现都能回溯到 AC、TECH_PLAN、提交和验证证据。
- 防止子 Agent 擅自扩张范围、修改权威状态或绕过门禁。
- 让并发失败能够局部回收，不污染其他执行槽和主分支。

# 非目标

- 不让多个 Agent 各自成为完整 P1–P5 的控制中心。
- 第一版不解除“最多一个活跃迭代”的约束。
- 不允许子 Agent 自行修改 AC、TECH_PLAN、里程碑或迭代台账。
- 不以并发为理由降低验证、独立复核或收口标准。

# 推荐架构

## 控制面串行，执行面并行

```text
主 Agent / Coordinator
  P1 理解
  P2 冻结验收
  P3 方案准入
        │
        ├── 执行槽 A → Agent A → 独立工作树
        ├── 执行槽 B → Agent B → 独立工作树
        └── 执行槽 C → Agent C → 独立工作树
                    │
              集成队列逐个合并
                    │
              P5 整体验证与独立复核
```

主 Agent 是唯一能改变需求、验收、方案和运行状态的执行者。子 Agent 只接收已经通过 P3 的工作包，在独立 Git worktree 或分支中实现、验证并返回提交与证据。

# 并发单位：执行槽

执行槽不是新迭代，也不是子 Agent 的自由任务。它是 TECH_PLAN 中可独立交付、可独立验证、写入边界明确的 P4 工作包。

建议在 TECH_PLAN 增加 `Parallel Execution Plan`：

| 执行槽 | 负责 AC | 可写范围 | 输入契约 | 依赖 | 合并顺序 |
|---|---|---|---|---|---|
| SLOT-A | AC-01、AC-02 | `src/api/**` | 已冻结接口约定 | 无 | 1 |
| SLOT-B | AC-03 | `src/ui/**` | SLOT-A 的公开接口 | 接口契约已冻结，不依赖其内部实现 | 2 |
| SLOT-C | AC-04 | `tests/**` | AC 与公开行为 | A、B 可并行准备，最终组合验证 | 3 |

每个执行槽至少声明：

- 槽标识和目标。
- 对应的 AC。
- 精确可写路径与唯一 owner。
- 允许读取但不允许写入的范围。
- 输入、输出和接口契约。
- 前置依赖与合并顺序。
- 槽级验证命令和期望证据。
- 失败、漂移和冲突时的返回条件。

# 执行槽状态机

```text
queued
→ ready
→ executing
→ submitted
→ integration-check
→ merged
→ verified
```

异常状态：

| 状态 | 含义 | 处理人 |
|---|---|---|
| `blocked` | 缺少外部条件或依赖 | 主 Agent 决定等待、改序或停机 |
| `drifted` | 实现发现 AC 或方案假设不成立 | 主 Agent 按事实回退 P1、P2 或 P3 |
| `conflicted` | 与其他槽发生路径或语义冲突 | 文件 owner 或主 Agent 处理 |
| `rejected` | 未通过范围、证据或集成检查 | 原执行槽修复后重新提交 |

子 Agent 遇到 `drifted` 时只能报告，不得自行修改 AC 或 TECH_PLAN 后继续实现。

# 权限和所有权

## 单写者状态层

只有主 Agent 可以写入：

- `.ai/CONCEPT.md`
- `.ai/AC_LIST.md`
- `.ai/TECH_PLAN.md`
- `.ai/VERIFY_REPORT.md`
- `.ai/ITERATIONS.md`
- `.ai/MILESTONES.md`
- `.ai/task-state.md`

子 Agent 不得宣布迭代完成、直接合并主分支或改变 Goal 状态。

## 四层写入门禁

执行槽写入路径必须同时满足：

```text
宿主物理权限
∩ 需求 Workspace Scope
∩ TECH_PLAN Workspace Write Plan
∩ 当前执行槽 Owned Paths
```

任一层拒绝，写入即拒绝。共享文件、生成文件和锁文件必须指定唯一 owner；其他槽只能读取或提交变更请求。

# 子 Agent 输入与回执

## 输入

- 本执行槽负责的 AC。
- TECH_PLAN 中该槽的设计与路径边界。
- 冻结后的接口契约。
- 允许写入和只读的文件范围。
- 槽级验证要求。
- 基线提交和独立工作树信息。

## 固定回执

子 Agent 完成后返回：

1. 提交或补丁身份。
2. 实际改动文件清单。
3. AC 与实现的映射。
4. 已执行的验证及其机器证据。
5. 与 TECH_PLAN 的偏差。
6. 未解决的风险、阻塞和冲突。

没有证据的“已通过”只能视为 `reported`，不能关闭自动验证项。

# 集成门

槽级验证通过不等于迭代通过。主 Agent 在合并每个执行槽前必须检查：

- 实际改动路径没有越界。
- 改动仍能映射到分配的 AC。
- 没有未经批准改变接口、状态边界或数据契约。
- 提交基线与证据所对应的代码一致。
- 与已合并槽组合后，相关探测仍然通过。
- Must Fix、refuted AC 或开放漂移已经处理。

所有槽合并后，再进入 P5 的整体验证、Goal 裁决和独立复核。执行槽不能单独收口迭代。

# 并行准入判断

| 路线关系 | 并行判断 |
|---|---|
| 写入目录和语义边界独立 | 允许并行 |
| 只依赖已冻结公开接口 | 允许并行 |
| 共用生成文件或锁文件 | 指定唯一 owner 后允许 |
| 一个槽会改变另一个槽依赖的接口 | 不允许直接并行，先冻结契约或改为串行 |
| 共用数据库迁移序列 | 默认串行 |
| 同时修改同一核心模块 | 默认串行，除非进一步拆出唯一 owner |

并行判断不能只比较文件路径。即使文件不重叠，只要一个槽会改变另一个槽依赖的行为或契约，仍存在语义冲突。

# 多迭代并行的后续形态

多个迭代同时执行需要解除根级四件套的全局单例。候选布局：

```text
.ai/iterations/ITER-0093/live/
  CONCEPT.md
  AC_LIST.md
  TECH_PLAN.md
  VERIFY_REPORT.md
  task-state.md

.ai/iterations/ITER-0094/live/
  ...
```

根级四件套不再作为唯一真源，只保留为当前观察焦点的投影视图。迭代台账需要从单个 `current` 演进为活跃集合和集成焦点，例如：

```yaml
active_iterations:
  - ITER-0093
  - ITER-0094
integration_focus: ITER-0093
```

这一变化会影响 artifact pipeline、phase gate、handoff、Goal 裁决、证据归档和收口审计，因此不进入第一版。

# 分阶段路线

## R1：单迭代并行执行合同

- TECH_PLAN 增加执行槽结构。
- 定义槽状态机、输入、回执和单写者规则。
- 主 Agent 可以按依赖图派发多个子 Agent。

## R2：路径门禁与证据绑定

- 写前门禁增加执行槽 Owned Paths。
- diff 对账增加槽身份和实际路径检查。
- 验证证据绑定槽、提交和基线。

## R3：集成队列

- 定义槽提交、检查、合并、拒绝和重试流程。
- 每次合并后运行受影响验证，全部合并后运行整体 P5。
- 支持冲突和方案漂移回流。

## R4：迭代级 live 产物

- 将当前四件套真源迁移到迭代目录。
- 根级文件改为投影或兼容入口。
- 改造 hooks、artifact pipeline、handoff 和 Goal 读取层。

## R5：多迭代同时执行

- 台账允许多个执行态迭代。
- 引入迭代依赖图和集成焦点。
- 只有依赖、写入范围和契约均满足并行条件时才准入。

## R6：批量审计与版本级集成验证

- 对多个迭代统一执行范围审计、AC 核对和证据检查。
- 在里程碑收口前运行跨迭代组合验证。
- 对共享契约、数据库迁移和生成产物做版本级一致性检查。

# 风险与应对

| 风险 | 应对 |
|---|---|
| Agent 修改范围互相覆盖 | 精确 Owned Paths、唯一 owner、独立工作树 |
| 文件不冲突但行为冲突 | P3 冻结接口契约，集成阶段做组合验证 |
| 子 Agent 擅自改规格 | `.ai/` 权威状态单写，偏差只允许报告 |
| 并行结果长期排队无法合并 | 执行槽保持小而独立，明确依赖和合并顺序 |
| 测试证据对应旧代码 | 证据绑定槽、提交和基线 |
| 多活迭代让状态失真 | 第一版保持单 active；多活延后到迭代级真源完成后 |
| 主 Agent 成为新的吞吐瓶颈 | 集成检查机械化，按风险决定全量或受影响验证 |

# MVP 边界

第一版只实现以下闭环：

```text
单个 active 迭代
→ P1–P3 仍由主 Agent 串行完成
→ TECH_PLAN 拆出多个互不冲突的执行槽
→ 多个 Agent 在独立工作树并行实现
→ 主 Agent 按集成队列合并
→ P5 统一验证和复核
```

第一版不实现多 active 迭代、不迁移四件套路径，也不允许子 Agent直接操作权威状态。

# 当前结论

## 已确认方向

- Butler 的效率问题主要出在执行层，而不是需求和方案决策层。
- 应优先并行 P4，而不是让多个 Agent 各自维护一套互相竞争的控制状态。
- 主 Agent 单写权威状态、子 Agent 受限写实现，是兼顾效率与安全的基本结构。
- 第一版采用“单迭代、多执行槽”，多迭代并行作为后续能力。

## 待验证问题

- 执行槽是否作为 TECH_PLAN 的固定机器结构，还是另设独立 manifest。
- 子 Agent 的提交与 evidence record 如何形成稳定、可机械核对的身份绑定。
- 共享文件 owner 和跨槽变更请求如何表达，避免人为协调成为瓶颈。
- 合并后的验证选择采用完整重跑，还是基于影响面的分层策略。
- 多迭代并行是否有足够真实场景，值得承担四件套与状态机迁移成本。

# 新增分支：旁路 Agent 成果回钩主线（2026-07-29）

## 场景

- 项目推进主要集中在一个 Butler 迭代 Agent 上。
- 同时可能存在若干没有被当前迭代预先拆分和派发的旁路 Agent，处理暂时不相关的事情。
- 旁路工作完成后，用户希望其成果能够被主 Agent 发现、理解，并由主 Agent 决定是否接入当前迭代或后续工作。

## 初步判断

- 这不是上文“执行槽”的同义场景。执行槽由主 Agent 事先规划、授权和验收；旁路成果是事后提交，不能冒充已获当前迭代授权的执行结果。
- 不应直接写入 `02_SESSION_HANDOFF.md`。handoff 只负责同一主线跨会话恢复，旁路成果若混入会破坏它的断点入口职责。
- 候选抽象是“成果投递与认领”：生产者提交一份带来源、影响范围、验证与风险的回执；主 Agent 发现后先审查，再明确接受、延后、拒绝或转成参考资料。
- 该抽象可能不限于 Agent，也可覆盖人工研究、外部工具、另一个会话或独立工作树，因此具备泛用性。

## 与既有机制的潜在关系

- `references/` 适合承载调研和方案类资料，但缺少统一的待认领状态与代码变更身份。
- `INBOX.md` 已有“来源 → 派生产物”的稳定身份、状态和幂等思路，但当前语义是需求材料收件箱，不能未经设计直接拿来登记执行成果。
- 执行槽回执适合已规划任务；旁路投递可以复用其“改动文件、AC 映射、验证证据、偏差和风险”字段，但必须保留“尚未获主线授权”的状态。

## 当前待探测问题

- 实际主路径是“旁路 Agent 已修改同一仓库代码，主 Agent 认领变更”，还是“旁路 Agent 只交付调研、方案或实验结论，主 Agent 决定是否吸收”。两类都可支持，但第一版的身份、冲突和验证成本差异很大。

用户补充：代码修改与调研方案都有可能，并且更常见的是混合成果。因此第一版必须支持同一投递同时包含多种成果，不能按成果类型拆成两套互不相通的流程。

## 候选核心模型：贡献包 + 成果项

一个旁路工作提交一个“贡献包”（Contribution）。贡献包负责说明共同背景和来源，里面包含一个或多个可分别处置的“成果项”（Item）：

| 层级 | 负责回答 | 示例 |
|---|---|---|
| 贡献包 | 谁在什么基线上、为什么做了这组工作 | 一个旁路 Agent 对缓存问题的独立排查 |
| 成果项 | 具体交付了什么、在哪里、如何验证、主线怎么处置 | 调研报告、代码提交、实验数据、设计建议 |

必须允许逐项处置。主 Agent 可以接受调研结论、拒绝代码实现、延后实验建议；不能被迫整包接受或拒绝。

### 候选落盘结构

```text
.ai/contributions/
  00_INDEX.md                 # 待认领地图，只放身份、摘要、状态和入口
  CONTRIB-0001.md             # 贡献包回执，内含成果项表与处置结果
```

大体量原文、代码、补丁和证据不复制进回执，只保留稳定指针：

- 研究 / 方案：指向 `.ai/references/insight-*.md` 或其他受控资料。
- 代码：优先指向提交、分支、独立工作树或补丁，并记录基线 revision。
- 实验 / 验证：指向 evidence record、命令结果或可复现脚本。
- 已直接落在共享工作区的文件：记录实际路径、内容指纹和基线，但归属强度必须降级披露。

### 贡献包候选字段

- 稳定 `contribution_id`、标题、生产者线索、创建时间。
- 工作动机、是否由主线事先委托、所基于的 revision / 迭代状态。
- 成果项表：`item_id`、类型、摘要、locator、内容指纹、声明影响范围。
- 实际改动文件、验证动作与结果、依赖、偏差、已知风险。
- 与当前 AC / milestone / backlog 的候选关系；生产者只能提议，不能自行认领主线身份。
- 主 Agent 的逐项处置与理由。

### 状态语义

投递状态不能等于接纳状态。候选状态分为：

```text
submitted -> triaged -> accepted -> integrated
                     -> deferred
                     -> rejected
                     -> conflicted / stale
```

- `submitted` 只表示主线能发现它，不表示内容可信、代码获授权或当前迭代应吸收。
- `accepted` 表示主 Agent 明确认领某个成果项；代码仍需经过冲突检查和验证才能 `integrated`。
- 混合贡献的包级状态由各成果项派生，例如 `partially-integrated`，不能用包级状态覆盖逐项事实。

## 主 Agent 的发现与消费

推荐把发现接在有限的语义边界，而不是每轮自动吞入全部内容：

1. 冷启动读完当前状态后，只扫 `contributions/00_INDEX.md` 的未处置行。
2. P1 / P3 阶段边界检查是否有能改变问题理解或技术方案的新贡献。
3. P5 / 收口前检查是否还有与当前范围相关、尚未处置的贡献。
4. 用户可随时显式要求扫描贡献箱。

扫描只让主 Agent“知道有东西”，不能自动把内容注入当前 AC。主 Agent逐项审查后再路由：

- 研究 / 方案可接入 `.ai/references/`，再按参考资料规则影响 P1–P3。
- 代码可进入当前迭代的集成检查，也可转成后续迭代候办；不得因为文件已经存在就视为当前 AC 的实现。
- 若贡献推翻了已冻结假设，应按 Goal Calibration 回退对应阶段，不能静默改写四件套。
- 暂不相关成果可延后到 milestone backlog；纯记录可保留为 record-only。

## 三维压力测试

### 使用体验

- 优点：旁路 Agent 只需交一份统一回执，主 Agent 从一个索引发现全部待处理成果。
- 风险：字段过多会让小调研也背负重流程。MVP 应允许“摘要 + 一个成果项 + locator + 风险”最小提交，代码 / 多项混合成果才要求完整字段。
- 风险：如果主 Agent 每次冷启动都详读全部贡献，会重新制造上下文膨胀。索引必须只做地图，按相关性定向钻取。

### 架构

- 不能直接复用 `02_SESSION_HANDOFF.md`，因为它是单主线断点派生视图。
- 不能直接把贡献改叫 `INBOX.md` 的一种来源。需求收件箱处理的是“输入材料怎样派生需求产物”，贡献箱处理的是“已经做出的工作怎样被主线认领”；二者可以复用稳定身份、状态、指纹和幂等原则，但职责不同。
- 与上文执行槽的关系：执行槽是事前授权的贡献；旁路贡献是事后投递。未来可让二者共享成果项回执格式，但保留授权来源字段。

### 安全与可信度

- 生产者不得写主线 AC、TECH_PLAN、task-state、台账或宣布 Goal 完成，只能提交声明和指针。
- 回执中的“测试通过”是生产者声明；主线只有取得可重现证据或复跑后才能升级验证强度。
- 独立提交 / 补丁可以较强地绑定作者、基线和内容。多个 Agent 直接写同一个工作区时，事后回执无法可靠恢复逐行归属；路径与 hash 只能证明现状，不能证明作者。
- locator 必须限制在项目允许的范围，外部 URL 要脱敏；符号链接逃逸、缺失 payload、hash 漂移均应拒绝自动消费。

## 当前推荐的 MVP

- 新增 `.ai/contributions/00_INDEX.md` 与一包一文件的回执格式。
- 支持 `research`、`design`、`code`、`experiment`、`evidence` 五类成果项混装。
- 支持逐项 `accepted / deferred / rejected / integrated`，包级状态机械派生。
- 冷启动与 P5 只扫描未处置索引，不自动接入当前迭代。
- 代码项优先绑定 commit / patch / worktree；共享工作区模式允许登记，但明确低归属强度并强制主线重验。
- 第一版不做自动合并、不让旁路 Agent 修改主线权威状态、不建立通用 Agent 调度器。

## 新的待确认问题

- 这套协议是否可以要求旁路 Agent 在开工前或交付时主动按固定格式投递；还是必须把“主 Agent 事后从任意共享工作区和聊天记录中捞回无结构成果”也作为第一版主路径。后者只能尽力恢复，无法保证归属和完整性。

## 方向纠偏：不建立“接受 / 拒绝”审批流（2026-07-29）

用户指出，实际场景中的旁路工作通常由用户主动发起，不是陌生生产者向主线提交待审核贡献。模型无权替用户决定是否接受。因此上文候选状态流中的 `accepted / rejected` 建模不成立，不能进入后续设计。

纠偏后的问题是：

- 用户已经授权旁路工作，主 Agent 缺的是对成果的**发现、理解与衔接**，不是审批权。
- 若成果与当前主线冲突，模型应亮出冲突和影响，按 Butler 正常决策边界请用户裁决；不能伪装成模型自己的接受 / 拒绝。
- 在证明真实痛点和使用频率前，不预设必须新增 `.ai/contributions/` 子系统。统一回执、既有 `references/`、一句显式唤醒指令，或现有 handoff 的旁路变体都应作为更小替代方案比较。

### 当前必要性假设

只有出现以下一种或多种持续成本时，专门功能才可能值得做：

- 用户需要反复向主 Agent 人工复述旁路 Agent 做了什么。
- 旁路成果跨会话后难以发现，或 locator、基线、验证信息经常丢失。
- 多个旁路成果经常混在共享工作区，主 Agent 无法判断影响面和后续入口。
- 成果需要在主迭代的特定阶段自动提醒，靠用户记忆容易漏掉。

如果真实路径只是“偶尔开一个旁路 Agent，结束后把报告路径告诉主 Agent”，新增索引、身份和状态机会大于收益；此时一份固定的最小回执模板已经足够。

### 待探测的核心事实

- 今天实际最痛的一步是什么：找不到成果、需要重复解释、主 Agent 不知道何时读取、代码基线混乱，还是容易忘记把旁路结论纳入主线。
- 该场景在一个项目推进周期里大约出现多少次，是否经常跨会话或同时存在多个旁路 Agent。

## 当前收敛方向：旁路工作回执协议（2026-07-29）

用户确认，轻量回执符合最初想要的功能内容。当前不再预设贡献箱、自动扫描、身份台账或审批状态机。

### 一句话定义

用户主动发起的旁路 Agent 在收工时落一张短回执，记录已确认结论、成果位置、代码影响、验证事实和主线续接入口；用户随后把回执路径交给主 Agent，主 Agent据此衔接工作。

### 候选目录

```text
.ai/sidework/
  2026-07-29-cache-investigation.md
```

- 一项旁路工作一份文件，避免多个 Agent 争写同一索引。
- 文件名用日期 + 语义 slug，路径由旁路 Agent 在交付时回报给用户。
- 第一版不设 `00_INDEX.md`，也不让主 Agent默认扫描整个目录；由用户显式给路径完成回钩。
- 该目录保存的是项目内部旁路工作的交接事实，不混入“项目外部权威资料”语义的 `.ai/references/`，也不占用主线唯一的 `.ai/02_SESSION_HANDOFF.md`。

### 最小模板候选

```markdown
# 旁路工作回执 — <标题>

## 用户发起的目标

## 成果结论

## 成果与改动位置

| 类型 | 路径 / 提交 / 补丁 | 说明 |
|---|---|---|

## 验证事实

## 对主线的影响

## 主 Agent 续接入口
```

书写规则：

- 写最终有效结论，不写冗长思考过程和失败日志。
- 代码、长报告和 evidence 只给稳定指针，不复制正文。
- 有代码时记录工作基线、实际改动文件和提交 / 补丁；若直接写共享工作区，要明确这一事实，不能冒称独立归属。
- “对主线的影响”只陈述可能影响哪些模块、假设或后续动作，不替用户决定是否改方向。
- “续接入口”必须让另一个 Agent 不读原会话也知道先读什么、核什么、从哪里继续。

### 生产与消费

1. 用户主动发起旁路工作，并要求其收工时按模板写回执。
2. 旁路 Agent 完成实际工作后写一份新回执，不修改主线 `task-state`、四件套或 handoff。
3. 旁路 Agent 向用户返回回执路径。
4. 用户在主 Agent 会话中说“接回这份旁路工作：<path>”。
5. 主 Agent 读取回执和其中的必要指针，对照当前主线状态，报告已能直接纳入的事实、冲突和需要用户决定的问题，再按用户指示继续。

### 泛用边界

它的通用对象不是“Agent 贡献”，而是“脱离当前主上下文完成的一段工作”。因此同一协议可用于：

- 旁路 Agent 的代码 + 调研混合工作；
- 另一个会话做的实验或故障排查；
- 人工完成后希望交给 Agent 续接的工作；
- 外部工具执行后需要带回主线的结果。

通用的是回执字段和续接语义，不是自动调度、成果审批或多 Agent 状态管理。

### 暂不进入第一版

- 未读 / 已读 / 接受 / 拒绝状态。
- 自动发现、冷启动强制扫描和提醒。
- 自动合并代码或自动改写当前 AC / TECH_PLAN。
- 全局贡献身份、生产者信誉和跨项目汇总。
- 对任意无结构旧会话的自动打捞。

### 当前仍需验证

- 是否需要给这个协议一个显式 Butler 命令 / skill，还是先仅以模板和一句触发约定 dogfood。
- 文件名只用日期 + slug 时，同日同名冲突是否在真实使用中值得增加时间或短序号。
- 实际使用若经常忘记回钩，再评估最小提醒；在证据出现前不引入扫描索引。
