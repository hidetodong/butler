# 一句话结论

Butler 应保留一个负责冻结需求、方案和状态的控制中心，同时把 P4 实现拆成多个边界明确的执行槽并行推进；先实现“单迭代、多 Agent 并行 P4”，验证稳定后再考虑多个迭代同时执行。

# 当前问题

现有 Butler 把以下三件事绑定成一个全局单例：

1. 同一时刻最多一个活跃迭代。
2. 项目根只有一套当前工作区四件套。
3. 一个主 Agent 同时负责决策、实现、集成和验证。

这种模式安全、容易审计，但 P4 中原本可以独立进行的实现也被迫串行。长迭代或跨模块迭代因此不能充分利用多个 Agent。

# 设计目标

- 保留 P1 理解、P2 验收冻结、P3 方案准入和 P5 整体验证。
- 允许多个 Agent 同时实现互不冲突的工作包。
- 保证每项实现都能回溯到 AC、TECH_PLAN、提交和验证证据。
- 防止子 Agent 擅自扩张范围、修改权威状态或绕过门禁。
- 让并发失败能够局部回收，不污染其他执行槽和主分支。

# 非目标

- 不让多个 Agent 各自成为完整 P1–P5 的控制中心。
- 第一版不解除“最多一个活跃迭代”的约束。
- 不允许子 Agent 自行修改 AC、TECH_PLAN、里程碑或迭代台账。
- 不以并发为理由降低验证、独立复核或收口标准。

# 推荐架构

## 控制面串行，执行面并行

```text
主 Agent / Coordinator
  P1 理解
  P2 冻结验收
  P3 方案准入
        │
        ├── 执行槽 A → Agent A → 独立工作树
        ├── 执行槽 B → Agent B → 独立工作树
        └── 执行槽 C → Agent C → 独立工作树
                    │
              集成队列逐个合并
                    │
              P5 整体验证与独立复核
```

主 Agent 是唯一能改变需求、验收、方案和运行状态的执行者。子 Agent 只接收已经通过 P3 的工作包，在独立 Git worktree 或分支中实现、验证并返回提交与证据。

# 并发单位：执行槽

执行槽不是新迭代，也不是子 Agent 的自由任务。它是 TECH_PLAN 中可独立交付、可独立验证、写入边界明确的 P4 工作包。

建议在 TECH_PLAN 增加 `Parallel Execution Plan`：

| 执行槽 | 负责 AC | 可写范围 | 输入契约 | 依赖 | 合并顺序 |
|---|---|---|---|---|---|
| SLOT-A | AC-01、AC-02 | `src/api/**` | 已冻结接口约定 | 无 | 1 |
| SLOT-B | AC-03 | `src/ui/**` | SLOT-A 的公开接口 | 接口契约已冻结，不依赖其内部实现 | 2 |
| SLOT-C | AC-04 | `tests/**` | AC 与公开行为 | A、B 可并行准备，最终组合验证 | 3 |

每个执行槽至少声明：

- 槽标识和目标。
- 对应的 AC。
- 精确可写路径与唯一 owner。
- 允许读取但不允许写入的范围。
- 输入、输出和接口契约。
- 前置依赖与合并顺序。
- 槽级验证命令和期望证据。
- 失败、漂移和冲突时的返回条件。

# 执行槽状态机

```text
queued
→ ready
→ executing
→ submitted
→ integration-check
→ merged
→ verified
```

异常状态：

| 状态 | 含义 | 处理人 |
|---|---|---|
| `blocked` | 缺少外部条件或依赖 | 主 Agent 决定等待、改序或停机 |
| `drifted` | 实现发现 AC 或方案假设不成立 | 主 Agent 按事实回退 P1、P2 或 P3 |
| `conflicted` | 与其他槽发生路径或语义冲突 | 文件 owner 或主 Agent 处理 |
| `rejected` | 未通过范围、证据或集成检查 | 原执行槽修复后重新提交 |

子 Agent 遇到 `drifted` 时只能报告，不得自行修改 AC 或 TECH_PLAN 后继续实现。

# 权限和所有权

## 单写者状态层

只有主 Agent 可以写入：

- `.ai/CONCEPT.md`
- `.ai/AC_LIST.md`
- `.ai/TECH_PLAN.md`
- `.ai/VERIFY_REPORT.md`
- `.ai/ITERATIONS.md`
- `.ai/MILESTONES.md`
- `.ai/task-state.md`

子 Agent 不得宣布迭代完成、直接合并主分支或改变 Goal 状态。

## 四层写入门禁

执行槽写入路径必须同时满足：

```text
宿主物理权限
∩ 需求 Workspace Scope
∩ TECH_PLAN Workspace Write Plan
∩ 当前执行槽 Owned Paths
```

任一层拒绝，写入即拒绝。共享文件、生成文件和锁文件必须指定唯一 owner；其他槽只能读取或提交变更请求。

# 子 Agent 输入与回执

## 输入

- 本执行槽负责的 AC。
- TECH_PLAN 中该槽的设计与路径边界。
- 冻结后的接口契约。
- 允许写入和只读的文件范围。
- 槽级验证要求。
- 基线提交和独立工作树信息。

## 固定回执

子 Agent 完成后返回：

1. 提交或补丁身份。
2. 实际改动文件清单。
3. AC 与实现的映射。
4. 已执行的验证及其机器证据。
5. 与 TECH_PLAN 的偏差。
6. 未解决的风险、阻塞和冲突。

没有证据的“已通过”只能视为 `reported`，不能关闭自动验证项。

# 集成门

槽级验证通过不等于迭代通过。主 Agent 在合并每个执行槽前必须检查：

- 实际改动路径没有越界。
- 改动仍能映射到分配的 AC。
- 没有未经批准改变接口、状态边界或数据契约。
- 提交基线与证据所对应的代码一致。
- 与已合并槽组合后，相关探测仍然通过。
- Must Fix、refuted AC 或开放漂移已经处理。

所有槽合并后，再进入 P5 的整体验证、Goal 裁决和独立复核。执行槽不能单独收口迭代。

# 并行准入判断

| 路线关系 | 并行判断 |
|---|---|
| 写入目录和语义边界独立 | 允许并行 |
| 只依赖已冻结公开接口 | 允许并行 |
| 共用生成文件或锁文件 | 指定唯一 owner 后允许 |
| 一个槽会改变另一个槽依赖的接口 | 不允许直接并行，先冻结契约或改为串行 |
| 共用数据库迁移序列 | 默认串行 |
| 同时修改同一核心模块 | 默认串行，除非进一步拆出唯一 owner |

并行判断不能只比较文件路径。即使文件不重叠，只要一个槽会改变另一个槽依赖的行为或契约，仍存在语义冲突。

# 多迭代并行的后续形态

多个迭代同时执行需要解除根级四件套的全局单例。候选布局：

```text
.ai/iterations/ITER-0093/live/
  CONCEPT.md
  AC_LIST.md
  TECH_PLAN.md
  VERIFY_REPORT.md
  task-state.md

.ai/iterations/ITER-0094/live/
  ...
```

根级四件套不再作为唯一真源，只保留为当前观察焦点的投影视图。迭代台账需要从单个 `current` 演进为活跃集合和集成焦点，例如：

```yaml
active_iterations:
  - ITER-0093
  - ITER-0094
integration_focus: ITER-0093
```

这一变化会影响 artifact pipeline、phase gate、handoff、Goal 裁决、证据归档和收口审计，因此不进入第一版。

# 分阶段路线

## R1：单迭代并行执行合同

- TECH_PLAN 增加执行槽结构。
- 定义槽状态机、输入、回执和单写者规则。
- 主 Agent 可以按依赖图派发多个子 Agent。

## R2：路径门禁与证据绑定

- 写前门禁增加执行槽 Owned Paths。
- diff 对账增加槽身份和实际路径检查。
- 验证证据绑定槽、提交和基线。

## R3：集成队列

- 定义槽提交、检查、合并、拒绝和重试流程。
- 每次合并后运行受影响验证，全部合并后运行整体 P5。
- 支持冲突和方案漂移回流。

## R4：迭代级 live 产物

- 将当前四件套真源迁移到迭代目录。
- 根级文件改为投影或兼容入口。
- 改造 hooks、artifact pipeline、handoff 和 Goal 读取层。

## R5：多迭代同时执行

- 台账允许多个执行态迭代。
- 引入迭代依赖图和集成焦点。
- 只有依赖、写入范围和契约均满足并行条件时才准入。

## R6：批量审计与版本级集成验证

- 对多个迭代统一执行范围审计、AC 核对和证据检查。
- 在里程碑收口前运行跨迭代组合验证。
- 对共享契约、数据库迁移和生成产物做版本级一致性检查。

# 风险与应对

| 风险 | 应对 |
|---|---|
| Agent 修改范围互相覆盖 | 精确 Owned Paths、唯一 owner、独立工作树 |
| 文件不冲突但行为冲突 | P3 冻结接口契约，集成阶段做组合验证 |
| 子 Agent 擅自改规格 | `.ai/` 权威状态单写，偏差只允许报告 |
| 并行结果长期排队无法合并 | 执行槽保持小而独立，明确依赖和合并顺序 |
| 测试证据对应旧代码 | 证据绑定槽、提交和基线 |
| 多活迭代让状态失真 | 第一版保持单 active；多活延后到迭代级真源完成后 |
| 主 Agent 成为新的吞吐瓶颈 | 集成检查机械化，按风险决定全量或受影响验证 |

# MVP 边界

第一版只实现以下闭环：

```text
单个 active 迭代
→ P1–P3 仍由主 Agent 串行完成
→ TECH_PLAN 拆出多个互不冲突的执行槽
→ 多个 Agent 在独立工作树并行实现
→ 主 Agent 按集成队列合并
→ P5 统一验证和复核
```

第一版不实现多 active 迭代、不迁移四件套路径，也不允许子 Agent直接操作权威状态。

# 当前结论

## 已确认方向

- Butler 的效率问题主要出在执行层，而不是需求和方案决策层。
- 应优先并行 P4，而不是让多个 Agent 各自维护一套互相竞争的控制状态。
- 主 Agent 单写权威状态、子 Agent 受限写实现，是兼顾效率与安全的基本结构。
- 第一版采用“单迭代、多执行槽”，多迭代并行作为后续能力。

## 待验证问题

- 执行槽是否作为 TECH_PLAN 的固定机器结构，还是另设独立 manifest。
- 子 Agent 的提交与 evidence record 如何形成稳定、可机械核对的身份绑定。
- 共享文件 owner 和跨槽变更请求如何表达，避免人为协调成为瓶颈。
- 合并后的验证选择采用完整重跑，还是基于影响面的分层策略。
- 多迭代并行是否有足够真实场景，值得承担四件套与状态机迁移成本。
