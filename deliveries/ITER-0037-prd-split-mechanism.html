把大 PRD 切成切片的机制（PRD 切分机制）

ITER-0037 迭代交付（小版本）· MILE-0004 R2 收口 2026-07-09

本次交付目标

  • 上一块（R1）建了一份契约，规定"一份 PRD 存进 .ai/references/prd/ 之后该长什么样"——每个模块一片、切片必须逐字原文、每个模块有个终身不变的英文代号（slug）、带版本落盘。但它刻意只定了"结果该长什么样"，没定"怎么动手把 PRD 变成那个样子"——这个切分动作被明确留给了本轮 R2。
  • 本轮就是兑现它：新建一份机制文档，把"拿到一份大 PRD、怎么一步步切成那个知识文件夹"的程序写清楚。核心是四条纪律——顺着 PRD 自己的结构切、绝不把一条完整规则拦腰切碎、每片逐字照搬不概括、切之前先把方案摆给用户确认再落盘（不搞全自动黑箱）。

已完成内容

新建 Coder/40_Context_Management/prd-split.md——PRD 切分机制的程序规范，六节：

  • §1 定位（契约 vs 动作）：讲清本文件是"动作层"、去履行 R1 的 references-schema 契约；两者分工——"契约说结果该长什么样，本文件说怎么动手做出来"。用一张表把 slug 身份、无损切片、落盘、结构、判据五项全部回指 references-schema、不复制一份过来（避免将来两头改漂移）。
  • §2 边界识别（怎么切）：按 PRD 自己的结构切——它分几章讲几个功能、按"V1.1 修改项 1/2/3"组织，就顺着切，不自造边界。立红线：绝不把一条完整的规则/校验/文案从中间截断跨两片；两难时宁可切得粗（一片多含点）也不切碎（切碎会让某片验收时找不到完整规则）。
  • §3 slug 分配 + 写索引：首切时给每个模块分一个见名知意的终身英文代号（如 save-validation），此后 PRD 怎么改版都不动它；写 00_INDEX（这份 PRD 是什么 + 模块地图 + 登记表）。字段与规则全守 R1 契约。
  • §4 逐字保真：每片是对应模块原文的无损照搬——精确文案、精确校验规则一个字都不改、不删、不"顺手总结成一句"（少一字，将来验收就对不上真源）。唯一能摘要的地方是索引里的导航叙述。
  • §5 小 PRD 退化态：PRD 很小（就一个功能）时不另开特例、也不退回单文件——走同一套模型、只是模块数=1，这样它将来改版/钉版本一样无缝。
  • §6 soft 对齐（提议→确认→落盘）："soft 对齐"就是不硬切——AI 先把切分方案（模块清单、每个 slug、每片边界依据）摆给用户看、此时不写盘，用户确认或调整（"这两个该合成一片""这条规则被你切到两片了，并回去"）后才真落盘。配一条硬约束："未经确认不得落盘，宁可停下来问，也不擅自切。"

补最小触发：logic-protocol.md 的"外部参考资料注入"类型表加一行——用户在任意阶段丢来一份大/结构化 PRD，就走这套切分机制（而不是像小文档那样直接存成单文件）。判据回指 R1 契约、不重写。

关键变更 / 用户可感知变化

  • butler 现在知道"怎么把一份大 PRD 切开"了：以前只有"切完该长什么样"的契约、没有"怎么切"的程序；现在补齐。你在任意阶段丢来一份大 PRD，它会走这套机制处理，而不是笨拙地整份塞进一个文件。
  • 切分不会背着你硬来：最关键的用户可感知点——切之前 AI 一定先把切分方案摆给你确认（分几片、每片叫什么、边界怎么划），你点头或调整后才落盘。它不会自作主张把你 PRD 里一条完整的校验规则从中间截断。
  • 本轮仍是"半成品链条的一环"：这套机制目前只接了"用户手动丢 PRD"这一个入口。"开里程碑时 brief 本身就是大 PRD、自动触发切分并和路线图交叉挂钩"那条更顺的路是下一块（R3）的活，本轮还没接。
