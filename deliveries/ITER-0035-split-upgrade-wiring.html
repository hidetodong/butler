把 [split] 迁移标签接进升级执行器（并定死它是"问一句再迁"）

ITER-0035 迭代交付（小版本）· 独立迭代 收口 2026-07-08

本次交付目标

  • 上一版 v2.0.0 引入了一个迁移动作叫 [split]——把老项目那份单文件项目摘要 .ai/PROJECT.md 拆成 .ai/project/ 知识文件夹。这个动作的定义写在了迁移规范里，也给 v2.0.0 配了实例，但负责执行升级的规则 butler-upgrade.md 从来没同步认领它：/butler-upgrade 逐条处理迁移标签时，压根没有 [split] 这一项。真跑到这一步，AI 没有明确路径，只能临时回去翻定义硬拼——不是设计好的自动路径。
  • 还有一个悬而未决的口径：其它迁移标签都是"起始态对了就默默自动跑"，但规则又说"不强制立即迁"。那 [split] 到底是自动拆、还是先问用户一句？没定死（实例里写了"可暂缓"、却和"它是配方里的一步"打架）。
  • 本轮把这个接线缺口补上，并一锤定音：[split] 是 opt-in（英文"选择性加入"，这里就是"先问用户一句再迁、不问不动"），不是机械自动步。

已完成内容

  • 把 [split] 接进标签枚举（butler-upgrade §5.1）：升级执行器逐条认领的迁移标签清单里补上 [split]（指向新写的落地细则 §6.5），和 [rename]/[add-field]/[sync-hooks] 等并列不再漏。同处加了一段分类说明——机械步（改名、补字段、同步 hook、重打版本戳这些）起始态对了就默默自动落地；结构迁移步 [split] 是形态级大动作（一份文件 → 一个文件夹），必须"先问再迁"。
  • 新写落地细则 butler-upgrade §6.5，讲清执行器碰到 [split] 具体怎么办，四件事：① 先问用户（现在迁 / 继续用单文件、以后再迁）；② 选"继续单文件"就跳过这步、单文件照常受支持，其它机械步照跑；③ 真要迁时怎么拆（按主题路由进 00_INDEX + 各主题文件、拆出的新文件走 git add、删旧单文件）；④ 撞到冲突就停（目标已经拆了一半、或用户手工改过旧文件对不上，就不覆盖、停下报差异、等用户确认——绝不把用户手写的内容拆丢）。
  • 在迁移规范里补一句指路（migration-schema §4）：标签的语义定义仍以这里为唯一真源，只加一句"升级时它是'先问再迁'、落地细则见 butler-upgrade §6.5"，不把定义搬走、不两头写。
  • 升级完的验证清单加一行（butler-upgrade §7）：[split] 的结果必须二选一如实报告——已迁成文件夹 / 用户选了暂缓——不许有"该停没停、暂缓了却不报告、把用户内容拆丢"的闷声操作。
  • v2.0.0 迁移说明补上 opt-in 注：让那份实例配方自己也标清楚"第一步 [split] 不是机械必跑、执行器会先问"。

关键变更 / 用户可感知变化

  • 在老项目里升级 butler，不会被强行改结构了：升级碰到 [split] 会先问你"要不要现在把单文件项目摘要拆成知识文件夹"。你答"以后再说"，它就跳过、你的 .ai/PROJECT.md 原样不动、继续正常工作；该拿的版本更新（重打规则卡、更新版本戳）照样拿到。
  • 两种形态长期共存这条承诺被真正落到了执行层：以前"不强制立即迁"只是嘴上说，执行器其实没有"跳过"这条路；现在有了。
  • 安全兜底更明确：万一你手工改过旧文件、或文件夹已经拆了一半，升级会停下来问你，不会闷头覆盖把你写的东西冲掉。
