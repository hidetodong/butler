Verdict

方向成立，证明合同还没成立。

当前设计能保留 Red 和 Green 的命令记录，却不能排除“先写实现再启动 cycle”、 “同一命令换了测试集合”以及“额外生产改动没进入任何 cycle”等绕过路径。 如果现在启动，最可能交付的是一份形式完整、事实不够硬的 TDD 凭证。

HOLD
保留候办，不提升为正式 milestone。

六个 Must Fix 形成明确机器合同后，做一次定点复查即可；无需重新论证是否应该引入 TDD。

Must fix

六处会让“可信”名不副实的断点。

MUST / 01

Sidecar 与 evidence v1 的固定目录合同直接冲突

方案准备在 Green evidence 目录增加 tdd-cycle.json，但现有 verifier 只接受 record.json、stdout.log 和 stderr.log。多一个文件就会失败， Goal evaluator 也不会读取这个 cycle 文件。

修复合同

在同一 evidence 根中定义版本化的 cycle evidence 类型或 schema v2，把固定文件集、哈希、归档和 Goal 读取一次说清；不要放未受 verifier 保护的附属文件。

SOURCE · backlog:15,54 · tools/verification-evidence/evidence.py:303

MUST / 02

Baseline 没有绑定迭代起点，无法证明测试先于实现

如果执行者已经先改了生产代码，再调用 begin，后续依然可以得到一条漂亮的 Red→Green 记录。 当前设计要求拒绝“生产代码提前修改”，却没有定义“提前”相对哪个权威时刻判断。

修复合同

把 baseline 固定到迭代或切片开始时的工作树事实；要求 B→R 生产代码不变、R→G 测试和证明配置不变，P5 再确认最终文件匹配最后一次有效 Green/Refactor。

SOURCE · backlog:14,39,44

MUST / 03

tdd:on 同时被写成“可不阻断”和“必须兑现”

P1 被要求说明缺 evidence 是否阻止完成，意味着 on 可能只是提醒； 后文又规定 Iteration complete 必须满足 TDD obligation。一个开关不能承担两种完成语义。

修复合同

规定 tdd:on 必然对 required 切片形成 completion blocker。若需要只记录、不阻断的模式，新增独立 advisory 枚举。

SOURCE · backlog:11,43

MUST / 04

策略与 adapter 没有冻结，可在收口前被降级绕过

项目默认、单迭代覆盖和 workspace adapter 配置尚无唯一优先级；中途把 on 改成 off、替换 adapter 或修改命令后，已有 cycle 是否失效也没有答案。

修复合同

提供唯一 policy resolver，在 P1 固定 effective policy、workspace、adapter 与配置摘要；任何削弱义务或改变证明模型的修改都触发 Goal Calibration，并作废相关 cycle。

SOURCE · backlog:10,16 · local-constraints-schema.md:11

MUST / 05

相同 argv 不等于相同测试，更不等于相同证明条件

配置、依赖锁、插件、环境变量、随机种子和测试发现规则都可能改变实际执行的用例。 Green 可以在命令文本不变的情况下，通过缩小测试集合或切换配置获得。

修复合同

cycle 还要绑定 adapter 版本、配置和依赖锁哈希、受控环境指纹，以及 Red/Green 实际收集到的测试身份；任一漂移都使旧 cycle 失效。

SOURCE · backlog:20,40,56

MUST / 06

P5 没有把最终生产代码 diff 与 cycle 全量对账

P3 只要求规划“非平凡代码切片”，P5 只检查已声明的 required cycle。 执行期间额外修改未列入 TDD Strategy 的生产文件时，当前方案没有机械机制发现这部分绕过。

修复合同

增加类似 Workspace Scope 的 tdd check-diff：每个符合条件的实际生产改动都必须映射到有效 cycle 或经准入确认的 N/A，并明确重叠文件的依赖与失效规则。

SOURCE · backlog:18,20

Target contract

第一版应该承诺什么。

不必宣称能证明整个开发历史绝对遵循 TDD。更诚实、也更能落地的承诺是： 在固定策略、固定测试身份、固定配置和受控文件差异下，证明一段由 Butler 从开始到结束完整记录的 Red→Green 周期。

Policy

冻结义务

唯一 resolver 计算有效策略；后续弱化使已有 cycle 失效。

Baseline

固定起点

绑定工作树事实；目标生产代码已有不明变化时拒绝可靠 cycle。

Red

正确失败

测试实际运行；生产代码未改；失败命中声明的行为缺失 oracle。

Green

同证据通过

测试身份、配置和依赖不变；目标生产实现发生变化并通过。

P5

对账收口

最终 diff 全覆盖；完整回归通过；证据与最终工作树没有陈旧漂移。

Should fix

四个不会立刻击穿、但会持续制造假绿的缺口。

SHOULD / 01

Generic Runner 无法天然判断“有效 Red”

任意 argv 的非零退出可能来自断言失败，也可能来自编译、依赖、收集或环境错误。Generic Core 不能仅凭退出码给出可靠结论。

建议

generic 默认只产出弱证据；只有声明机器可校验的 Red oracle，或 adapter 具备可靠分类能力时，才能关闭 required obligation。

SHOULD / 02

状态机与 Runner 命令集合不一致

规则要求 supersede/reset，命令列表却没有这两个动作；refactor-confirmed/complete 也不是清晰的机器状态。

建议

补全状态转移表、允许动作、非法转移、终态和幂等规则；Refactor 后必须重新运行目标测试。

SHOULD / 03

R1–R3 横向拆分会留下可配置但不可兑现的半成品

R1 暴露开关和阶段义务，R2 才有 Runner，R3 才接入 Goal 与 P5。前两轮无法独立兑现已经暴露的承诺。

建议

在最终接线前保持能力不可对外启用，或改成可独立工作的纵向切片；新增 TECH_PLAN 一级章节时，同轮更新 artifact manifest、模板和结构检查器。

SHOULD / 04

敏感日志与并行 cycle 还只是“记得处理”

现有 evidence 会保存原始 stdout/stderr 且不自动脱敏；并行 cycle 覆盖同一文件时，也可能互相污染 baseline 和 Green 快照。

建议

把安全输出策略、配置秘密检测、cycle 路径锁或依赖图写进 R2 的明确验收项和负向 fixture。

Revised route

按可验证能力拆，不按文件层次拆。

路线项建议范围结束时必须真实成立
R1 / 合同冻结 Policy resolver、明确 off/on 语义、配置优先级、P1/P3 固定摘要、artifact manifest 与负向 fixture。 TDD 仍不对外启用，不产生半成品承诺。
R2 / 可信 cycle 版本化 cycle evidence、完整状态机、Red oracle、文件与配置指纹、supersede/abort、并发与安全日志。 一个 pytest cycle 可生成、校验、识别篡改并原子归档。
R3 / 对账收口 tdd check-diff、P5 adjudicator、Goal evaluator、VERIFY 投影、完整回归与陈旧检测。 漏 cycle、测试漂移、配置漂移、额外生产改动和陈旧 Green 都被拒绝。
R4 / 正式启用 Butler pytest dogfood、关闭态兼容、双宿主同步、迁移说明和完整 CI。 完成 dogfood 后，项目才能正式使用 tdd:on。

启动条件不是“文档补得更长”，而是六个断点都有机械答案。

修订完成后只做定点复查：Evidence schema、时间顺序、完成语义、配置冻结、测试身份和最终 diff 对账。全部形成明确合同，即可从候办提升。
