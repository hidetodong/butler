PRD 出新版怎么办：改版同步机制 /prd update

ITER-0040 迭代交付（小版本） 收口 2026-07-09

本次交付目标

  • 前四块（R1–R4）让"一份 PRD → 切成模块切片 → 挂进里程碑 → 验收钉住版本"都成了，但全是"第一次导入"的静态视角。真实项目里 PRD 天天改版（V1.1→V1.2 改个校验、加个功能），却一直没定改版了怎么办。
  • 本轮新建 /prd update 改版同步机制——把"PRD 出新版"变成一套确定性流程：搞清楚改了哪些模块、按新版重切这些切片、先把旧版整份冻存再更新到最新、然后报告谁受影响（还没开工的 / 正在做的 / 已经收工的三类），受影响的活按既有规矩重做或另开一轮。外加 /prd status 只读看板随时查现状。这是 MILE-0004"改版有兜底协议"的收官核心。

已完成内容

新建规则文件 Coder/40_Context_Management/prd-update.md（改版同步动作层，与 R2 的 prd-split 同族——split 管第一次切、update 管之后每次改版），八节：

  • 变更检测（清单优先 + diff 兜底 + 对账）：以你给的"修改项清单"为主（你最清楚改了啥），同时机器把旧切片和新 PRD 逐字比一遍兜底防漏，两者对不上的地方必须亮出来问你——不因你没提就当没改，也不擅自采信机器。
  • 重新派生 + 先冻后更：受影响模块按 R2 的切分规矩重切；落盘有硬顺序红线——旧版整份先冻进 .archive/v<旧版>/ 全量快照（打开就是当年完整规格），然后才把最新切片覆盖上去。顺序不能颠倒：live 一旦覆盖，旧版原文就没了，R4 钉版说的"回头能读到旧版"就落空。
  • 登记表认亲基础态：新版多出来的模块发个新代号（slug），少掉的模块标成"已移除"（切片留档、代号不回收）。至于模块改名、两个并一个、一个拆两个这种"还是不是同一个"的疑难认亲，明确留给下一块 R6，本轮只回答"多了谁、少了谁"。
  • 三态影响面报告（亮牌不自动）：改版后扫一遍"哪些活引用了这次改的切片"，分没开工 / 进行中 / 已收口三类摆给你看。只报告、绝不自动去改任何已冻结或已验收的东西——这是全机制的命门红线：静默改已冻结的活，就等于废掉了钉版和冻结的全部意义。
  • 受影响工作怎么处理（接既有规矩、只指路不改流程）：正在做的 → 走迭代内修订重新确认（amend 重冻）；已经收工的 → 收口的不能改，只能另开一轮承接（扩张转迭代）；还没开工的 → 不用动，将来做时自然对最新版。
  • /prd status 只读看板：不改任何东西，只汇总当前 PRD 版本 + 模块清单 + 最近一次改版的影响面，随时可查。
  • soft 对齐硬约束：改版和第一次切一样"先提议、经你确认、再落盘"——改版牵一发动全身（旧版会被冻、已冻结的活会被牵连），比首切更需要你在落盘前过目，绝不擅自改版。

关键变更 / 用户可感知变化

  • PRD 改版从此有章可循：给一份新版 PRD + 一句"改了哪些"，/prd update 会带你走完检测→重切→冻旧版→报影响面全程，每一步都要你确认。
  • 改版绝不暗中破坏已验收的活：受影响的已冻结/已收口工作只会被"亮牌提醒"，要不要动、怎么动由你拍板——不会有任何自动重写。
  • 旧版永远查得到：每次改版旧版都冻成自包含快照，配合 R4 钉版，回头审计"当年那次验收对的是哪一版规格"始终有据。
  • 不用 PRD 的人完全无感：这是一条新增的 opt-in 机制，普通开发流、对话驱动流、别的参考资料注入（Confluence/设计稿等）一字未改。
